## 1. ① gap 3→0 后 31 行的像素账 —— **2.5% 余量是算错的**

### 1.1 上一轮的口径 vs 本轮实测

上一轮报告 §7 写：

```
「像素账：1868×256 + 95×128 + 107×256 = 517,760 ≤ 524,288（只余 6,528 = 2.5%）」
```

这三项的**含义是错的**：

| 上一轮写法 | 实际含义 | 对不对 |
|---|---|---|
| `1868×256` | 1868 个对偶字形 | ✓（1,504 现役 + 364 新），但这**只算对偶** |
| `95×128` | 95 个 ASCII 记录 | ⚠ 实测 ASCII 段 = 94 个有墨矩形（95 唯一），8px 宽可两条共格 ⇒ 占 **47** 格位 |
| `107×256` | 107 个单字节汉字记录 | ⚠ 这 107 条记录**实测是 106 个格位**（105 条 16px 宽 + 2 条窄）|

**真正的漏项**：`1868×256 + 95×128 + 107×256` 这个式子里，
后两项被当成了「**额外加在 1868 之外的东西**」，但它们**本来就在图集里**，
而且**和图集里已有的 1,736 个对偶字形抢的是同一块 524,288 texel**。
所以正确的式子是：

```
需求 = (1736 + 364) × 256  +  [记录占的 texel]
     = 537,600             +  ~40,664
     = 578,264 texel   >   524,288 texel  ⇒  超 53,976 texel (10.3%)
```

（上一轮的 `517,760` 里把 `107×256=27,392` **重复计入了两次语义**：
既当成"记录自己的面积"，又当成"对偶之外的补充"，所以看起来还剩 2.5%。）

### 1.2 正确的像素账（逐条从盘上量，不靠估）

```
图集 = 1024 × 512 texel = 524,288 texel     （4bpp ⇒ 每 texel 半字节; 与"容器 262,144 B"自洽）
每个 16×16 字形 = 256 texel                  （格位 = 图集的原子单位）
图集格位总量 = 524,288 / 256 = 2,048 格位

现役占用（逐条从盘上量, 不是估）:
  ① 对偶码字形（网格 slot 0..1735）      1,736 格位  = 444,416 texel
  ② 记录字形（544 条 → 208 唯一矩形 → 有墨 204）:
       ASCII 段 (记录 idx 0..95)   94 个有墨矩形, 全 8px 宽  -> 47 格位
       汉字段 (记录 idx ≥96)      110 个有墨矩形, 108 个 16px -> 109 格位
       （4 个全空白矩形可与别人共格, 不计）
       小计（格位当量）                                158.8 格位 = 40,664 texel
  ------------------------------------------------------------------
  现役合计（实测, 网格 ∩ 记录 = 0 texel）            1,894.8 格位 = 485,080 texel
  空余（实测）                                         153.2 格位 =  39,208 texel
```

**★ 关键实测数字**：记录**不是免费的**，它占 **40,664 texel = 图集的 7.8%**。

**★ 第二个关键实测数字（反直觉，且**推翻了 §3 判据 1 的 153**）**：这剩下的 153.2 格位
**放不下哪怕一个 16×16 字形**——实测 **0 个**（`zx_r84_plan2.py` S1）。
原因是它被切成了 `32px 右边缘条 × 32 行` + `每两行之间的 2px 缝`，
**没有一个连续的 16×16 空洞**。⇒ 想再加字，**必须重排记录**。

**★ 第三个关键结论（真正的瓶颈，见 §3.4）**：
`153 格` 是**纯面积**上界，它假设 153 个 16×16 空洞可以任意摆放。
但「对偶 slot 是**一维**的」这条约束把可放位置锁死在 `(16c, y0+16r)` 晶格上，
一旦记录也要占格子，**现役结构下新字上限 = 0**。

### 1.3 744 字上移 48 px 会不会溢出？—— 不会溢出，但**换不来 364**

| 项 | 值 |
|---|---|
| gap 3→0 去掉的是 y=194..241 那 **48 行**（3 条 16px 带）| +48 行可用 |
| 现在记录带就住在这 48 行**下方**（EN 带 y=452..467 / KB 带 y=482..497）| 记录要搬家 |
| 行数上限（62 列，y=0 起步 16px stride）| 512/16 = **32 行** ⇒ 1,984 槽 |
| 地址可寻址（62 列 × 行）| rows=31 → 1,922 槽；rows=32 → 1,984 槽 |
| **但格位（面积）上限恒为 2,048**，与行数无关 | ← ★ 真瓶颈在这里 |

⚙ **判据：溢出不是问题**（48 px 上移在图集内，逐 texel 可验），
**"行数"也不是问题**（gap→0 后 32 行 × 62 列 = 1,984 槽 ≥ 任何可行字数）。
真正的墙是 **`字形数 × 256 texel ≤ 524,288`**，即**图集格位 2,048 是死的**。

**★ 上移的真实工作量比任务书写的大**：
任务书说「行 12..24 的 **744** 个字形整体上移 48 px」，
但现役盘已经用到 **slot 0..1735**，而 gap→0 会改变**行 12 及以后所有行**的 y，
所以必须搬的是 **slot 744..1735 = 992 个字形**（不是 744），
外加 **204 个有墨记录矩形**全部重排。

### 1.4 2.5% 余量够不够？—— **不够，实际是 -10.3%**

```
需求 = 485,080 (现役实测) + 364 × 256 = 578,264 texel
供给 = 524,288 texel
差额 = -53,976 texel = -210.8 格位   ⇔   需求是供给的 110.3%
```

⇒ **"2.5% 余量"这个前提本身不成立**：正确的余量是 **−10.3%**（超支）。

## 3. ★★ 为什么 364 不可达（三条独立判据）

### 判据 0（最硬）：★ 对偶 slot 是**一维**的 —— 这才是真瓶颈

```
对偶码 (lead,trail) ⇒ slot = (lead−0xA1)·94 + (trail−0xA1)    ← 一个整数
slot ⇒ 物理位置由 cave 公式**唯一决定**：
        row = slot // 62 ; col = slot % 62
        x = 16·col ; y = y0 + 16·(row + (gap if row ≥ gaprow else 0))
⇒ 「前 n 个 slot」占哪些格子**完全确定**，不能挑肥拣瘦。
⇒ 记录也必须落在同一张图集里、且**不能与格位重叠**。
```

**穷举结果（`zx_r84_ceil_final.py`，承认一维性 + 记录自由平移 + 不可重叠）**：

| ncol | y0 | gap | 最大对偶字形 n | **新字上限** | 说明 |
|---|---|---|---|---|---|
| 62 | 2 | +3 | **1736** | **0** | ★ **现役结构：图集已满到格子级** |
| 62 | 2 | +2 | 1798 | **62** | 只让出 1 条 16px 带 |
| 62 | 2 | +1 | 1860 | **124** | 让出 2 条带 |
| 62 | 0 | +0 | **1892** | **156** | ★ **全局最大** |
| 60/63/64 | 0 | +0 | 1892 | 156 | 更高 ncol **不再增加**（记录成为瓶颈）|
| 64 | 2 | +3 | 1792 | 56 | 改 cave 只换来 56 |

**⇒ 全局上限 = 1,892 个对偶字形 ⇒ 本轮最多再加 156 个新字。**
（与纯面积上界 1,889 吻合；差 3 是复用 4 个空白记录矩形换来的。）

**⇒ 现役盘的「新字上限 = 0」**：`zx_r84_plan2.py` S1 与 `zx_r84_ceil_final.py`
两条独立路径都得到同一结论。上一轮落 232 个字已经**把图集用到格子级饱和**。

> ⚠ **本报告早期版本的 +132 / +186 / +248 是 solver bug 的产物**（判据写成
> 「整块 `y..y+h` 全空的列」，会把记录塞进已占位置还报成功）。**已修**：
> `zx_r84_solve3.py` / `zx_r84_ceil_final.py` 改成逐行扫描 + 整块校验。
> **权威数字以上表为准。**

### 判据 1：面积（纯面积上界 = 153，但不可达）

```
524,288 texel 图集
− 40,664 texel 记录（有墨 204 个唯一矩形；ASCII 94 个必须留，引擎硬编码 idx 0..95）
= 483,624 texel ÷ 256 = 1,889 个 16×16 格位（纯面积绝对上限）
现役对偶已占 1,736 ⇒ **纯面积**允许再加 153
364 ⇒ 差 211 个     ← 即使"纯面积"也已经不够
```

### 判据 2：记录不能省

```
想省记录只能：
  a) 把 108 个 16px 汉字记录压成 8px  ⇒ 字形被切一半（可见损坏）✗
  b) 把记录画到图集外                ⇒ 不存在 ✗
  c) 把 ASCII 记录搬走               ⇒ 引擎硬编码用 idx 0..95，必须留 ✗
  d) 复用空白记录                    ⇒ 实测只有 4 个空白矩形，省 0～3 格 ✗
```

### 判据 3：地址/行数也不够

```
ncol=62 时最多 32 行（y0=0）⇒ 1,984 槽
即便这样也只有 1,984 − 1,736 = 248 个新槽 < 364
要把 1,736 现役也重铺才拿得到这 248（992 个字形要搬，见 §6.1）
```

**三条判据 + 判据 0 同时否证 ⇒ 364 不可达，且不是"努力不够"，是算术 + 一维寻址。**

### 3.4 ★ 更正：`opt.txt` / `zc_r84_plan2.py` 早期版本的 1612 是**错的**

早期 solver 用「整块 `y..y+h` 全空的列」当判据，导致把记录塞进已占位置还报成功
（`opt.txt` 的 "1612" 就是这么来的）。**已修**：
- `zx_r84_solve3.py` 改成逐行扫描 + 整块校验
- `zx_r84_ceil_final.py` 用同一判据做穷举
**权威数字以上表为准。**
