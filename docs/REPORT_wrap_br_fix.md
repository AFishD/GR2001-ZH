## 1. 背景：这个 bug 为什么危险

工具链的契约是「**CSV 里的换行 ↔ 盘上的换行**」：

```
盘上 {br}  →  CSV 里 1 个换行  →  注入回盘 {br}
盘上 {p}   →  CSV 里 1 个空行  →  注入回盘 {p}
```

round34 及更早的 `tcslib.wrap_render()` 破坏了前半段（dump 方向）：

* 每个 `{br}` 在 CSV 里渲染成 **2 个换行**（= 一个空行）；
* 每个 `{p}` 渲染成 **3 个换行**（= 两个空行）；
* 引擎的自动折行点渲染成**真换行**（与人工敲的回车完全一样）。

于是"人工只改一个字"就会触发注入端的折叠规则（1 换行 = `{br}`，≥2 换行 = `{p}`）：

```
盘上：…士 兵可获得…{br}1. 多次…{br}2. …{p}国会最高勋章…
旧 CSV：…士 兵可获得…(空行)1. 多次…(空行)2. …(空行)(空行)国会最高勋章…
        ↑ 每个 {br} 多出一个空行
再注入：…士兵可获得…{p}1. 多次…{p}2. …{p}国会最上勋章…
        ↑ 2 个真 {br} 变成 {p}（真·空行）；6 个建议断点变成 {br}；行尾空格被吃掉
```

用户是**非程序员、反复用 Excel 改同一条**，所以这不是"理论风险"：只要他对这 26 条里的
任何一条动一个字，盘上结构就会被改掉，而且**改得越多越乱**（§5-B 实测：再一轮就变成
`{br}×0 / {p}×9`，全部换行都成了空行）。

## 3. 根因（代码级）

### 3.1 `wrap_render()` 的 off-by-one（主因）

```python
# round34 及更早 (tools/text_csv/tcslib.py)
for kind, payload in parts:
    if kind == 'br':
        soft_lines.append(''); n_hard += 1            # ← 追加一个"空行"
    elif kind == 'p':
        soft_lines.append(''); soft_lines.append('')  # ← 追加两个"空行"
    ...
return '\n'.join(soft_lines), n_soft, n_hard
```

`'\n'.join(['A', '', 'B'])` = `"A\n\nB"` —— **2 个换行**（= 一个空行），而
`text_to_cell('A{br}B')` = `"A\nB"`（1 个换行）。**同一份数据，两个函数给出不同视图**：

| 盘上 | `text_to_cell`（解析口径的逆） | `wrap_render`（旧渲染口径） |
|---|---|---|
| `{br}` | 1 个换行 | **2 个换行** |
| `{p}` | 2 个换行 | **3 个换行** |

注入端 `cell_to_bytes_text` 的规则是「1 个换行 = `{br}`，≥2 个换行折叠成 1 个 `{p}`」
（与 `text_to_cell` 一致）⇒ **渲染端多出来的那一个换行，在下一轮就变成 `{p}`**。

### 3.2 建议断点与硬换行**不可区分**（第二个根因）

旧渲染把"引擎自动折行点"也写成 `\n`。于是 CSV 里三种东西长得一模一样：
盘上的 `{br}`、引擎的建议断点、人工敲的回车。注入端只能一律当 `{br}` 处理
⇒ 编辑一个字就把 6 个建议断点**固化**成硬换行（这是 round29 起就记录在案的
"固化折行"行为，但它是**隐式**发生的，用户并不知道）。

### 3.3 行尾空格被吞（附带发现，同一条链上）

旧渲染 `ln.rstrip(' ')` 会删掉每个折行点前的空格。因为空格被换行替代，观感无碍；
但一旦这些换行被固化（或反过来被丢弃），**空格就真的没了**：

```
盘上：…符合以下条件的士 兵可获得…          ← 中间有一个空格
旧 CSV：…符合以下条件的士\n兵可获得…        ← 空格被 rstrip 掉
注入后：…符合以下条件的士{br}兵可获得…      ← 空格永久丢失（实测于 B_before_bug.iso）
```

### 3.4 表达力边界：盘上的"连续标记"

CSV 的约定是「1 换行 = `{br}` / 空行 = `{p}`」，**无法表达** `{br}{br}`（两个连续显式换行）
或 `{p}{p}`（两个连续分段）——它们都会被渲染成一个空行。现役盘实测 **0 处**，
但工具链对此没有任何守卫（旧代码遇到就会静默给出一个不可逆的视图）。

## 4. 修法

### 4.1 新口径：进出严格互逆（`tools/text_csv/FORMAT.md` §3）

| 盘上引擎字节 | CSV 单元格 | 注入回盘 |
|---|---|---|
| `{br}` | **恰好 1 个换行** | 1 个换行 → `{br}` |
| `{p}` | **恰好 1 个空行**（连续 2 个换行） | ≥2 个连续换行 → 1 个 `{p}` |
| （无标记，引擎自动折行） | **`{WRAP}` 建议断点标记**（不换行） | **整段丢弃**，不写任何字节 |
| — | 人工敲的回车 | 1 个换行 → `{br}`（人工确认的硬换行） |

### 4.2 为什么给建议断点单独发明 `{WRAP}` 标记

需求是「建议断点与人工硬换行在语义上要能区分」，且「人工怎么改都不会意外改变盘上结构」。
可选的方案与取舍：

| 方案 | 问题 |
|---|---|
| 建议断点仍写成真换行，另加一列记录"哪些换行是建议" | 用户一改字/换行，字符下标就漂移，无法可靠映射；而且要用户理解两列的关系 |
| 干脆不插建议断点 | 破坏"一眼看到现在断在哪"的既有能力（用户明确要求保留） |
| **`{WRAP}` 行内标记**（采用） | 纯 ASCII、Excel 可见可复制、与 `{br}`/`{p}`/`{{BTN:XXXX}}` 不冲突；**注入时整段丢弃** ⇒ 天然"零风险" |

`{WRAP}` 的语义（写进 FORMAT.md §3.4，也是给用户的一句话）：

* **留着 / 删掉** ⇒ 盘上**零变化**（只是少了一条提示，文字自动接回一行）；
* **换成回车** ⇒ 那个位置恰好多 1 个 `{br}`（= 把建议变成硬换行，"人工确认"）；
* 标记插在**行尾空格之后**的零宽位置 ⇒ 去掉标记即逐字符还原原文本。

### 4.3 逐字符保真：`wrap_seg_spans()` + `mark_wrap_points()`

折行模型 `wrap_seg()`（忠实还原 `RSTextComponent::DoWordWrap`）返回的是**行文本**，
直接拼回去会丢空格。新增的 `wrap_seg_spans()` 用**同一套算术**返回每行的**字符区间**
`[(start, end)]`，区间首尾相接、覆盖整段；`mark_wrap_points()` 只在区间边界插标记：

```python
seg   = '…条件的士 兵可获得…'          # 盘上原文（含空格）
cell  = '…条件的士 {WRAP}兵可获得…'    # 渲染视图（标记插在空格之后）
strip_wrap_marks(cell) == seg          # ★ 逐字符保真（自检项）
```

一致性有断言保护：dump 每行都会校验 `wrap_seg_spans` 与 `wrap_seg` 行数/内容一致、
区间连续、且 `cell_to_bytes_text(text_zh) == 盘上原字节`。

### 4.4 四道防线（让"改 N 次也不会累积变坏"变成机器保证）

| # | 防线 | 位置 | 行为 |
|---|---|---|---|
| 1 | **往返自检** | `dump_text_csv.lossless_reason()` | 每行 `text_zh` 用**注入器的解析口径**回写，必须逐字节等于盘上原字节；不通过 ⇒ **拒绝写 CSV**（工程侧 `--allow-roundtrip-diff` 可强行导出，那些行标记为不可安全编辑） |
| 2 | **写错就拒绝** | `tcslib.scan_wrap_marks()` / `inject.scan_wrap_marks()` | `{WRAP` / `{ WRAP }` / `{WRAPP}` / `{ W R A P }` / `{WRP}` 等 ⇒ 注入前**全 CSV 前瞻拦下**，退出码 1，`--force` 也不能绕过（放行就会把 `"{WRAP"` 写进游戏文本） |

## 6. 已知限制

1. **旧格式 CSV（round34 及更早）必须重新 dump 才能安全编辑长段。**
   注入器会在 `.meta.json` 写着 `text-csv/1` 时**拒绝**被编辑过的 `wrap_w>0` 长段（exit 1）。
   若 meta 丢失，只剩一条**提示**（"没有 `{WRAP}` 却有好几处空行"）—— 此时工具无法 100% 判定，
   需要人工重新 dump。**`text_edited` 里旧单元格的空行不要照抄**。
2. **盘上"连续标记"无法无损表达**：若某条盘上出现 `{br}{br}` / `{p}{p}`，
   「1 换行 = `{br}` / 空行 = `{p}`」无法唯一还原它。现役盘实测 0 处；真遇到时 dump 会
   **拒绝写 CSV**并指名道姓（需要工程侧给这种条目一个无损写法）。这也是"严格互逆"的边界。
3. **`{WRAP}` 标记只覆盖"已标定折行宽度"的资源**（现役盘 = `SFXML` 58 条，1548 个标记）。
   `LANG` 的折行宽度仍未标定（`wrap_w=0`），所以语言表长段**看不到建议断点** —— 与 round34 相同。
4. **下游文本快照会带 `{WRAP}` 字样**：`tools/iso_build/make_build.py` 产出的
   `<版本>_text.txt` 取的是 CSV"渲染视图"，而视图现在含建议断点标记 ⇒
   跨版本对比长段时会看到 `{WRAP}`。这是**视图**差异，不代表盘上字节变了
   （字节级证据请看注入器的「全盘差异窗口」断言）。`tools/iso_build/**` 本轮不在改动范围内，
   故只记录、未处理。
5. **`{WRAP}` 与 `{{BTN:XXXX}}` 之外的裸花括号**：现役盘正文里**没有任何**裸花括号
   （486 个 `{` 全部来自 `{br}`/`{p}`/`{{BTN:...}}`），所以标记识别的误报面为 0。
   但这也意味着：**CSV 里手写 `{...}` 会被当成工具标记**（写错 ⇒ 拒绝注入）。
   想在游戏文本里显示真正的花括号需要另行设计（当前盘没有这种需求）。
6. **建议断点是"当前文本"的**：它随文本变化重算（这是预期行为）。若用户想固定断行，
   必须显式敲回车（§3.4）。**没有**"一键把建议断点全部固化"的开关 —— 需要的话可以后加。
7. **未做实机验证**：本轮只到"字节级 + 模型级 + 工具链行为"验证，没有跑 PCSX2。
   `work/builds/GR_ZH97_br/` 里的产物盘可直接上模拟器抽帧（`B_after.iso` 改了 `T0043` 一个字，
   `C_semantics.iso` 在两条语言表文本里加了换行/空行，`D_wrap.iso` 在 `T0048/T0049` 上演示了
   建议断点的丢弃与固化）。
8. **折行模型"看词"时折叠连续空格**（它按单个空格切词）：建议断点的**位置**按折叠后的宽度算，
   而 CSV 保留原文的每一个空格（逐字节保真，往返自检保证）。实测只有 1 条受影响
   （`LANG:G058.I760` = `R1` + 21 个空格 + `L1`），且只在 `--wrapw LANG=NNN` 强制开启语言表
   建议断点时才会碰到 —— 默认 dump（`LANG` 的 `wrap_w=0`）不受影响。
   这是**折行模型自身**的既有口径（round29 起、已被实机标定），本轮未改；
   发现过程见下：放宽前的区间自检把这一条误报成"无法逐字节还原"，
   实际写盘字节是**正确**的（往返自检第 2 步通过），已把比较口径改为 `norm_ws()` 折叠空白。

## 8. 给用户的一句话

> **以后长段里那些 `{WRAP}` 是"引擎会在这里折行"的提示 —— 你留着、删掉、或者改多少个字，
> 都不会动到盘上的换行；想让某处永久断行，就把那个 `{WRAP}` 删掉、在那里敲一个回车。
> 换行照旧直接敲回车，空行照旧敲两次回车；同一条改多少遍都不会越改越坏。**
> （手上如果是旧 CSV，先按 §3.6 重新 dump 一份再改。）
