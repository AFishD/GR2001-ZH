## 一、✅ 人名「·」分界点 —— 完成，零回归

### 成果
角色档案（`.ATR`）的 `<ActorName>` 全部换成「**理想标准译名 + 名·姓 分界点**」：

```
阿斯特拉加林斯基  → 阿斯特拉·加林斯基
卡里姆阿姆斯通    → 卡里姆·阿姆斯特朗
德门德勒格特      → 德蒙德·勒格特
巴兹格登          → 巴兹·戈登
```

- **252 条**名字含 `·`，与方案 **0 不符**
- 间隔号 = **U+00B7**（对偶码 `0xABC3`，已在码表中）

### 实机验证（`GR_ZH256`）
```
drawlog.txt  基线 32,828,647  ZH256 32,828,647   ✓ **完全相同**
strlog.txt      738,990        738,990          ✓ **完全相同**
截图 87 张, 相同 82, 差异 1~2 像素（抗锯齿级）
```

### 方案来源（413 行，逐行可复现）
`tools/font_pipeline/data/name_dot_plan.csv`
表头 `文件/键,理想译名,加点后,段数,备注`，**413/413 通过** `加点后.replace('·','') == 理想译名`。

切分不是猜音节，而是用工程内既有权威表做**联合约束求解**：
`work/_dis/_std_tokens.py` 的 STD（229 词素）+ `work/_squad/name_tokens_zh.json`（409 词素）
⇒ 同一词素的汉字块跨行必须一致且拼接恰等于该行译名
⇒ **377 行机器唯一确定**，36 行歧义逐行人工判定
⇒ 另推出 85 个表外词素（Todd=托德、Getz=盖茨、Cao=曹 …）

### ★ 关键工程发现：**原地增长，不搬移**
```
.ATR 条目在 GR.IMG 内紧密排列，每条后有 11~15 B 全零间隙
加一个「·」只增 2 字节（两字节对偶码）
⇒ 只要「新长度 ≤ 原长度 + 后随余量」就原地写回，只更新 stored/real

实测: 253 条中 240 条原地、13 条搬移，**净增长仅 177 B**
对比早期"整体搬到空闲间隙"需 133 KB ⇒ 省 750 倍空间
```
实现：`tools/font_pipeline/apply_name_dots.py`

## 二、🔴 关卡名 12px —— 未达成，含 3 个**否定性**发现

用户目标：只让关卡名（战役 `GR-M01`）用 12px，不污染其它文字。

### 发现 1：`GR-M01` 的真实来源是 `.MIS` 文件，不是文本表
```
46 个 .MIS 里: <MapName>M01 Caves</MapName>
显示规则 = "GR-" + <MapName> 的第一个 token
  'M01 Caves'      → **GR-M01**   ✓
  'D01 Beach'      → GR-D01
  'TAC01 Shooting' → GR-TAC01
```
`"GR-"` 是 ELF 里的静态串（VA `0x57ECA0`，紧邻 `LOCATION`/`MISSION`/`MAP_SHOTS`）。
**汉化从未碰过 `.MIS`** ⇒ 战役关卡名至今仍是英文 `GR-M01`。

### 发现 2：🔴 **MENU.IMG 的内部偏移不可移动**
```
改 .MIS 需要重压子流 0（我的压缩器比原版差 2.4%，+111~166 B/条）
⇒ 把尾部数据平移以腾空间
⇒ 平移后条目表**完全自洽**（0 个不一致、0 重叠、0 越界）
⇒ 但游戏**卡死在记忆卡界面**（drawlog 0 行）

证据: 读取序列前 39986 次**完全相同**，然后停止
      ⇒ 读了同样的 LBA 却拿到不同数据
      ⇒ **ELF 里有硬编码的 MENU.IMG 内部偏移**
```
这解释了项目铁律「`EN_STRINGS.RES` 的 off/stored/real 三字段绝对不动」的真正原因。

**⇒ 结论：`.MIS` 换码位最多只能原地增长 ~1500 B（`EN_STRINGS.RES` 之前的唯一空隙），
   仅够 ~13 个 `.MIS`，不足 46 个。**

### 发现 3：🔴 **改 FT 记录的 UV 会渲染错乱，但盘上数据完全正确**
```
记录结构 (f0, f1, u0, v0, u1, v1)
  ASCII:  f1 = 8,  区域 8×16
  汉字:   f1 = 16, 区域 16×16
  ⇒ 高度恒 16；f1 与字宽相关
```

实测尝试（**全部失败**）:
| 尝试 | 结果 |
|---|---|
| 只改 UV 宽 8→12（f1 不变）| 字符**重叠** |
| `f1=12` + 区域 12×16 | 字形**不显示** |
| 6 变体一次实验（T/E/Q/S/U/N 各一种 f1/区域组合）| 全部渲染错乱 |
| 字形放进**已验证可寻址的 ASCII 带**（v=452..468）| 仍渲染出**其它**字形 |

**★ 最关键的证据（排除了一切"我写错位置"的可能）：**
```
ZH257 的纹理在 v=452..468, u=448..520 处，用 read_atlas 解码后
可以清楚看到 6 个 12px 字形 T E Q S U N，互不重叠、形状正确:

   .......#####.......#####........###.........###........#...#.......#...#....
   .........#.........#...........#...#.......#...#.......#...#.......##..#....
   .........#.........####........#...#........##.........#...#.......#.#.#....
   .........#.........#...........#...#..........#........#...#.......#..##....
   .........#.........####........#...#........#...#.......#...#.......#...#....

FT 记录也正确: 'T' idx=52 → (0, 12, 448, 452, 460, 468)
```
**⇒ 纹理正确、记录正确、引擎确实读这两处（cdvd 日志命中 130 次），
   但渲染出的字形既不是我的、也不是原位置的。**

**⇒ 结论：引擎对 ASCII 码位的字形源坐标有一套**尚未查明**的解析规则
   （可能与纹理 swizzle 的页/块结构有关，而非简单的逻辑 (u,v) 直映）。**

已排除的干扰因素（都逐一验证过）：
- 纹理写入位置正确（`MENU+0x58431+0x44C` 与 `pack_atlas(A)` **262,144/262,144 字节完全相同**）
- 字形写入正确（解码后可读出正确形状，且互不重叠）
- FT 写回正确（读回记录与写入值一致）
- 引擎确实读该纹理区（cdvd 日志 **130 次**命中 LBA 776462..776591）与 `FONT.RES`（3 次）
- 噪声基线为零（同盘重跑 drawlog/截图 100% 相同）

**⇒ 这是一个**精确定位、可复现**的未解问题，已超出本次会话的排查预算。**

### 已排除的方案
| 方案 | 结果 |
|---|---|
| 扩 `nrec`（改 `fld[4]`）| ❌ 渲染错乱（`top` 变垃圾值）|
| 扩 `nrec`（改 `fld[5]`）| ❌ 渲染错乱 |
| 全局 12px（所有汉字）| ❌ 字距过大、可读性下降 |
| 改 `.MIS` 的 `<MapName>` | ❌ 需平移 MENU.IMG ⇒ 卡死 |
| 改 ASCII 的 FT 记录 UV | ❌ 渲染错乱 |
