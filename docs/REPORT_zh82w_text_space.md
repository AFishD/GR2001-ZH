## 1. 报障定位（字节级）

```
XML 0x3E75  4d 31 38 20 d7 e1 a1 fe a1 ef a2 b3 d3 fc ab b0   M18 定向反步兵
XML 0x3E85  a7 d2 c8 af a1 bd 20 a6 a9 ac d6 20 a5 c4 bf a2   地雷由曲面的方 ⎵ 形硬 ⎵ 质弹
                              ^^ 0x3E8B(+22)     ^^ 0x3E90(+27)
```

| | 字节 | 渲染 |
|---|---|---|
| 现役（base） | `… A1 BD 20 A6 A9 AC D6 20 A5 C4 …` | `…由曲面的方 ⎵ 形硬 ⎵ 质弹体…` ← 第 2 个 `20`（+27）落在行内 ⇒ **可见** |
| 修复后 | `… A1 BD 20 A6 A9 AC D6 A5 C4 …` | `…由曲面的方 ⎵ 形硬质弹体…` ✓ |

前后完整 dump（含 ASCII 栏与逐字节差异）：`work/archive/cmp/r27_sf_text/r27_text10_bytes.txt`。

> **解码口径提醒（重要）**：本盘 ELF 四处 `sltiu reg, lead, 0xAE`（`0x416EE8 / 0x417160 / 0x41751C / 0x5656A4`，`work/_dis/r27_elf_lead.py` 实测）
> ⇒ DBCS lead 只能是 `0xA1..0xAD`，**`0xAF..0xFE` 是单字节码（`的` = `0xAF`）**。
> 因此 `AF A1 BD` 在游戏里画的是 **`的` `方`**；而"贪心 pair-first"解码器会把 `AF A1` 先配成 `弗`
> 再剩 `BD`=`开` —— 得到"由曲面弗开"这种假象（本工程 `patch_zh84.py` 的 `dec()` 就是这种口径）。
> 本报告所有"玩家看到的文本"均用**引擎口径**解码（`work/_dis/r27_faithful.py` / `r27_bytes.py` 内 `dec_engine()`）。

## 2. 来源考证：这是 ZH84 轮插入的"行边界空格"，不是残留换行符

仓库里留着当年三代 `<text>` 台账，逐条 diff 即可定性：

| 世代 | 该处字节 | 台账原文（M18 条） |
|---|---|---|
| 补丁前（ZH82/83） | **无空格** | `…地雷由曲面的方形硬质弹体制成，内装约 340 克…`（`work/_dis/_xml82.txt` #10） |
| ZH84 一轮插空格 | **`AC D6 20 A5 C4`** | `…由曲面的方形硬 质弹体制成，内装约 340 克 C3 炸药。…`（`work/_dis/_xml84.txt` #10） |
| 现役（v4 二轮重排） | 同上（保留） | `M18 定向反步兵地雷由曲面的方 ⎵ 形硬 ⎵ 质弹体制成，…` |

**二轮重排的字节级铁证**：`enc(reflow_v4(_xml84 台账文本))` 与现役 ISO 的 `<text>` 原始字节
**58/58 条完全一致**（`work/_dis/r27_lineage_byte.py`，台账里的 `\'` 转义还原后）——
即现役文本 = **v4 算法作用在"已插过空格的一轮文本"上**。

**那个空格是怎么被插进去的（一轮算法）**：一轮是"按行宽切行、在行间插 0x20"的同族算法
（`work/_dis/reflow_fix.py` 就是它的规则说明，`git show 8358a0a4:tools/iso_build/patch_zh84.py` 是同期版本）。
反解首行上限得 **243 = wrapW(270) − cost("M18")(27)** ⇒ 首行恰好装 **14 个汉字**
`定向反步兵地雷由曲面的方形硬` ⇒ **断点落在 `硬`|`质` 之间**，于是插了这个 0x20
（`work/_dis/r27_v1fit.py` mode c：复现出与 `_xml84` 完全相同的 `…方形硬 ⎵ 质弹体…`；
pre-84 文本本身没有任何空格，一轮算法只会**增**不会删）。

**为什么二轮没把它去掉**：v4 的规则是"**原文空格只增不删**"（`patch_zh84.py` 文档头第 4 条）。
二轮用 token 预算重算首行：`budget = 270 − 26 − 2×4 − 1 = 235` ⇒ 首行只装 **12 个汉字**
`定向反步兵地雷由曲面的方`（`cut = max(1, k−1)`），正文从 `形硬 ⎵ 质弹体…` 开始重排。
空格被保留，但**行边界移动了**：第 2 行现在是 `形硬 ⎵ 质弹体制成，…` ⇒ **原本行尾的空格变成行内空格**。

**"残留换行符"假设的排除**：全 69 条 `<text>` 内容里 `\r`/`\n`/`\t` 出现 **0 次**
（`work/_dis/r27_scan.py` 输出：`<text> 内 \r/\n/\t : 0 条`）；坏位置字节就是 `0x20`，不是 `0x0D/0x0A`。
XML 元素之间的确到处是 `\r\n` 缩进，但它们都在 `<text>…</text>` **之外**，引擎不会把它们算进正文。

## 3. 为什么"多余空格"会被画出来（引擎口径）

`RSTextComponent::DoWordWrap @0x21CC10`（`docs/REPORT_wrap_and_title.md` §1 已逐字核对反汇编）：

```
按空白切 token;  行宽预算 wrapW = comp[0x40] − comp[0xB4] = 270
每个 token: budget −= StringWidth(tok) (+fp 若非行首); budget −= tracking; budget < 0 ⇒ 断行(断点记在 token 起点)
每个字面空格: budget −= fp            # fp = spaceW(3) + tracking(1) = 4
```

* 断行只在 **token 起点**登记 ⇒ 落在断点前的那个空格属于**上一行行尾**，没有墨迹；
* 两个 token 落在**同一行**时，它们之间的空格会被**当作字面空格画出来**（3+1=4 单位宽的空隙）；
* 所以"空格多余不多余"取决于**它是否恰好落在断行处** —— 这正是本 bug 的成因：一代行边界，二代行内。

3. **补偿位置选"条目末尾"**：末行行尾的空格永远不可能变成行内空格（其后没有 token），
   且末行 `范围毁伤区。`(101) + 4 « 270，不影响任何折行。
4. 断言清单：目标资源/条目/字节上下文、`<text>` 69 条、结构元素计数、145 个 `name` 属性、
   其它 68 条 `<text>` 逐字节不变、子流回环、槽前/槽后全盘逐字节一致、折行模型无超宽 token。
5. **可重放**：同一命令再跑一遍（输出到 `GR_ZH82_W_replay.iso`）得到**完全相同的 sha256 `9820926d…`**（已核对后删除重放盘）。
