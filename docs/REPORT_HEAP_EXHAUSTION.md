## 0. 一句话结论（三层，别混）

1. **不是「堆耗尽」，也不是「碎片化」——是空闲链被写坏（free-list corruption）。**
   崩前（存档恢复后第 43 帧 = 用户存档本身）堆里**还有 5,908,256 B 空闲（22.33%）**，其中**一整块连续 4,756,224 B（4.54 MB）**就在堆顶；而失败的那次请求只要 **65,568 B（0x10020）**，**余量是请求的 ~90 倍**。所谓「malloc 失败」跟容量毫无关系。
2. **失败的请求正好落在被写坏的那个桶上。** 按 `0x00102050` 反汇编逐条推演：请求 `0x10011` → 对齐后 `nb=0x10020` → 桶号 `idx = 110 + (nb>>12) = 126`；而**桶 126 的头/尾指针槽（`0x0055BB98/9C`）里写着 `0xA73D37F0`**——一个超出 EE 32 MB 物理 RAM 的地址，而且这个 4 字节值**在整个 32 MB RAM 里只出现在这两个槽位**（不是从别处拷贝来的，是算出来/写进去的）。
3. **最早分叉点：日志 `207.6867 s` 的第一次 TLB Miss 是「最早可见」的异常；而用两份即时存档夹逼，损坏发生在 `193.61 s`（健康）与 `223.84 s`（已损坏）之间。** 没有泄漏指纹：30.1 s 的游戏时间里已用堆只涨了 46,224 B（+0.22%），且堆顶指针一动没动。
4. 本地复现里「malloc 返回 0」**不是 OOM 失败**：分配器走到坏桶→把读到的 0 当成下一个 chunk→用 `chunk=0` 空转一圈→把**地址 0 处的异常向量区别的字节**当成 chunk 尺寸（`0x0F2B1F00` = 254,484,224 B ≥ nb+32）→走**切分**分支、在地址 0 一带写分配器元数据、并把 `0`（chunk 指针原值）当结果返回；`0x001026B0` 的「chunk==0 ⇒ 返回 NULL」约定把它变成 NULL，解压器就把 0 当输出缓冲基址 → 写坏异常向量 → 第 45 帧 Trap（与 `docs\REPORT_CULPRIT_STORE.md` 已定案的致命一步接上）。

### 1.2 堆管理器全局与桶数组（用 hook 寄存器 + RAM 实证）

- 核心分配函数的 `a0` = **`0x0055B7A0`**：hook 原文 `hook pc=001024E8 ... a0=0055B7A0 a1=00000060 ... ra=0010270C`（`work\builds\GR_CULPRIT\runs\c03_allocres_freelist\hooklog.txt`），且 `0x001026E8 addiu $a0, $v0, -18528`（`$v0=0x00560000`）→ `0x0055B7A0`。
- 头部只有 8 字节：`+0x00` = 64 位 binmap（各状态取值 `0xF229F9FE / 0xF7EF7FFE / 0xF209C9FE / 0x72EFFFFE`，高 32 位恒 0）。
- `+0x08` = **堆顶（wilderness/top）chunk 指针**：`0x0010262C lw $v0, 16($t1)`（`t1 = a0-8 = 0x0055B798`）→ 读到的就是 `0x0055B7A8`，随后 `0x102638` 取它的 size 并按 `size-nb` 切分或**返回 0**（`0x00102650 beq $zero,$zero → 0x0010269C`，延迟槽 `pcpyld $v0,$zero,$zero`）。英文盘 d01 的三次成功分配正好从该值 `+0x10` 起按请求尺寸递增（`0x01B0FBB0 → 0x01B0FBC0 → 0x01B1FBE0 → 0x01B3FC00 → 0x01B4FC20`），与该字段语义一致。
- `+0x0C` = 常量 `0x0055B798`（= 管理器首地址 8 字节；所有被检状态一致，与账目无关）。
- **桶数组从 `0x0055B7A8` 开始，每桶 8 字节（fd,bk）**，桶 `i` 的伪 chunk 地址 = `0x0055B798 + 8*i`，其 fd 在 `0x0055B7A8+8*i`、bk 在 `0x0055B7AC+8*i`。证据同时来自代码与数据：
  - 代码：`0x00102068-0x0010207C`（小块）与 `0x00102158-0x0010216C`（大块）都算出 `v1/a3 = a0 + 8*idx - 8`，`fd` 在 `+8`、`bk` 在 `+12`；
  - 数据：空桶自指（值 = 槽地址 − 16），如 `0x55B7B0 = 0x55B7A0`、`0x55B7B8 = 0x55B7A8`、`0x55B7C0 = 0x55B7B0` …… 一直到 `0x55BBA0 = 0x55BB90`；桶 0 的槽（`0x55B7A8/AC`）被 `top`/常量别名，而 `idx=0` 对应 `nb<8`，**分配器永远不会用**（最小 `nb=32 ⇒ idx≥4`，大块路径 `idx≥56`）。

### 1.3 「失败请求 → 桶 126」逐条推演（本次取证的枢纽）

请求来自解压器 `0x00539110`：`malloc(s0+1)`，`s0 = 0x00010010`（解压后 65,552 B）⇒ 请求 `0x10011` ⇒ `nb = (0x10011+23)&~15 = 0x10020`。

0x1020E4  srl  $v1,$v0,9    ; v1 = nb>>9 = 0x80 = 128
0x1020E8  bne  $v1,$zero → 0x1020F8

### 2.3 判定：**堆耗尽 / 碎片化 / 空闲链被写坏** 三者选一

**结论：空闲链被写坏（第三项）。** 三条互相独立的证据：

1. **不是总容量不足**：失败请求 65,568 B，堆里有 5,904,352 B 空闲（90 倍），其中 top 块 4,756,224 B（72 倍）。
2. **不是碎片化**：最大空闲块 4,756,224 B 连续（它是 top chunk，`heap_end` 之前无其他 chunk）；空闲块只有 95 个、分布高度合并（第 2 大 59,200 B）；「有空闲但无 65 KB 连续块」不成立。
3. **是链被写坏**：桶 126 的 fd/bk 槽 `0x0055BB98/9C` = `0xA73D37F0`（>32 MB 物理 RAM 上界；`u223` 全 RAM 检索该 4 字节值**仅命中这两个槽**）；而 f43/f44/f45/对照 run 的这一槽位值**逐帧不变**，说明它不是「某一帧正在被改写的瞬间值」，而是**已经落定的坏值**。
   - 同一损坏的**前身**：`u193`（193.61 s）该槽 = `0x0055BB88 / 0x0055BB88`（正常空桶自指）⇒ 损坏确实是在这 30 s 内新增的。
   - 分配器随后（帧 44）在这个桶上 `ld $v1, 8($v0)`（`0x00102180`/`0x001024D0`）= 读 `0xA73D37F8` → 用户机上打 TLB Miss；本地机上读到 0 → `bk` 也读到 0 → **`chunk=0` 的连锁**（见 §0.4、§3.3）。

> **补充（本地实测的完整机制，纠正「分配器返回 0 = 内存不足」这个直觉）**：本地复现时 `hook pc=001024E8 frame=44 a1=00010020 v0=00000000`（`0x1024E8` 是**切分**分支的第一条指令，不是「放弃」分支），而 `RAM[0x08..0x0F] = 0x07EA090E0F2B1F00` ⇒ 被当成 chunk 尺寸 = `0x0F2B1F00`（254,484,224）≥ `nb+32` ⇒ **分配器把地址 0 当成一块 254 MB 的 chunk 切开、并把 chunk 指针原值 0 当结果返回**；`0x001026B0` 的 `beql $v0,$zero` 把 `chunk==0` 转成 NULL 返回给调用者。所以这**既不是容量失败，也不是「分配器老实报错」**，而是坏链导致的「幻觉分配」。

**② `c05 f43 → f44`（崩溃帧，按 L1 的那一帧）**
- 分配器管理区只有 **9 B** 变化：`0x0055B7D8/DC`（桶 6）、`0x0055B89C`（桶 30）——正是那次**成功的** `malloc(0x420)`（返回 `0x00B71EC0`，取自桶 77 附近）造成的正常摘链/切分；**桶 126（`0x55BB98/9C`）一动不动** ⇒ 坏值**先于**这一帧就存在（随存档而来），L1 只是把它撞上的触发器。
- 低端 `0x400..0xFFFF` 变化 125 B；异常向量区 0 B。

**③ `c05 f44 → f45`（致命一步的定量证据）**
- **异常向量区 `0x0000..0x03FF` 变了 839 B**，`0x400..0xFFFF` 变了 9,895 B，块 `0x00000000-0x0000FFFF` 共 10,734 B ⇒ 与「解压游标 `sink[8]=0x305D`（已写 12,445 B）」吻合：**解压输出确实从地址 0 起写了约 12.4 KB**（`REPORT_CULPRIT_STORE.md` §2.3 的 sink 表由此得到独立字节级印证）。
- 分配器管理区 25 B 变化，含 **`0x0055B7B0/B4`（桶 1）= `A0 B7 55` → `20 00 01`**（即 `0x00010020` = 那次失败请求的对齐尺寸被写进「指针」槽）、桶 4 fd/bk 互换、桶 44/77 抖动 ⇒ 失败路径把「尺寸」当「指针」用的痕迹（与 `REPORT_CULPRIT_STORE.md` §3.4「更正 3」的观察一致）。
- 最大差异块 `0x014B0000`（22,390 B）等属场景活动，与本病灶无关。

**④ `r06 f40 → f46`（同存档、不按键对照）**
- 分配器管理区只变 **6 B**（桶 4 一对指针），堆顶指针、桶 126 都不动 ⇒ 空闲时堆完全静止；再次说明坏桶不是按键造成的。



- 同一会话两点时间序列：`193.61 s → 223.84 s`（30.1 s 游戏时间），已用堆 `20,514,064 → 20,560,288` = **+46,224 B（+0.225 %）**；**堆顶指针一动没动**（都是 `0x01B0ED20`，top 尺寸都是 4,756,224）⇒ 这 30 s 里**没有净增长**，只有正常的分配/释放抖动（chunk 数 42,680 → 42,781，桶数 30 → 21 说明发生了合并）。
- 跨构建/跨场景的点（`ENG_s10` 70.5 %、`7A361FB5_s02` 70.6 % 等）不能拼成曲线：不同构建、不同进度、不同场景。

- ⇒ **判定：无泄漏指纹**。严格说法：「在 30.1 s 的同一会话窗口内，已用堆非单调增长且堆顶未移动；手上没有更多同会话存档，故不能对更长时间尺度做泄漏判定。」

## 4. C. 结论与建议

### 4.1 最初病灶最可能是什么（四选一）

| 候选 | 判定 | 依据 |
|---|---|---|
| 泄漏 | **否** | 30.1 s 内 +46 KB、堆顶不动（§3.3）；崩前仍有 22.3 % 空闲 |
| 一次性大分配 | **否** | 请求仅 65,568 B；崩前同类/更大请求（0x420 等）都成功；本地 f44 前一次 0x420 分配正常返回 `0x00B71EC0` |
| **空闲链被写坏** | **是（主因）** | 桶 126 槽位 = `0xA73D37F0`（越界、RAM 内唯一命中）；分配器读它→`chunk=0` 连锁；用户机 free/insert 路径 TLB Miss 风暴 |
| 数据量导致的容量不足 | **否** | 90 倍余量；英文盘同类空闲块存在 |

**更精确的病灶表述**：**有代码把「不是合法 chunk 的指针」交给了分配器（或直接写进了桶数组），使桶 126 里出现越界指针**。用户日志把它拍在了 free/合并/摘链/插链这四段代码上（`0x101D10`/`0x101DAC`/`0x101DD8`/`0x101E34`/`0x101E6C`/`0x102008` = `ld size` / `ld prev_foot` / unlink 两条 `sw` / 读 fd,bk / 写 head / 插入四条 `sw`），地址都是 `>0x2000000` 的垃圾值（`0x14E228F7`、`0x52ABF48`、`0x3C36BF50`）或直接 `0`。

**关于「是不是汉化造成的」——如实说：未达成。** 桶 126 的坏值在**多个汉化构建**的存档里都出现（含 `0xA73D37F0` 在另一次会话复现），但**英文原盘的 `3E571E91` 存档同样有坏的桶 126**（`0x00ACEA20`，不是 chunk 起点）⇒ 这个签名**不是汉化独有**，更像引擎/数据侧的既有缺陷（或至少不能靠现有证据归因汉化）。要归因必须做「同场景两版对照」（§2.2 未达成）。

### 4.2 两条修复路线评估

**① 鲁棒性修复（解压器 NULL 检查，`1a003be5` 在做）**

- 能治：
  - 本地复现那条路：`0x00539110` 拿到 NULL 后不再把它当输出基址 ⇒ **不再从地址 0 开始写** ⇒ 异常向量区（`0x0..0x300`）不被砸 ⇒ 第 45 帧不会执行垃圾 ⇒ **Trap 消失**。调用者 `0x0051BE10` 本来就有失败分支（`free(s1[0x14])` + 置失败标志 + 跳过后续），返回 0 即可复用（`docs\REPORT_CULPRIT_STORE.md` §6 的 cave 方案）。
  - 顺带把「幻觉分配」（§2.3 补充：把地址 0 当 254 MB chunk 切分）造成的低端内存写一并挡在解压器之外。
- **不能治**：
  - **坏桶本身**：桶 126 依旧是 `0xA73D37F0`；下一次任何 64 KB 量级的分配（不止 L1；换武器/换场景/载具/音效等都可能有）仍会走到这条坏链上。
  - **用户机上「分配器自己空转」那种表现**：`pc=0x1024d0/0x102584` 无限循环发生**在 malloc 内部**，NULL 检查根本等不到返回值 ⇒ 那条路照旧卡死（用户日志 224.79 s 就是这个形态）。要挡它得改分配器（不建议，风险大）。
  - **其它没有 NULL 检查的 716 处 `jal 0x00102D40` 调用点**：坏链还可能让别的分配返回 0 或返回假指针（本地 f45 帧出现的桶 1 = `0x00010020` 就是坏链把「尺寸」写进「指针」槽的痕迹，说明坏链仍在扩散）。
  - **安全网 vs 病灶**：它把「堆损坏」降级为「某次资源加载失败」，游戏可能表现为贴图/武器缺失而不是崩溃——可作为**发布安全网**，但不是根因修复。

**② 若确为泄漏/容量不足，真正的修法是什么**——按本次账目，**前提不成立**（不是泄漏、不是容量），所以「真正的修法」应改为**修坏链**，需要这些证据才能定案：

1. **抓到写坏桶 126 的那条 store 本体**（决定性证据）。现成手段：`-grwatch` 监视 `0x0055BB98`（槽地址，十进制 `5618584`）**4 字节**；本次取证显示该槽**只在损坏那一刻被写一次**（f40–f46 七帧值不变），因此 64 命中/区的上限完全够用（上一轮在 `0x55B7B0` 上耗尽预算是因为那是一对高频改写的活动桶指针，桶 126 不同）。拿到 `writer_block` + 寄存器即可反推是 `free(坏指针)` 还是「野写把数据盖到桶数组上」。
2. **能从 193.61 s 那份健康存档回放到 207 s 的输入脚本**（本机无头做不到：需要一长串菜单/读盘/移动/开火输入；用户手动做最省事，见 §4.3）。
3. **同场景两版对照**（英文盘 + 汉化盘各一份「任务中、按 L1 能触发武器资源加载」的存档），才能回答「汉化是否抬高了这条路径的触发概率」。
4. 若第 1 步抓到的是「野写」（像 `7A36E0B1` 那样 13 个桶被 `0x0098xxxx` 数据样值覆盖），则病灶在别处（某个上限被突破后溢出到 `0x55B7A8` 一带），应改为对 `0x55B7A8..0x55BBA8` 整段做写监视并按帧定位。

### 4.3 给用户的复测清单（照做即可，官方模拟器手动复测）
