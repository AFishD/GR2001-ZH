## 0. 一句话结论

**「贴图加高」这条路的瓶颈不是 r73 报告担心的 `+0x30` 记账（那条已被本报告读透，是误报），
而是 `COMMON.PAK` 长大的物理空间**：现役盘 `COMMON.PAK` **身后只有 13 字节余量**，
整个 `MENU.IMG` **只剩 61,236 字节零尾料**，ISO 尾部另有 28,672 字节 ⇒
**任何"不动别人"的原地长大上限 ≈ 89,908 字节**，而 `h=1024` 需要 **+262,912 字节**。

| | 结论 |
|---|---|
| **L1（h=1024）** | ❌ **按 r73 报告的形态不可行**（不是引擎不行，是**装不下**）。要装下必须平移 `MENU.IMG` 尾部 57.5 MB —— 这是历史上**唯一一次干净实验就卡死**的操作。 |
| **L1-mini（h=640）** | ⚠ **可行但同样要平移尾部**（+66,016 B，靠 61 KB 零尾料 + 3 个 ISO 尾扇区吸收，ISO 总大小不变）。**这才是值得做探针的形态。** |
| **L0（只抬 gate，用现有空闲格）** | ✅ **零风险，可立即做，净 +105~108 字**（覆盖 364 缺字的 **29%**）。 |
| **改格距（CW/CH 缩）** | ⚠ 数字上够用（`CW=14` → 1898 格、`CH=15`+`NCOL=64` → 1920 格，都 ≥ 1876），但**要重排全部 1504 个现有字形 + 改字宽/字高常量** ⇒ 文本度量、折行、居中全线回归。**这是 L1 失败后的兜底，不是首选。** |
| **`+0x30` 记账** | ✅ **不是风险**。r73 报告的 `B'` 读错了（`0x40000/W` 而非 `W·⌊0x10000/W⌋·4`）；按磁盘字节重算，**DMA 交付字节数恒等于 `px_size`**，永不越界。现役盘的 `+0x30` 值是 `0x3C3D0`（比像素字节数少 15,424 B）却工作正常 —— 这本身就证明"差多少"无意义。 |
| **推荐路线** | **先 L0（+108）→ 再做「MENU.IMG 纯平移」单变量探针 → 通过则 L2 + L1-mini(h=640)（+372）→ 不通过才考虑改格距。** |

**关键算术**：`512×512×8bpp = 1024×512×4bpp = 0x40000 B` —— 4bpp 让**同字节数装 2 倍 texel**，
所以「换 1024 宽」是**字节中性**动作。这正是它被选中的第一理由（`FEASIBILITY_ANALYSIS_R4.md:95-99`）。

### 2.2 PAK 长大 / 下游条目移位：**成没成功？——从来没做过，也不需要做**

本报告实测（`work/tools/cap_menu_slack.py`，现役盘 vs 原版盘逐条 `off/stored/real` 对比）：

```
COMMON.PAK   off=0x00057400  stored=400659  real=400659   ← 两张盘逐字段相同

MENU.IMG 686 条目：与英文原盘逐字段不同的只有 1 条 = EN_STRINGS.TXT（MOVED 0x24D600 → 0x378A000）
```

⇒ **现役盘的 `COMMON.PAK` 长度 = 原版长度，后续条目一条都没移位。**
「PAK 长大 + 条目移位」这条分支在本工程里 **从未真正执行过**：

* 唯一相关的实验是 **F5 的 ZX2B**（pda 缩 + PAK **缩小** + 表项 stored/real 同步）→ 挂死
  （但被标注为 `CDVD_STALL`，且**从未重跑**）；
* plan 里的「乙方案（512×608 8bpp，后续条目后移 49,152 B）」**没有出过盘**
  （`FEASIBILITY_ANALYSIS_R4.md:134-153`）；
* 现役盘走的是**不需要移位**的 4bpp 路线。

⇒ **"PAK 长大成没成功" 的诚实答案是：没有证据，因为没有实验。** 见 §4.3。

## 3. 【交付物③】改格距路线的数字表

### 3.1 先定标：现役格位的**真实相位**（本报告实测）

`work/tools/cap_grid.py` 从现役盘 `GR_ZH113b` 解出引擎口径图集，对 row 0/1/2/3/11/12/15/20/24/27
逐列统计墨：

```
row 0  y=  2  filled=62 [0..61]   每格墨 bbox（格内相对坐标）: [0,14]×50 格 / [1,14]×4 …
row 20 y=370  filled=62 [0..61]   每格墨 bbox: [0,14]×51 …
row 24 y=434  filled=16 [0..15]   ← slot 1488..1503（行 24 只用了 16 格）
row 27 y=482  filled=28 [0..27]   ← 旧世代残墨，不被任何 slot 采样
```

⇒ **每个 slot 的字形就落在它名义上的 16×16 格 `(16·col, yrow(row))` 的第 0~14 列**，
**采样与 cave 输出是格对齐的**（没有任何额外相位）。
（历史上 `PROGRESS.md:406-419` 说的「绘制原点 X0: 20→4」是**写盘侧**的记账，
不是"引擎多采 4 texel"；本测量是盘上像素的直接结果。）

由此得到两条硬约束：

* **列上限** = `⌊W / CW⌋`（现役 `⌊1024/16⌋ = 64`，用的是 **62**，留 2 列余量）
* **行上限** = 最大的 `r` 使 `yrow(r) + CH ≤ H`，其中 `yrow(r) = Y0 + CH·(r + SKIP_ROWS·[r ≥ SKIP_ROW])`
* **图标窗**（`DrawString` 硬编码 UV `(1,198)-(21,218)` / `(25,198)-(45,218)`）**必须落在跳行洞里**：
  `Y0 + CH·SKIP_ROW ≤ 198` 且 `Y0 + CH·(SKIP_ROW+SKIP_ROWS) ≥ 222`
* **EN/ASCII 带** `[452,468)`（盘上 FT 记录实测 v0/v1）**必须避开网格格**：它恒定吃掉 2 行

| **12** | **12** | 16+3 | 85 | 39 | 2 | 37 | **3145** | 1.333 / 1.333 | ✅（也够 L4 的 3056） |

**读表要点**

1. **只缩 CW（CH=16 不动）**：列数 62 → `⌊1024/CW⌋`。
   `CW=14` → 73 列 → **1898 格**（≥1876，只多 22）；`CW=15` → 68 列 → 1768 格（**不够**）。
   ⇒ **CW 只能到 14，且余量极薄**。
   （`CW=15` 若连跳行一起改成 13+2 可到 1836 格，**仍不够 1876**。）
2. **只缩 CH（CW=16 不动）**：行数 28 → 32(15) / 34(14) / 37(13) / 39(12)；
   但 **EN 带仍恒吃 2 行**，且 SKIP 必须同步改（否则图标窗落空）。
   ⇒ `CH=15` + 列数 64 → 1920 格 ✅。**注意：CH=15 时 SKIP 必须从 12+3 改成 13+2**，
   而且**列数还得从 62 抬到 64** —— 也就是"改格距"从来不是只改一个数。
3. **两者同时缩**：`13/13` → 2730 格，`12/12` → 3145 格。
   这正是历史上**被验证过**的那条（ZH16：`37/13/13` 在 512×512 内做 1221 格 / 1212 字）。
4. **16px 字形能不能塞进更小的格？**
   * 盘上实测：现役字形墨迹**填满 16×16 格的第 0~14 列**（§3.1）⇒ 格一缩，**墨就装不下**。
   * 引擎的采样是一个 **CW×CH 的 UV 带拉伸填满 quad**（quad 宽 = CJK 步进宽，quad 高 = 各 cave 常量）。
     所以缩格有两条子路：
     - **(a) 把字形重渲成更小的点阵**（历史上 CH13 配的就是 13px 字形：ZH16 = 方正/Zpix 13px）。
       代价 = 换字形源、可读性下降（round65 判"不推荐"的理由）。
     - **(b) 保持 16px 字形、让引擎拉伸**：band 13 塞进 quad 16 ⇒ **1.23× 纵向放大 + 横向挤压**。
       这正是 ZH13/ZH35 时代花了 **3 轮**（V18 四边形解耦 → V18B → V19 行距 CLAMP）才消掉的
       "拉伸"缺陷（`docs/PROGRESS.md:371-376,421-439`）。**改 CH 会把它请回来。**
   * ⇒ **判断：可行，但代价不是"改几个常量"，而是"重新引入一个已经修好的缺陷类别"。**
5. **改格距的真正成本清单**（`docs/FONT_CURRENT_STATE.md:108-126`、`docs/han_v2/FONT_CAPACITY.md:364-380`）：
   ① cave 常量 `NCOL/CW/CH/SKIP_ROW/SKIP_ROWS/Y0`（`0x4170AC/0x4170C4/0x4170EC/0x4170D8/0x4170E8/0x4170F8`）；
   ② **CJK 步进宽常量** `0x416FC0`（现役硬编码 16 —— 改 CW 不改它就横拉伸）；
   ③ quad 高常量（V18B 族 cave，现役 16 —— 改 CH 不改它就纵拉伸）；
   ④ **整张图集重渲重排**（全部 1504 个现有字形换格位）；
   ⑤ charset `grid` 块与写盘工具同源参数化（`FONT_CAPACITY.md:372-376` "同一张配方单"）；
   ⑥ 若改 CW 则**所有文本变窄 12.5%**（advance = CW）⇒ 折行/居中/盒子全套回归。

### 3.4 「改格距」与「放大贴图」**能否叠加**、各自先决条件

| | 先决条件 | 与另一条的关系 |
|---|---|---|
| **放大贴图（L1）** | ① `COMMON.PAK` 必须能长大（**当前唯一硬阻塞**，见 §4）；② GIF 容器必须重写成 N 个自闭合包（**已有现成模板** = 现役 8 段）；③ 显存要能给出 512 KB 连续块（h>512 时 TH 9→10，**任何 h>512 都是 512 KB**）；④ `FONT.RES` face 表**不用动**（CJK 不走记录表） | **正交，可叠加**。叠加时格位公式不变 ⇒ 现有字形**零搬迁** |

### 4.1 ★ `+0x30` 记账**已读透**：不是风险（r73 报告的公式读错了）

**磁盘字节实证**（`work/tools/cap_loader30.py`，现役盘 ELF @LBA295，符号来自 `.symtab`）：

```
0051B958  lhu  $v1,0x10($s1)    ; v1 = W (UITexture+0x10)
0051B95C  lui  $v0,0x1          ; 0x10000
0051B960  lw   $a0,0x6C($sp)    ; a0 = px_size
0051B964  divu $v0,$v1          ; lo = 0x10000 / W
0051B970  mflo $v0
0051B974  mult $v1,$v0          ; ← 死码 (结果从不被 mflo 读)
0051B978  sll  $v0,$v0,2        ; ★ B' = (0x10000/W) << 2  = 0x40000 / W
0051B97C  addiu $v1,$v0,0x10    ; 单元 = B' + 16
0051B980..0051B994  n = ceil(px_size / (B'+16))
0051B998  sll  $v0,$v0,4        ; n*16
0051B99C  subu $v0,$a0,$v0      ; ★ +0x30 = px_size − 16·ceil(px_size/(B'+16))
0051B9A4  sw   $v0,0x30($s1)
```

`LoadPS2Img`（`0x51DA80-0x51DACC`）是**逐指令同款**的 13 条。

* **r73 报告写的 `iVar4 = w·(0x10000/w)·4 + 0x10` 是错的** —— `sll` 作用在 **`divu` 的商**上，
  不在乘积上；`0x51B974` 的 `mult` 是死码。正确值是 **`B' = 0x40000/W`**
  （W=512 → B'=512；W=1024 → B'=**256**）。
  **独立交叉验证**：v17 报告实测「已验证可用的 512 案例 `npackets = 497`」
  （`REPORT_16px_fix_v17.md:94`），本报告公式对 W=512、`px_size=0x40010` 算出 **npackets = 497** ✓。

**谁写、谁读**（`lw/sw $rt,0x30($rs)` 全 ELF 扫描，限 UITexture/UIPacket 模块 `0x517000-0x520000`）：

| 角色 | 站点 | 语义 |
|---|---|---|
| **写** | `LoadingTexturePak+0x344` (`0x51B9A4`) / `LoadPS2Img+0x1BC` (`0x51DACC`) | 上式的 `+0x30`（**现役字体走 `LoadPS2Img`**，mode=0） |
| 写 | `__ct__9UITexture+0x54` / `ReSetBuf+0x24` / `ReleaseObsolete+0x88` | `= 0` |
| 写 | `LoadRSBFile` ×6（+0x780/0x91C/0xAAC/0xC50/0xDEC/0xF60） | wire-rsb 各分支，**每条后面紧跟一条读**，自产自销 |
| 写 | `CreateJPEGBuffer+0x70` | JPEG 路径 |
| **读** | **`SetTexturePkt+0xADC`（`0x5181BC`）—— 唯一一个真正消费它的地方** | `lw $a3,0x30($s0)` = DMA 剩余字节数 |
| 读 | `RefreshActive+0x108/+0x144/+0x258`、`CreateJPEGBuffer` | 与 `+0x30` 同函数的写点配对 |

**`SetTexturePkt` 的分块循环**（`0x5181B8-0x5182D4`，本报告逐条解码）：

```
B'      = (0x10000/W) << 2                     ; 0x5181D8  ← 与加载器同一个 B'
rem     = this+0x30                            ; 0x5181BC
npackets= ceil(rem / B')                       ; 0x5181E4-0x5181F8
每包 i:  t1 = min(B', rem)                     ; 0x51821C-0x518230
        DMA REF { QWC = t1/16 + 1 }            ; 0x518240
        ADDR = pixel_buf + i·(B'+16)           ; 0x518230-0x518244
```

**算术封闭性（本报告证明）**：设 `P = px_size`、`u = B'+16`、`c = ceil(P/u)`、`+0x30 = P − 16c`。
恒有 `npackets = c`（因为 `c·u − P ∈ [0,u)` ⇒ `ceil((P−16c)/B') = c`），
于是 **总交付字节 = `Σt1 + 16·npackets = (P − 16c) + 16c = P`**。
**且最后一包的 `ADDR + QWC·16 = P` 恰好等于容器末尾 ⇒ 永不越界读。**

**唯一真实边界**：若 `c·u − P ∈ (B', B'+16)`（272 个值里的 15 个，约 **5.5%**），
则 `npackets = c−1`，**少交付 16 字节**（容器最后一包的 tag 被截断）。
—— 这就是 F6 那堵墙的**同一族**故障（tag 不闭合）。候选的 `px_size` 都不落在这个集合里（下表）。

**对 r73 §9-2 的裁定**：

| r73 的说法 | 本报告 |
|---|---|
| `h=1024, px_size=0x80310` 时 `+0x30 = 0x802E0`，真实像素 `0x80000`，**差 736 B**，是"L1 唯一可能致命的点" | ❌ **误报**。`+0x30` **按定义就不是像素字节数**，是"DMA 要传的字节数" = `px_size − 16 × 包数`。**拿它减像素字节数是无效比较。** |
| 现役 1024×512 "恰好给出 0x40000 = 真像素字节数，完全正确" | ❌ 同样错的比较。按正确公式，**现役盘 `+0x30 = 0x3C3D0`（246,736）**，与像素字节数 `0x40000` **差 15,424 B** —— 比 736 大 20 倍，而这张盘**跑得好好的**。 |
| — | ✅ 正确结论：**记账本身无缺陷**；L1 的成败**与 `+0x30` 无关**。需实测的是 §4.3 的三件事。 |

> 现役 `h=512` 的容器把 **8 个 48 B 头从像素数据里挤出来**（末段只有 63.25 行，

### 4.4 真正的阻塞点③：显存

GS 的 4bpp 纹理缓冲按 `TBW × 64 × 2^TH` 分配，`TH = ceil_log2(h)`：

| h | TH | TEX0 | 缓冲 |
|---|---|---|---|
| 512（现役） | 9 | TW=10, TH=9, TBW=16 | **256 KB** |
| **任何 h > 512** | **10** | TW=10, TH=10, TBW=16 | **512 KB** |

⇒ **`h=640` 与 `h=1024` 的显存代价完全一样（512 KB）**，而 `h=1024` 是 PSMT4 的硬件上限
（`TW/TH` 4 bit 字段最大 10，TBW 6 bit 够用）。
⇒ 既然显存代价一样，选 h 的时候**只受 PAK 空间约束**，不受显存约束。
⚠ `UITextureMgr` 的 VRAM 分配器**仍未逆到**：现役 256 KB 分配成功，512 KB 能否拿到连续块 **未证实**。
**这是 L1 唯一必须靠实机回答的问题。**

| **级 1（立刻可做）** | **L0**：gate `0xB1→0xB4`（4 处 `sltiu`，各 1 字）+ 把用满现有 108 个**已空**格（row 24 col16..61 = 46，row 27 = 62）；扣掉被吃的 `0xB2/0xB3` 两个单字节汉字 ⇒ **净 +105** | **+105 字** | ELF 4 字 + 108 个字形像素 | 无 | **低**（有先例：round67 往空位塞 329 字，实机四档 lead 全部正常） |
| **级 2（需 P1+P2 通过）** | **L2 + L1-mini**：gate `0xB1→0xB5`（净 +372）+ 贴图 `h 512→640`（10 段容器，`px_size=0x501F0`）+ MENU.IMG 尾部后移 66,016 B | **+372 字**（**一次补齐全部 364 缺字，余 8**） | ELF 4~5 字 + PAK 记录 +66,016 B + MENU.IMG 条目 `off` | P1（平移安全）、P2（容器被接受） | **中**：三处未知全在"盘外"（IOP 硬编码 / 容器形状 / 512 KB 显存） |
| **级 3（级 2 失败才用）** | **L2 + 改格距**：`CW 16→14`（1898 格，仅横向）或 `CH 16→15`+`NCOL→64`（1920 格） | **+372 字** | ELF 常量 + **全盘重渲重排** + 步进宽/quad 高常量 | 无（不需要 PAK 长大） | **中高**：注册一个已经修好的缺陷类别（拉伸 / 文本度量回归）；`CW=14` 只剩 22 格余量 |

**容量终局**（级 2 达成时）：

| 项 | 值 |
|---|---|
| pair 码位 | `(0xB5 − 0xA1) × 94 = 1880`，扣 3 个被吃单字节 + 1 个图标码 ⇒ **1876** |
| 物理格 | `h=640`：36 行，EN 吃 2 行 ⇒ 34 可用行 × 62 列 = **2108 格**（现役用 1504，**余 604**） |
| 单字节码 | **110**（不变；`0xB1/0xB5` 仍是图标码） |
| **总汉字容量** | **1876 + 110 ≈ 1986**（现役 1504 + 110 = 1614） |
| 对缺字 364 | **全覆盖，余 8 个 pair 槽 + 604 − 372 = 232 个空闲格** |
| 若要 L4（stride 191） | 需 3056 码位 > 2108 ⇒ **必须同时改格距或再长高**；不建议本轮碰 |

### 5.2 ★ 与 r73 报告的 R1（`L1 + L2`）**逐条对账**

| 项 | r73 R1 | 本报告 | 一致？ |
|---|---|---|---|
| 图集尺寸 | 1024×512 → **1024×1024** | **1024×640**（1024 装不下） | ❌ **不一致**（原因：PAK 空间） |
| `px_size` | `0x80310`（16 段） | `0x501F0`（10 段） | ❌ 不一致 |
| 新增格 | 行 27..59 × 62 = **+2046** | `h=640`：行 27..35 × 62 = **+558**，加 row 24 尾 46 ⇒ **+604** | 口径不同，**算术本身一致**（r73 的 2046 + 46 = 2092 空闲，与"h=1024 → 3596 可用 − 1504 已用"相符） |
| PAK 长大 | "~0x40300，风险中" | **这是 L1 唯一的致命点**：可用空位只 89,908 B；`h=1024` 要 262,912 B | ⚠ **r73 定级偏低**（它列为"风险中"，实际是"物理装不下"） |
| 显存 | "1024×512=256 KB → 1024×1024=512 KB，未核" | 更精确：**任何 h>512 都跳 512 KB**（TH 9→10）；`h=640` 与 `h=1024` 代价相同 | ✅ 一致且更精确 |
| `+0x30` 记账 | "**唯一可能致命的点**，未查到，需再逆一层" | **读透了，不是风险**（r73 的 `B'` 公式错；交付字节恒 = `px_size`） | ❌ **r73 误报** |
| "网格行 ≥25 加 2 行跳空"补丁 | **需要**（让新槽落到 y ≥ 482） | **不需要**：行 27 起 `y = 16r + 50 ≥ 482`，天然越过 EN 带 `[452,468)` | ❌ **可以省掉一个补丁** |
| L2 gate 4 处 → `0xB5` | 4 个字 | 一致 | ✅ |
| 净增 | `376 − 3 − 1 = +372` | 一致 | ✅ |
| 现有 1504 格是否要重排 | 不需要 | **一致**（slot 公式与格位公式都不变） | ✅ |
| `MENU.IMG` 偏移冻结 | "证据冲突，未解决；若成立则 L1/L5 全堵死" | **本报告把它升级为 L1 的头号阻塞**，并给出 0 命中的双盘证据 + `EN_STRINGS.TXT` 搬迁先例 + 干净的 P1 探针 | ⚠ 从"未解决"变"必须先测" |
| 是否需要探针 | "必须"（h=1024 单变量） | 一致，但**探针要拆成 P1/P2/P3 三次**，且 **P1 优先** | ⚠ 细化 |
| 顺带发现（GR_ZH117 坏盘） | 已记录 | 本报告确认**最新完整盘 = `GR_ZH113b`**（`GR_ZH118` 目录里只有 dump，无 `.iso`） | ✅ |

## 6. 【交付物⑥】明确的「不要做什么」清单

| # | 不要做 | 为什么（历史证据） |

| 1 | **不要**再把"1024 维不被支持 / `pda` 描述符冻结 / 存在第二个尺寸硬假设点"当成先验结论 | F5/F6 都已被削弱或推翻；现役盘就是 1024 宽 PSMT4，在**原版 gsrunner** 上跑满 28300 帧 |

| 8 | **不要**在改 `CW` 时忘了 `0x416FC0` 的 CJK 步进宽（现役 16），或改 `CH` 时忘了 V18B 的 quad 高（现役 16） | 不改就是**横/纵拉伸**；这正是 ZH13→ZH36 花了 3 轮才消掉的缺陷 |
