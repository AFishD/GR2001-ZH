## 2. 先读代码：现役盘的 gate 到底是多少（`work/builds/GR_ZH98/temp/r65/p1_check_gate.py`）

直接从 ISO 读 ELF（LBA 295 + 段偏移 0x80，VA 基址 0x00100000），点名 4 个历史站点 + 全段扫描：

```
0x416EE8  2CA900B1  sltiu rs=5  rt=9   imm=0xB1   ★
0x417160  2D0900B1  sltiu rs=8  rt=9   imm=0xB1   ★
0x41751C  2D4B00B1  sltiu rs=10 rt=11  imm=0xB1   ★
0x5656A4  2D6C00B1  sltiu rs=11 rt=12  imm=0xB1   ★

全段 slti/sltiu 且 imm ∈ {A1,AD,AE,AF,B0,B1,B4,FE,FF}:
  imm=0xA1 : 11 处 (含每个 gate 前面的 `sltiu reg,0xA1` = 下界)
  imm=0xAE : 0 处          ← "只认 0xA1..0xAD" 的说法在现役盘上**没有对应指令**
  imm=0xB1 : 4 处 (就是上面那 4 条)
  imm=0xFF : 5 处 (trail 上界)
```

⇒ 判据 = `0xA1 ≤ b < 0xB1`，即 **lead ∈ 0xA1..0xB0（16 档）**；**全 ELF 没有第 5 处漏网 gate**。
这与 `docs/REPORT_plan_c_zh93.md`（`方案 C`，`GR_ZH93` 把 4 处 `0xAE` 抬到 `0xB1`）完全一致，
也解释了为什么现役 charset 里 **lead ≥ 0xAE 的 pair 一个都没有** —— 不是"引擎读不了"，
而是 round56 那次"死 pair 收敛"**按过时的判据多搬了一次**（白搬，没坏处）。

> ⚠ 工程里残留的**过时文案**（代码行为是对的，只有人话说明是旧的，建议后续清理，本轮未动）：
> · `tcslib.Charset.decode` 上方注释「严格按引擎 (ELF 四处 `sltiu lead,0xAE`)」；
> · `tcslib.Charset.encode` 的报错文案「引擎只认 0xA1..0xAD」；
> · `docs/FORMAT.md`、`docs/REPORT_charset_guard.md`、`docs/BUILD_TOOLCHAIN.md` 的同一句话。
> 代码里的真值常量 `LEAD_HI = PAIR_LEAD_HI = 0xB1` 一直是对的（`pair_capacity() = 1504`）。

## 3. 探针设计（`tools/iso_build/probe_engine_limit.py`）

**思路**：同一个汉字的字形**额外抄一份**到高 lead 的空白格里，再在「特别收录 → 访谈 → 开发访谈 1」
的 `<text>` 里写**同屏对照串** —— 只要看两组字长得一不一样，就知道那个 lead 能不能用。

| 行 | 用什么码位 | 作用 |
|---|---|---|
| `PROBE` | — | 标签行 |
| `O: 我国山` | 现役码位 `A6A9 / A5DE / A7C2` | **对照**：本来就能显示 |
| `AD: 我国山` | 新格 `ADD0 / ADD1 / ADD2`（slot 1175/1176/1177） | **写盘法对照**：新格 + 一个**已知可用**的 lead —— 证明"新写的字形真的被引擎采样" |
| `AE: 我国山` | 新格 `AEB1 / AEB2 / AEB3`（slot 1238/1239/1240） | 试探 lead `0xAE`（`方案 C` 扩出来的第一档） |
| `B0: 我国山` | 新格 `B0B1 / B0B2 / B0B3`（slot 1426/1427/1428） | 试探 lead `0xB0`（gate 允许的**最后一档**） |
| `B1: 我国山` | 新格 `B1B1 / B1B2 / B1B3`（slot 1520/1521/1522） | 试探 lead `0xB1`（gate 之外的第一个字节，**预期失效**） |
| `S: B2 B1 B5` | 单字节码 0xB2 / 0xB1 / 0xB5 | 次级问题：单字节带空码位能不能放字 / 图标码是不是硬编码 |

**判据**（每行都带 ASCII 标签，故**页面初始滚动在哪一行都能认出来**）：

* `O:` 正常 ⇒ 探针本身有效；
* `AD:` 与 `O:` 相同 ⇒ 写盘法有效 ⇒ 后面若失败，只可能是 **lead 被拒**；
* `AE:`/`B0:` 与 `O:` 相同 ⇒ 该 lead 可用；渲染成别的字/空白 ⇒ 该 lead 被引擎当单字节；
* `B1:` 与 `O:` 明显不同 ⇒ 上界 = `0xB1`，与 ELF gate 一致。

**目标格怎么挑**（全自动，硬门禁）：trail 只从 `0xB1..0xFE` 里挑（万一 lead 被当单字节，
trail 也不会再吞掉后一个字）；格必须 **零墨 + 不被任何 FT 记录矩形（3 个 face）覆盖 +
不在 `ATLAS_ENGINE_SINGLE_CELLS` + slot 未被现役 charset 占用**；列 ≤ 61（永不落到"回绕列" x ≥ 992）。

**payload 为什么要"探针块 + 90 个空格"反复交错**：`<text>` 载荷长度必须**一字不差**
（容器 `repack()` 断言 `len(new_blob) == len(blob)`）。而 round61/63 的实拍证据显示
**该正文框的初始滚动不在开头**（`work/builds/GR_ZH98/temp/r63/tp_unicode_report.json` +
drawlog 实测窗口落在全文第 52/65 行）⇒ 只把探针写在开头会看不到。
空格只有 3px 宽（64 个/行），所以"块 + 90 空格"铺满整个载荷后，**任何 ~10 行的可视窗口里
都必然含一整块探针**，而总视觉行数只有原来的 ~1.1 倍（不会踩 round60 的"文字太多 ⇒ 整页空白"）。
实拍结果验证了这一点：屏幕上正好显示**一整块**（第 2 块的首行 `O: 我国山` 也在窗口内）。

**硬门禁全过**（`probe_engine_limit.py` 自身输出）：


### 4.1 肉眼判据（`probe_page_zoom.png`）

```
PROBE
O: 我国山          ← 对照 (现役码位)                     ✓ 正常
AD: 我国山         ← 新格 + lead 0xAD                    ✓ 正常 (证明"新写字形"确实生效)
AE: 我国山         ← 新格 + lead 0xAE                    ✓ 正常 ⇒ ★ 假说 B 被证伪
B0: 我国山         ← 新格 + lead 0xB0                    ✓ 正常 ⇒ ★ gate 的最上一档也可用
B1: △△ △键 △练    ← 新格 + lead 0xB1                    ✗ 6 个字形块 = 0xB1 被当单字节
S: 键 △ ✕          ← 单字节码 0xB2 / 0xB1 / 0xB5         ⇒ 0xB1=△、0xB5=✕ 是引擎硬编码图标码
```

`B1:` 行的读法：`0xB1` 不是 lead ⇒ 每个"pair"被拆成**两个单字节**：
`(B1,B1)` → △ △；`(B1,B2)` → △ + `键`（0xB2 的现役单字节字）；`(B1,B3)` → △ + `练`（0xB3）。
**这正是 round61 记的"渲染成两个怪字"现象** —— 但它的成因是 **lead 上界是 0xB1**，
而不是"lead ≥ 0xAE 都读不了"。

### 4.2 量化（`work/builds/GR_ZH98/temp/r65/p13_rowspan.py` + `p14_figure.py`）

同一批字形，只差 lead。取每行"字形区"（标签之后到行尾）的墨像素宽度：

| 行 | 标签宽 | 字形区 x | 字形区宽 | ≈汉字数 | 判定 |
|---|---|---|---|---|---|
| `O:` | 19 px | 51..101 | **51 px** | 3.2 | 基准（3 个汉字 + 2 个空格 = 54 px） |
| `AD:` | 27 px | 59..109 | **51 px** | 3.2 | ✓ 与基准同宽 ⇒ 写盘法有效 |
| `AE:` | 27 px | 59..109 | **51 px** | 3.2 | ✓ 与基准同宽 ⇒ **lead 0xAE 可用** |
| `B0:` | 27 px | 59..111 | **53 px** | 3.3 | ✓ 与基准同宽 ⇒ **lead 0xB0 可用** |
| `B1:` | 27 px | 59..172 | **114 px** | 7.1 | ✗ **2.15 倍宽** = 6 个字形块（6×16 + 5×3 = 111 px）⇒ **0xB1 不是 lead** |

宽度口径**完全不受重采样相位干扰**（实拍 PNG 是 583×437 的非整数倍重采样，

结论一致但分离度只有 1.3~1.5 倍，故最终以**宽度口径**为准：3 个字 vs 6 个字，2.15 倍，无歧义）。

## 5. 结论：字库真实可用容量

### 5.1 假说裁决

| 假说 | 裁决 | 证据 |
|---|---|---|
| **A**：lead 0xB1..0xB3 可用，1736 格 | **证伪** | `B1:` 行渲染成 6 个字形块；ELF 4 处 gate 都是 `sltiu …,0xB1`（0xB1 及以上的字节**不是** lead） |
| **B**：只认 lead ≤ 0xAD，1222 格 | **证伪** | `AE:` / `B0:` 行与对照**同宽同形**，实机正常显示汉字；全 ELF 扫不到任何 `imm=0xAE` 的 lead 判据 |
| **真值**：lead 0xA1..0xB0（16 档） | **成立** | ELF gate `0xA1 ≤ b < 0xB1` + 实机 `0xAE`✓ `0xB0`✓ `0xB1`✗ |

> `0xAF` 未单独点名测试 —— 但判据是**一条无符号区间比较**（下界 `sltiu reg,0xA1`、上界 `sltiu reg,0xB1`），
> `0xAE` 与 `0xB0` 都在区间内成立、`0xB1` 落在区间外，故 `0xAF` 必在其中。
> 要单独取证也只是一条命令：`--leads AF`（§7）。

### 5.2 逐格账本（`p7_capacity.py` / `p8_blocked.py`，只读现役盘实测）

```
现役 charset: 对偶 1175 (slot 0..1174) + 单字节 110

[假说 B: lead ≤ 0xAD]    可寻址对偶 slot 1222  ⇒ 还能加  13 个
[现役 gate: lead ≤ 0xB0] 可寻址对偶 slot 1504  ⇒ 278 个 (按 tcslib 那张**过期标注表**口径)
                                                329 个 (按**实际像素**口径 —— 见 §5.3)  ★ 真值
[假说 A: lead ≤ 0xB3]    可寻址对偶 slot 1786  ⇒ 其中 1736 以外越界 50 个;
                          1504..1735 里干净格只有 112 个 (另有 91 格是 ASCII 带字形、29 格被 ASCII 记录压)
```

| 项 | 数字 |
|---|---|
| 引擎可寻址对偶 slot（lead 0xA1..0xB0 × trail 0xA1..0xFE） | **1504** |
| 现役已用对偶码 | 1175（slot 0..1174 连续） |
| **还能新增的汉字** | **329** |
| 免费格按 lead 分布 | `0xAD`: 47（trail D0..FE）／`0xAE`: 94／`0xAF`: 94／`0xB0`: 94 |
| 这 329 格的物理状态 | **全部零墨、且不在任何 FT 记录矩形里 ⇒ 直接可写** |
| 单字节带可用空码位 | **0**（见 §6） |
| **字库真实可用容量** | **1175 + 329 = 1504 汉字**（对上界 1504 恰好用满） |

### 5.3 ★ 附带发现：`ATLAS_ENGINE_SINGLE_CELLS` 的 51 条标注**已全部过期**

`tcslib.ATLAS_ENGINE_SINGLE_CELLS` 里有 51 条"对偶码不可占用"的封禁标注
（行 19 col 0..33、行 24 col 0..5 与 col 12、行 21/22 col 5..8、行 23 col 8/9）。
逐格实测：**这 51 格现在全部零墨、且不被任何 FT 记录矩形覆盖**（`p8_blocked.py` 的输出
「标注总数 51；其中现在其实零墨且无记录矩形的 = 51 个」）。

原因：那批**单字节码的 FT 记录矩形早被 round55/104 搬到 `y = 195/211` 的"跳过带"**了，
标注却还停在 round45 的旧版图（当时单字节记录就在网格行 19/24 上）。

后果：按**标注口径**算，空闲是 329 − 51 = 278；按**实际像素口径**算，空闲是 **329**。
本报告的 329 用的是实际像素（探针盘就是这么挑格的 —— 它只信"零墨 + 无记录矩形"，
不信那张标注表）。**建议后续把那 51 条标注按实测清掉**（本轮未改 `tcslib`，不在授权范围）。

## 6. 次级问题：单字节带空着的 18 个码位能不能放汉字

**结论：一个都不能。** 空码位 = `0xA1..0xB0`（16 个）+ `0xB1` + `0xB5`（共 18 个）。

| 码位 | 为什么不能用 | 证据 |
|---|---|---|
| `0xA1..0xB0`（16 个） | 它们是引擎的**对偶 lead 区间** —— 写出去会被当成双字节首字节，**吞掉后一个字** | ELF 4 处 `sltiu …,0xB1`；本轮 `AE:`/`B0:` 两行正是"这些字节确实是 lead"的实拍证据 |
| `0xB1` | 引擎**硬编码的 △ 三角键图标码**，不吃字库 | 探针 `S: 键 △ ✕`：0xB1 位置画的是 △；而它的 FT 记录矩形 `(480,213,490,229)` 是 **0 墨** —— 字库路径根本画不出 △ |
| `0xB5` | 引擎**硬编码的 ✕ 叉键图标码** | 同上（0xB5 记录矩形与 0xB1 共用 `(480,213,490,229)`，也是 0 墨） |

同屏 `S:` 行还顺带证明了**单字节路径本身是活的**：`0xB2` → `键`（现役 charset 里 0xB2 的字），
字形来自 FT 记录 `(80,195,96,211)`（y=195 的"跳过带"）。

⇒ 单字节带的贡献 = **0**，容量只能从对偶那 329 格出。

## 7. 可复用探针工具

```
python tools/iso_build/probe_engine_limit.py <src.iso> <dst.iso>
       [--chars 我国山] [--leads AD,AE,B0,B1] [--singles B2,B1,B5]
       [--item-name 开发访谈 1] [--charset PATH] [--gap 90] [--label PROBE]
       [--report R.json] [--dry-run]
```

* 给一组 `(汉字, lead)` 即自动：挑干净格 → 抄字形 → 拼对照串 → 写盘 → 跑 5 条门禁 → **打印导航命令**；
* 可以直接当 `make_build.py` 的 `--patch` 脚本（它只认 `<src> <dst>` 两个位置参数）：

```
python tools/iso_build/make_build.py GR_TEST_PROBE_LEAD --from work/builds/GR_ZH109 \
       --patch tools/iso_build/probe_engine_limit.py \
       --no-font-compact --no-textdump --no-text-snapshot --no-font-dump
python tools/capture/nav_hook.py GR_TEST_PROBE_LEAD --tag probe        # ≈ 6 分钟
# 看 work/builds/GR_TEST_PROBE_LEAD/temp/dump_probe/probe_page.png
```

> ★ `--no-font-compact` **必须**带上 —— 默认的字库紧凑重排会把字形搬回 `slot 0..N-1` 并重编码全盘文本，
> 探针盘的对照关系会被它抹掉。

**同类问题怎么问**（改几个参数即可，都是一次实机 ≈ 6 分钟）：

| 想问的 | 命令 |
|---|---|
| `0xAF` 单独取证 | `--leads AF` |
| 单字节带上限 | `--singles B2,B3,B4,B6,07` 等 |
| 图集 row 25~27 能不能用（要先把 gate 抬到 0xB4） | `--leads B2,B3`（并在 `--patch` 前先打 ELF gate 补丁） |
| 一个新的空闲格是否真被采样 | `--leads 某lead --chars 某字`，看 `AD:` 行 |

## 9. 已知限制 / 未验证项

1. **只点名测了 `0xAE` 与 `0xB0`**；`0xAF` 由"区间比较 + 两端成立"推得，未单独点名（一条命令可补）。
2. **只测了 SFXML `<text>` 这一条渲染路径**。4 处 gate 里 3 处在共用的文本模块（`0x41xxxx`）、
   1 处在 `0x5656A4`，理论上 HUD/菜单/RES 走同一套；但**未在其它界面复核**。
3. **只放了 12 个新字形**（3 字 × 4 lead）。这是"逐 lead"的机制验证，不是 329 格的逐格遍历；
   不过"格是空的 + 引擎按 `(16*col, yrow)` 采样"这两点分别有 round45 A/B 证据
   （`docs/REPORT_glyph_align.md`）与本轮 `AD:` 行的实证。
4. **实拍 PNG 是 583×437 的非整数倍重采样** ⇒ 逐像素模板匹配对同一内容也有 10~20 px 噪声；
   最终判据改用了不受影响的**字形区宽度**（3 字 vs 6 字，2.15 倍分离）。若需逐像素级证据，
   得让模拟器出 1:1 的 512×448 截图（本轮未做）。
5. **`ATLAS_ENGINE_SINGLE_CELLS` 过期**这条只在本轮脚本里按实测口径处理；`tcslib` / `font_cell_map.py`
   里那张表**没改**（不在本轮授权范围）⇒ 其它工具仍会按 278 而不是 329 算。
6. 未做：`--gap` 空格铺法在**别的正文框**（行宽不同）上的通用性；本轮只验证了「开发访谈 1」这一页。
7. 未做：把 329 个新格真的分配出去（那是字库工程的活，本轮只回答"能不能用"）。
