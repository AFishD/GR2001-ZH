# 字库用量核算 + 码位/格位回收工具（`tools/font_pipeline/font_usage.py`）

> **round38 新增** · 只读工具 + dry-run 回收 · 本报告全部数字可在现役盘上复现
> 盘：`work/builds/GR_ZH92/GR_ZH92.iso`（sha256 `1d30c1067beb8fc8534193486f23f75489447eb0487ab24d06ef66c0627120b6`）
> 对照盘：`work/builds/GR_EN_ORIG/GR_EN_ORIG.iso`（英文原盘）

---

## 0. 给用户的一句话

**字库能腾出来的格位，比看上去少得多 —— 但本来就够用。**

新译文要补 70 个非 ASCII 字，字库还剩 **78** 个空位 ⇒ **不改字库也能补完**（余 8）。
回收闲置字能再多腾 **13** 个格位（合计 91，余 21）。
"闲置字"看着有 145 个，但其中 **132 个是死 pair**（引擎根本读不了的旧垃圾），
把它们算进"能腾多少"是**算多了**。本工具的价值不在于多腾几个格位，而在于
**第一次把"哪些字真的不该再占位置"这件事量清楚了**，并且**证明了**其他容器里的
"命中"全是噪声。

## 1. 为什么要做这个工具（它补的是哪一半）

现有工具链的「字库覆盖预检」（`tools/text_csv/inject_text_csv.py::charset_precheck`）
**只做加法**：

* 它统计「**将被写入的文本**里、字库没有的字」→ 缺字清单 → 缺字就拒绝写盘；
* 它**从不统计**「字库里有、但全盘已经不再使用」的字 → **没有回收逻辑**。

后果：字库只增不减。改一次译就多几个字，老字永远占着码位与图集格位，
即使游戏里再也不会画它。`font_usage.py` 补上「减法」那一半。

## 6. 与 Lead 临时核算的交叉验证（验收 #3）

Lead 的临时核算（`work/builds/GR_ZH92/temp/字库用量核算.md`）只覆盖 `LANG` + `SFXML`，
用的是 CSV 文本表口径。本工具在**同一个 charset 版本**（构筑期 1357 字）上：

| 项 | Lead 临时核算 | 本工具 | 结论 |
|---|---|---|---|
| 新文本缺字总数 | 153 | **151** | 差 2 |
| — 非 ASCII（真正要补） | **70** | **70** | ✅ **完全一致** |
| — ASCII（不阻断） | 83 | 81 | 差 2 |
| 字库闲置字 | **145** | **145** | ✅ **完全一致** |
| — 其中"本次改译释放" | 0 | **0** | ✅ 一致 |
| 闲置里"旧文本也没用到" | 151 | 151 | ✅ 一致 |

### 6.1 差异逐条解释

**差异只有一处：ASCII 缺字 83 vs 81（总数 153 vs 151）。**

原因：Lead 的脚本 `chars()` 只过滤 `ord(c) >= 0x20`，**保留了 `{WRAP}` 之类的工具标记里的
字母**（`W` `R` `A` `P`）与 `{{BTN:XXXX}}` 标记里的 `B` `T` `N` `X`。本工具按工具链口径
先把 `T.WRAP_RE` / `T.BTN_RE` **整体剔除**再取字符 —— 这些标记**不会写进盘**
（`{WRAP}` 变真换行、`{{BTN}}` 由引擎直接画图标），所以它们不是"缺字"。

* Lead 的 ASCII 缺字里有 `{` `}` `W` `R` `A` `P` `B` `T` `N` `X` 等；
* 本工具剔掉标记后剩 81 个，**非 ASCII 一个不差（都是 70）**。

⇒ **两套口径在"真正要补的字"上完全一致**；差异纯粹是"工具标记算不算字"。
本工具的口径与 `inject_text_csv.py` 的预检**同一套**（预检也整体跳过这两类标记）。

### 6.2 ★ 本工具**修正**了 Lead 报告里的一处关键误导

Lead 的临时报告写：

> 「若回收全部闲置字: 78 + 145 = 223」

**这个加法是错的**（对"能补多少新字"这个问题而言）。实测：

* 145 个闲置字里，**132 个是"死 pair"** —— 它们的 lead 是 `0xAE/0xAF/0xB0`，
  而引擎的 DBCS 判据是 `sltiu lead, 0xAE`（只认 `0xA1..0xAD`）。
  解码器 `decode()` **永远不会**产出它们（分支条件就写着 `0xA1 <= v < 0xAE`），
  编码器 `encode()` 也**明确拒绝写出**它们。
* 死 pair 的格位号 `slot = (lead-0xA1)*94 + (trail-0xA1) >= 13*94 = 1222`，
  **落在合法对偶空间（0..1221）之外** ⇒ 释放它们**换不来任何新字格位**。

⇒ 真正的增量是 **13 个**（合法对偶），不是 145 个。
Lead 报告里点名的人名用字（`兰冈凡刘俊傅勃卜…`）经查**全部是死 pair**；
只有 `丁 丹 丽 乔 亨 伟 伯 佐` 等 **8 个**人名用字是合法对偶、真的能腾格位。

### 6.3 ★ 本工具的 E0 与 CSV 文本表**逐字完全一致**

| 口径 | 字库内用到的字 |
|---|---|
| 本工具 E0（直接解析盘上 `LANG`/`SFXML` 正文） | **1206** |
| CSV `text_zh` 列（既有 dump 出来的现值） | **1206** |
| 只在 E0 里、CSV 没有 | **0** |
| 只在 CSV 里、E0 没有 | **0** |

⇒ 两套口径**差集为空**，说明 E0 解析可信、且与既有工具链同口径。

## 7. 保守性验证（验收 #4）

脚本：`work/builds/GR_ZH92/temp/r38/test_conservative.py`（**全部通过**）

**A. 真实盘实测 —— 如实说明**

现役盘 `.ATR` **1460 个**（`GR.IMG` 1193 + `MENU.IMG` 267），解压后共 **889,234 B**，
出现的**非 ASCII 字符 0 种**。
⇒ **人名全是英文**，盘上**不存在**"只在 `.ATR` 里出现"的真实汉字。
这直接决定了可回收量：`.ATR` 对可回收量**没有贡献**（但它仍被逐字节扫，
是为了将来人名回填中文时不会漏）。

同理实测：`.MIS`（92 个 / 5.0 MB）、`.XML`（35 个 / 1.3 MB）、`.TXT`（17 个 / 0.1 MB）、
`.RES`、`ELF`、其它 ISO 文件 —— 减去英文盘命中后**独立贡献都是 0**，即**都没有中文文本证据**。

**B. 构造用例（证明"某字只在 `.ATR` 里出现"不会被判为可回收）**

取真实 `.ATR` 内容（含 `<ActorName>`），把闲置字「±」的对偶码 `A4 D4` 插进人名里，
再用**本工具的同一个扫描函数**判定：

```
[ok] E1 扫描把「±」判为"用到" ✓ (在 >=4 的可读串内部)
[ok] 「±」**不在**可回收清单里 ✓
[ok] 「±」被拦下 ✓ 原因: E1 其它可能装文本的容器里有可读串证据 (已减掉英文原盘命中)
```

**C. 对照（positive control）** —— 同一个字在**没有任何证据**时必须被判为可回收：

```
[ok] 对照: 同一个字在**没有任何证据**时确实被判为可回收 ✓ (否则判据就是坏的)
[ok] 对照: 走 E0 (结构化文本) 路径同样拦得住 ✓
```

**D. 单字节码路径**：把单字节字「一」(码 `0xC5`) 塞进 `.ATR` ⇒ 同样被判为"用到"、同样不回收。
（附带结论：**76 个单字节码全部在用**，没有闲置的单字节字。）

**E. 死 pair 的分类**：137 个死 pair 归入**可回收的清理项**（不是"拦截项"），
且它们的格位号全部 `>= 1222`（合法对偶空间之外）✓

### ★ 与另一个子代理的撞车（如实记录）

测试期间 `charset_compiled_zh16.json` 被**外部进程**改动了多次
（`5727af6b…` → `68d1b124…` → `14c80288…`，字数 1357 → 1433 → 1428）。

1. 工具自报"读到的字符集 sha256" == 运行前量到的值（只读）；

旁证：文件被改后，本工具列为"可回收"的字**仍然在文件里**（本工具若写就会摘掉它们）。

## 9. 与现有「只做加法」预检的关系（互补，不是替代）

| | `inject_text_csv.py` 预检（加法） | `font_usage.py`（减法） |
|---|---|---|
| 问的问题 | "**要写的文本**里有字库没有的字吗？" | "**字库里有**全盘不再用的字吗？" |
| 输入 | 要写入的 CSV 行 | 整张盘 + 字符集 |
| 输出 | 缺字 ⇒ **拒绝写盘**（退出码 3） | 可回收字 ⇒ **释放码位/格位** |
| 时机 | **每次注入前**，秒级，是硬门槛 | 改译一批之后，分钟级，是决策依据 |
| 判据 | 逐字符查 charset + 盘上字形（FT 记录/图集） | E0 结构化文本 + 对照减法（四级证据） |

**两者口径已经对齐**（§6.3 实测差集为空），但**职责不重叠**：

* 预检保证"**不会写出画不出来的字**"；
* 本工具保证"**不会永远占着用不到的字**"，并回答"**格位够不够**"。

**推荐顺序**：

```
font_usage.py（算能腾多少 / 够不够）
   → 需要时 --apply 出**新** charset + 重排计划
   → 字库管线按计划重铺图集（另轮）
   → inject_text_csv.py 注入文本（预检把关）
```

## 10. 已知限制（诚实清单）

1. **视频/音频流**（`MEDIA`：`.PSS/.SS/.TM/…`，1300 MB）只做**字节级**扫描 ——
   引擎不会从它们里面画字，但仍按最保守口径扫了它们的字节。
2. **运行时写入的数据**（记忆卡存档、运行时拼出来的字符串）**无法离线扫描**。
   若某字只在存档里用，本工具会误判为可回收。
3. E1/E2 判据是"编码落在长度 ≥ 阈值的可读串内部" ⇒ 藏得**很短**的中文串会被漏判
   （`--min-run` 可调小重跑对比）。
4. `SFXML` 只解析 `<text>…</text>` 正文（与 dump/inject 同口径）；XML 标签属性里的中文不在 E0 里。
5. 本工具**不改**字库图集 PNG / FT 记录表 —— 回收后要真正生效，还得由字库管线重铺图集。
6. **哪些容器"还没被覆盖"**：盘上**所有** ISO 文件与两个 IMG 的全部条目都扫了（4713 个）。
   没扫的只有"运行时才产生"的数据（见第 2 条）。
7. 与英文盘**不同的 30 个容器**（`LANG`×2、`SFXML`、`FONT.RES`×2、`COMMON.PAK`×2、
   20 个本地化贴图、`NTSC_IKE.RES`、`EN_STRINGS.TXT`、`SLUS_206.13`）无法用"逐字节相同"证明，
   但已用**同容器集合减法**处理（只有英文盘没有的命中才算证据）。

## 11. 顺带发现的三件事（交 Lead 判断，本轮**没有**动手改）

### 11.1 `tools/diag/res_text_dump.py` 的解码口径与本工程不一致（历史待办）

`res_text_dump.py::Dec.text()` 用的是**对偶优先**：

```python
if b in self.leads and (b, raw[i+1]) in self.pairs:   # 先试对偶
```

而本工程（`tcslib.Charset.decode` + ELF 四处 `sltiu lead,0xAE` 实测）是**单字节码优先**。
后果：`AF A1 BD`（的 方）会被它误读成 `弗开`，`B0 AF`（你 的）会被误读成 `蔡` ——
**整份 dump 系统性错字**。

本工具**没有**复制这个错误口径：`decode_chars()` 的分支顺序与 `tcslib` 逐条一致，
并在 `--selfcheck` 里用真实字节把它钉死（`[ok] AF A1 BD 解为 '的方'`）。
**本轮按铁律"只新增文件"没有改它** —— 建议 Lead 把 `res_text_dump.py` 的
`Dec.text()` 换成 `tcslib.Charset.decode` 的口径（一行级改动）。

### 11.2 charset JSON 里的 `grid` 块是**陈旧的 13px 几何**

现役 `charset_compiled_zh16.json` 的 `grid` 写的是：

```json
{"ncol": 37, "cw": 13, "ch": 13, "skip_row": 14, "skip_off": 39, "x0": 20, "n_chars": 1212, ...}
```

而 16px 图集实际用的是 **`ncol=62, cw=ch=16, skip_row=12, skip_rows=3`**
（`tcslib.NCOL/CW/CH/GRID_*`、`gen_font16.py` 的产物、ELF cave 的公式、`dump_font.py` 的输出，
四处一致）。**谁读 `grid` 谁就会算错格位。**

本工具一律按 62×16 公式算，并且做了**独立交叉验证**：把 `font/GR_ZH92_font_charset.csv`
里 1281 个对偶字的 `slot / cell_x / cell_y` 与公式结果**逐条比对，全部一致** ✓
（见 `make_charset_1357.py` 输出）。`grid` 块原样保留、没有改动。

### 11.3 ⚠ 现役 charset 里 32 个单字节码落在工具链的"毒区" `0x80..0x9F`

扩字库时新增的单字节码里，有 **32 个落在 `0x80..0x9F`**（实测例：`普=0x92 稳=0x80 箱=0x81
米=0x9F 纤=0x83 …`，码位随改写略有变动），另有 **1 个落在 `0xA0`**。
而本工程自己的工具链**明确拒绝**这个区间：

* `tools/hanliu/tools/text_replace.py`：`bad = [x for x in b if 0x80 <= x <= 0x9F]` → `die('输出含毒区字节')`；
* `font_build.py`：`POISON` 常量把这一段排除在单字节码池之外。

**这是观察记录，不是结论** —— 那个 charset 正在被另一个子代理改写中，可能只是中间状态。
`font_usage.py --selfcheck` 会把这类风险**自动报出来**（判据从 charset 现算，不写死版本），
建议扩字库任务收尾时跑一次：

```powershell
python tools/font_pipeline/font_usage.py --selfcheck
```

**同一次自检还抓到过两个更严重的问题**（`--selfcheck` 现在会自动报出来）：

| 现象 | 为什么严重 |
|---|---|
| `磅` 曾被映射到单字节码 **`0x7F`**（现已改掉） | `tcslib.decode` 的分支顺序是 `if v < 0x80 → ASCII`，所以 `0x7F` 上的字**永远解不回来** —— 写出去以后 `encode_strict` 的编解码对称自检会直接失败 |
| **`志=0xAE`、`普=0x92` 落在 charset 自己的 `protected` 列表里** | charset 文件自我矛盾：`protected` 的语义就是"这些字节不许占用"（原意：英文盘在用的 `® ± µ ç ñ` + 毒区字节 `0x92`）。本工具尊重该列表、**不回收**这两个字，但按定义它们本就不该占这些码位 ⇒ 建议扩字库侧核对 |

另有 5 个字（`延 志 普 略 米`）**同时**有单字节码和对偶码。`encode()` 单字节优先，
所以对偶那一份是"死重量"—— 所幸这 5 个的对偶都是死 pair（`AEFE/AFA5/AFB0/AFEC/AFF0`），
**不占合法格位**，没有浪费。若将来出现"单字节码 + **合法**对偶码"的组合，
那个对偶格位就是**白占的**，`--selfcheck` 会报出来。

建议扩字库任务收尾时跑一次：

```powershell
python tools/font_pipeline/font_usage.py --selfcheck
```

## 13. 结论

1. **工具做出来了，而且比临时脚本严格得多**：4713 个容器全覆盖、四级证据、
   英文原盘对照减法、逐字给拦截原因、dry-run 回收 + 重排计划 + 回收后自检。
2. **与 Lead 的临时核算在"真正要补的字"上完全一致（70 / 145）**；
   唯一差异是工具标记（`{WRAP}`/`{{BTN}}`）算不算字 —— 本工具按工具链口径剔除，更准确。
3. **修正了一处关键误导**：闲置 145 字里 132 个是死 pair，
   **真正能腾出的格位是 13 个，不是 145 个**。
4. **容量结论：够用**。78 个空位 ≥ 70 个缺字（余 8）；回收后 91 个（余 21）。
   ⇒ **回收不是"必须"，是"余量保险"**。
5. **"全盘字节搜索"这条判据已被实测证伪**（65536/65536 bigram 全出现），
   本工具改用「结构化文本 + 对照减法」，并把这个结论固化进了报告与文档。
6. **本轮只读**：没有修改任何 ISO / 字符集 / 字库 / 文本表；`--apply` 只做了 dry-run。
