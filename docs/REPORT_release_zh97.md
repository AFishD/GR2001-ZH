## 1. 出盘过程（怎么做的，为什么这么做）

### 1.1 第一步：给 GR_ZH95 打记录带补丁

```
python tools\iso_build\patch_zh96_record_band.py ^
    work\builds\GR_ZH95\GR_ZH95.iso  work\tmp_zh97\GR_ZH97_base.iso
```
（脚本 `GR_ZH95` 只读；产物是新文件。日志：`temp/verify/patch_zh95_to_zh97.log`）

```
[plan ] 记录矩形 208 个 (3 face 去重); 其中 **64 个**的矩形压在溢出带行上
[plan ] 这些格里: 39 个格的字与 方正像素16 模板本来就一致 ⇒ 无需动; 0 个无量宽模板
[plan ] 需要修的格: 20 个                     ← 训火动习面务准可会出换下如以到中定斗是任
[write] 共改 76 像素 (只统计"不同才写")
[self1] 变更 76 像素; 溢出带内 76; **带外 0** (期望 0)              ✓
[self2] 修好的格在"非溢出带行"里的变更: 0 (期望 0)                  ✓
[self3] 544 条记录矩形 (非溢出带行) 与源盘不同的: 0 (期望 0)        ✓
[self4] 修好的格与 方正像素16 模板逐像素相同: 20/20                 ✓
[ver  ] 回读: PAK 里除像素容器外逐字节不变 ✓; 盘上解出的引擎图 == 目标图 ✓
```

> ⚠ 该脚本把报告**硬编码**写到 `work/builds/GR_ZH96_fix/temp/r47/record_band_report.json`。
> 本轮把新产出的报告**另存**到 `GR_ZH97/temp/verify/record_band_report.json`，
> 并把 GR_ZH96_fix 那份**原样还原**（逐字节比对一致，见 §6）。

### 1.2 第二步：标准构筑

```
python tools\iso_build\make_build.py GR_ZH97 ^
    --from work\tmp_zh97\GR_ZH97_base.iso ^
    --inject-csv work\builds\GR_ZH95\text
```

**★ 为什么用"默认（字库重排在开）"而不是 `--no-font-repack`：**

1. **重排在这张基底上是幂等的**（实测 `字库紧凑重排 — 无需重排 (0 改动)`）⇒ 开着它不会多改一个字节；
2. 开着它才能拿到构筑器自带的**「charset 与这张盘对不对得上」检查**——
   日志里那句
   `[note] charset 记录的"上次写入的盘"是 c1f5d8498c66…, 本次输入盘是 6fc966159150…`
   **正面上验证了"现役 charset 就是写给 GR_ZH95 的"**（c1f5d849… = GR_ZH95 的 sha256），
   而本次输入盘不同只是因为"基底被本轮的补丁改过" —— 即 brief 说的"从 GR_ZH95 出发用当前 charset 是正确的"；
3. 若关掉它，就失去上面这条自动核对，还得靠人工判断 charset 版本（brief 的反面例子正是从 GR_ZH94 出发的情形）。

**☆ 附带说明**：`--inject-csv` 用的是 **`work/builds/GR_ZH95/text/`**（当前 charset 对应的表），
实测 `[diff] 全盘差异 0 B / 3 个写入窗口; 窗口外差异: 无 ✓`、`[hash] 逐字节相同 (无改动)`
⇒ 注入这一步**一个字节都没改**。

### 1.3 结果

```
[font-repack] 字库已经是紧凑的 ⇒ **无需重排** (0 改动): ISO / charset / 文本都不动
[inject] 1/1 完成: work/builds/GR_ZH95/text → ISO sha 6fc9661591509682…
[done] work/builds/GR_ZH97
```
* 打了补丁的基底 sha256 = `6fc9661591509682…`
* 最终 `GR_ZH97.iso` sha256 = `6fc9661591509682…` —— **完全相同**
  ⇒ "标准构筑"这一步是纯粹的 **no-op**，最终盘 == 补丁后的 GR_ZH95。

### 2.5 y=353 那一行是否真的恢复成字体模板（独立复核）

`temp/verify/verify_record_band.py`（**不采信补丁的自检输出，从两张 ISO 现读**）：

```
修前 GR_ZH95 : 引擎图墨 104748
修后 GR_ZH97 : 引擎图墨 104748
全图集差异 texel = 76; 落在行 [353] (溢出带 [353, 369, 385, 401, 417, 433])

```

20 格的 y=353 行 ASCII 对照（`#` = 墨；**修前 / 修后 / 模板**）：

| 字 | 码 | 修前 | 修后 = 模板 |
|---|---|---|---|
| 中 | 0xD6 | `.#######........` | `.......#........` |
| 斗 | 0xD8 | `..###########...` | `.........#......` |
| 是 | 0xD9 | `............#...` | `#.....#########.` |
| 训 | 0xC2 | `................` | `.....#.......#..` |
| 火 | 0xC3 | `...........#....` | `##...........##.` |
| 习 | 0xC7 | `.......#........` | `..........#.....` |
| 务 | 0xC9 | `................` | `..#......#......` |
| …（其余 13 格同见 `record_band_verify.log`） | | | |

**读法**：这一行本来是每个字的**最底一行**，却被"上方那个字的上一代字形"整行盖住 ⇒
「中」多出 6 个墨点（用户看到的横条）、「斗」多出 10 个（看着像多了一只「扌」= 用户说的"抖"）、
「是」则被稀疏的溢出墨**盖掉了自己的底横**。补丁把这一行整体恢复成字体原样：
**多出来的墨去掉、被盖掉的笔画补回**，20/20 与模板逐像素相同。

## 5. 已知限制（诚实挂账）

### 5.1 「斗」的实机画面**没有拍到**（round47 也没拍到）
* 事实：`斗` 只出现在长文里（"战斗"）。本轮**确实进到了**含它的那一页
  （`drawlog` 从 `F27230` 起就在画 `指挥他们。战斗最激烈的时候由…`），
  但那一行**在可视区之下**：该页下滚速度实测只有"每 1~2 次短按滚 1 行"，
  而这一行大约在第 12 行 ⇒ 还要再滚 ~20 次（≈ 24000 帧 ≈ 6 分钟/盘），
  且同前缀的导航**已经出现过一次漂移**（`nav_doc_scroll` 漂到「统计」）。
  按 brief"进不去就如实说明，不要硬耗"，**本轮到此为止**。
* 替代证据（足够强）：`斗`(0xD8) 那一格在 2.5 里被独立复核过 ——
  y=353 由 `..###########...`（11 个墨点，其中 10 个是溢出残墨）恢复成模板的 `.........#......`，
  **修后与字体模板逐像素相同**。也就是说"像多了个提手旁"的那 10 个墨点在盘上已经没有了。
* 另外：全游戏文本表里**没有「抖」这个字**（round47 已 grep 证实），用户看到的第二个字就是「斗」。

### 5.2 采样窗的 1 行余量（沿用 round47 的口径，未变）
记录矩形的口径是"采样窗 = 记录矩形那 16 行"；若实际采样窗再下移 1 行，
则 y=353 是显示的**倒数第二**行 —— 两种口径下本轮的修复**都**减少污染，
区别只是"最底下还留不留下面那个字的第 0 行"（那是"记录格与下方汉字格几何上重叠 1 行"的固有代价）。

### 5.3 实机菜单导航**仍有偶发漂移**（本轮实测，务必知道）
同一份 nav 前缀（逐行相同）在不同轮里落到了不同页面：
`何为幽灵`（成功）/「选项」/「统计」。这是 round47 记过的"引导时间线漂移 + 按键登记抖动"。
⇒ 结论：**本轮的成功抓帧是真实证据，但"同一条 nav 每次都能到同一页"这件事在本环境不成立**；
需要精确到页时，必须每轮用 `drawlog` 复核并接受重试。

### 5.4 `grid_row_alignment` 的口径
见 2.4 的说明：它是**公式自洽性**检查（工具常量），不是逐盘像素测量。
逐盘证据请引用 2.1 / 2.5。
