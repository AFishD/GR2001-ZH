### 1.2 根因（三选一里选②"写入偏移错"，附可复现证据）

**结论：写入侧的坐标错位（历史遗留），不是 dump/渲染的问题，也不是"回绕列低 1 行"这条本身。**

证据链（全部可复现）：

1. **上 15 行与 16px 模板逐像素完全一致**（`前15行不符 = 0`，吻合墨点数 = 字形的全部墨点）。
   ⇒ 不是整体位移、不是列错位、不是"渲染只画了 15 行"；就是**少了一行像素**。
2. **按位图全盘搜索，把源头追到 4 个版本之前**：
   把 孙/宁/宇 的 15 行特征块在**历次构筑的图集**里滑窗匹配，命中位置是：

   | 盘 | 孙 | 宁 | 宇 |
   |---|---|---|---|
   | GR_ZH91 / GR_ZH92 / GR_ZH93 | (976, **369**) | (992, **369**) | (1008, **369**) |
   | GR_ZH94 | (496, **370**) | (512, **370**) | (528, **370**) |
   | GR_ZH95 / GR_ZH97 | (528,370) | (544,370) | (560,370) |
   | GR_ZH98 / GR_ZH99 | 已被回收清空（0 处命中） | | |

   即：**在 GR_ZH93 及更早，这些字形被写在"引擎采样窗高 1 行"的位置上**（y=369，
   而引擎采样窗在 y=370）—— 正是 round41..44 记录的**写入侧相位错位**
   （历史补丁按 flat 口径写；row 20 的 16 行跨过容器第 384 行的**分段边界**，
   该字形的最后一行被推到采样窗之外）。
   实算：GR_ZH93 上 y=369 那一格对应容器里的旧相位偏移，跨过 384 行后
   `x_engine = x_raw + 448 − 96 = x_raw + 352` ⇒ 最后一行落到窗口左边 96 texel 处，
   **永远采不到**。
3. **缺陷是 round45 的"字形重排"固化下来的**：`patch_zh94_glyph_align.py` 把行 19..24 的字形
   从旧位置搬到 `(16*col, yrow)`，搬的是**引擎窗口里已经只有 15 行的那块像素** ⇒
   少的那一行被"原样"搬过去，从此留在盘上。
4. **不是 round46 的紧凑重排造成的**：GR_ZH94（重排**前**）上这 7 个字已经是同一份 15 行位图，
   与 GR_ZH95/GR_ZH97 **逐像素相同**（墨点数 47/68/71/95/54/40/55 完全一致）。
5. **也解释了"为什么只有这 7 个"**：这一片里只有 **grid 行 20** 的 16 行（y=370..385）
   跨过容器第 384 行的段边界；同片其它行（19/21/22/23/24）不跨，所以只有行 20 中
   "模板最后一行本来有墨"的那几个字遭殃。行 19 的 3 个字则是"整体偏下 1 行"，
   顶行被推出窗外 —— 同一个错位家族的另一面。

* 这 10 个字在**现役盘上已经不存在**（GR_ZH98 把它们当"死字"回收并擦白，
  它们的像素现在不被任何采样窗引用）⇒ 盘上**没有可修的截断**。

### 1.4 加固"错字检测"（用户点名的那条）

老判据（`tcslib.GlyphCache._check_record`）是**容差窗**：只要
「记录矩形 / 矩形+(4,2) / 矩形±(4,2)」三处**任一有墨**就算"画得出来" ——
round46 那 6 个**完全空白**的字就是被这圈邻域墨"蒙"过去的，而"少一行"它更是永远发现不了。

新判据（`tools/iso_build/glyph_geometry.py`）**全部是结构性的**（`geometry.rules` 里有全文）：

| 判据 | 含义 | 级别 |
|---|---|---|
| `empty` | 窗内一个墨点都没有 | **错误** |
| `ink_out` | 窗内触边 **且** 窗外紧邻有"无主墨"（不属于任何采样窗） | **错误** |
| `tpl_lost_rows` | **★ 与 16px 模板逐像素比对**：模板有墨的整行在盘上全空 | **错误** |
| `row_shift` | 字形整体错位若干行（错位把最下/最上的行推出窗外） | 警告 |
| `tpl_miss` / `tpl_extra` | 与模板的差异像素（紧阈值 `TPL_TOL=0`） | 警告 |
| `sparse` | 墨点 < 4 | 警告 |
| `touch_left/right/top/bottom` | 墨贴到窗边界（像素字库里正常，模板能证清白就只算提示） | 提示 |

* 模板 = `third_party/fonts/方正像素16.ttf` 的 16px em 窗（`a[8:24, 8:24] < 128`），
  与 `gen_font16.py::render16()` **同一配方** —— 盘上字形本就该等于它。
* 实测信噪比：GR_ZH98/99 上 1175 个字里只有 **2 个**（验 / 骚）与模板差 1~3 px
  （渲染器微差），其余 **1173 个 0 差异**；空白/越窗 **0**。
* 顺手订正一个会**假报**的口径：引擎采样窗**紧挨着铺满**图集（col 与 col+1 相邻、
  行与行之间是下一行的字形）⇒ "窗外有墨"本身毫无意义（实测 GR_ZH98 假报 1019 个）。
  现在只看"窗外那一像素**不被任何采样窗覆盖**"的真越界（GR_ZH98/99 = 0 个）。
* 也顺手订正：**38 条空 FT 记录全部有正当理由**（空格 / 未分配 0x7F / 0xA1..0xAD 是对偶 lead /
  0xB1 0xB5 是图标码 / 其它 face 不参与显示）⇒ 报告里单列一张"为什么不算坏"的表；
  只有「default face + 可打印 ASCII 或 charset 真有映射的单字节码」为空才报**错误**。

## 2. 用户第二诉求：锚点换成通用不变量

### 2.1 原来错在哪

`tools/text_csv/tcslib.py::selfcheck_charset` 里曾**写死**：

```python
t, _ = cs.decode(bytes.fromhex('af a1 bd'))
_exp = cs.pair_of.get((0xAF, 0xA1))
chk(t == ((_exp or '?') + cs.codes.get(0xBD, '?')), 'AF A1 BD → …')
```

它假设 `(0xAF,0xA1)` 一定是合法对偶码。字库**紧凑重排**（`tools/iso_build/repack_font.py`，
round46 起每轮构筑默认开）会按"当前槽位升序"**机器重新分配全部对偶码**
（GR_ZH95 那一轮就改了 636 个字），任何一个具体码位随时会变。

**这不是理论风险 —— 现役 charset 上它已经失败**：`弗` 原为 `AFA1`、重排后是 `AEE1`，
所以 `cs.pair_of[(0xAF,0xA1)]` 现在是 `None`，`AF A1 BD` 解出来是三个私有区回落字符。
round49 因此只能给构筑加 `--no-font-repack`（"重排后 dump_text_csv 直接拒绝出表"）。

### 2.2 改法（删掉这一处硬编码，换成 4 条通用不变量）

1. **全码位「编码→解码」逐字节自洽**
   `encode_strict(ch) == bytes(code)` 且 `decode(bytes(code))[0] == ch`
   —— 单字节 110 个 + 对偶 1175 个（死 pair 另由下一条把关）。
2. **对偶 lead 必须落在 `[0xA1, 0xB1)`**（原有 `bad` 检查保留）。
3. **单字节码不与任何对偶 lead 撞车**
   （撞了编码器就会写出 1 字节的"半个对偶码"）。
4. **动态锚点 —— 「对偶优先」的通用版**（= 旧 `AF A1 BD` 的推广）：
   从**本盘实际在用**的对偶码里取槽位最小/最大的各 1 个，配上单字节码里最小/最大的各 1 个，
   断言 `decode(bytes(pair) + bytes(single)) == pairchar + singlechar` 且字节边界是 `[0,2]`。
   现役盘实测：

   ```
   [ok] 对偶优先: '区'(a1 a1) + '《'(80) = [a1 a1 80] 解码 '区《' (字节边界 [0, 2])
   [ok] 对偶优先: '齐'(ae bd) + '著'(FF) = [ae bd ff] 解码 '齐著' (字节边界 [0, 2])
   ```
5. `ANCHORS_LANG` / `ANCHORS_XML`（正文锚点，如 `G058.I192 = 'A组'`）**原样保留** ——
   那是"容器正文对不对"的核对，与 charset 硬编码是两回事（且已有
   `MUTABLE_TEXT_ANCHORS` 机制把"翻译更新"降级成告警）。

`selfcheck_charset` 现在共 36 条断言，全 `[ok]`。

## 3. 用户第三诉求：`±` 与整体占位符逻辑

### 3.1 `±` 的结论：**真字，不是占位符**

| 证据 | 内容 |
|---|---|
| **英文原盘原文**（独立读取路径 `tcslib.en_read_tables` + `decode_en`） | `SFXML:T0039` = `… It can determine ranges out to approximately 10,000 meters with an accuracy of **+ or - 10 meters**.` |
| 中文译文（唯一一处用到 `±`） | `SFXML:T0039`「最远测距范围约 10000 米，**测距精度为 ±10 米**。」 |
| 它在 charset 里的形态 | **对偶码 `A4 D4`**（2 字节），走汉字同一条图集路径；全表**无重复映射** |
| 它的字形 | 引擎格 `slot=333 (row5 col23) = (368,82)`，26 个墨点，与 16px 模板**差异 0 像素** |

⇒ `±` 是 `+ or -` 的忠实翻译（数学加減号）。**不该**改成单字节符号：
现役盘 `0x80..0xFF` 里可用字节已经是 **0 个**，放对偶码是零成本拿一个 16×16 符号字形。

### 3.2 整套占位符/图标逻辑

已整理成 **`docs/PLACEHOLDER_AND_SYMBOLS.md`**（一页看完，含码位表与判据表）。要点：

* **手柄按键占位符**：`{{BTN:XXXX}}` ↔ 私有区 `U+E080..U+E0FF`（`XXXX` = 原码位），
  编码成**单字节**。引擎真正认的图标码**只有 2 个**：`0xB1`(△, UV `(25,198)-(45,218)`) /
  `0xB5`(✕, UV `(1,198)-(21,218)`)，硬编码在 `DrawString v1` 里，走另一张贴图 ⇒ **不吃字库**。
  正文用量：**△×7、✕×21**（除这两个之外没有任何其它 `{BTN}` 标记 —— 全表扫过）。
* **`{{BTN:E0E7}}` / `{{BTN:E0F1}}` 是历史别名**：字节 `0xE7`/`0xF1` 其实是拉丁字母 `ç`/`ñ`，
  引擎按普通字母画（round42 定性、round43 进 charset）。新文本请直接写 `ç`/`ñ`。
* **控制标记**：`{br}`（硬换行）/ `{p}`（空行）在盘上是**字面 ASCII**（`7B 62 72 7D` / `7B 70 7D`）；
  `{WRAP}`/`{Warp}`（`text_edited` 列 161 处：`{WRAP}` 7 + `{Warp}` 154）只是
  **作者给人看的标记，盘上永远不会出现**（编码器有硬闸门）。
* **图标码 ≠ 空字节**：`0xB1..0xFF` 里没被占用的字节**不会**自动变成图标码
  （那 2 个 `if` 写死了）。
* **"看起来像符号、其实是真字"清单**：`±`(数学符号) / `®`(注册商标，26 次，出现在
  `PlayStation®2`、`幽灵行动®任务`) / `·`(间隔号) / 全角标点 `，。：；！？、""（）`（对偶码）/
  `《` `》`(单字节 `0x80/0x81`) / `ç` `ñ`(单字节 `0xE7/0xF1`)。

### 4.3 ★ 新发现：紧凑重排会改变画面（doc 页标题变错字）

实机 A/B（同一份 nav、记忆卡每轮模板复位、单实例、按键 `tap`+紧跟 `release`(fr+2) 短按）：

| nav | 覆盖画面 | repack-ON GR_ZH99 vs GR_ZH98 | round49 基线（GR_ZH97 vs GR_ZH98，**没开重排**） |
|---|---|---|---|
| menu | 载入屏 / 选择文件 / 主菜单 | 122 / 127 帧相同 | **127 / 127 全等** |
| weapon | 主菜单 / 特别收录 / 武器详情页 / 滚动箭头 | 297 / 302 帧相同 | **302 / 302 全等** |
| doc | 长文页（何为幽灵） | 265 / 299 帧相同 | **299 / 299 全等** |

* round49 的基线证明**抓帧是确定性的**（同口径、同模拟器、不同盘也能 100% 全等）
  ⇒ 这 5 / 5 / 34 帧差异**不是噪声**。
* doc 的差异**全部集中在一处静止元素**：特别收录「背景 → 何为幽灵？」那页的**标题条**
  （47×15 px @ (285,80)）：GR_ZH98 画「何为**幽灵？**」，repack-ON 的 GR_ZH99 画「何为**强知营**」
  —— **肉眼可见的错字**。证据图：`<版本>/temp/verify/repackON/ab_zoom_doc_wide.png`。
* menu/weapon 的 5 帧差异都在**引导/载入阶段**（f1300~f1900，其中 f1900 整屏 maxΔ≤8 = 淡入相位），
  三组 nav 的差异像素数完全一致（304 / 254771）⇒ 同样是系统性的。
* 已核实的事实：盘上 **charset ↔ 图集自洽**（ZH99 里 `A6A6`=幽 且图集该格就是幽的位图，
  与 16px 模板差异 0；`±`/`®` 等亦然）。
  运行期画出的字形却落在**相邻 +1 格**（`A6A6`→画成 `A6A7`=强，`A5CE`→画成 `A5CF`=知）。
  **最合理的解释**：盘上存在**注入容器之外**的中文文本源，它仍带**旧码位**；
  重排把码位整体改了，这些文本就"指到别人的字形"上了。
  （drawlog 在标题那一处给出的是**新码位**，与这条推断不完全吻合 ⇒ **机理待专门追查**，
  我已把 drawlog、图集、码位表、复现脚本都留在 `<版本>/temp/verify/repackON/`。）
