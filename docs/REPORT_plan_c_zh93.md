## 二、为什么是「方案 C 最小步 0xB1」，而不是历史版的 0xB4

历史先例（提交 `eebe52ef`，`patch_zh220_planc.py`）把 gate 从 `0xAE` 抬到 **`0xB4`**
（lead `0xA1..0xB3`），代价是必须把落在新 lead 区间里的 **5 个单字节码**
（`的 0xAF`、`你 0xB0`、`键 0xB2`、`练 0xB3`、图标 `0xB1`）**1B→1B 搬到 `0x7F..0x83`**。

本盘做不到这一步，原因有两条硬约束（都已实测）：

1. **没有空闲单字节码可搬**：`0x80..0xA0 / 0x92 / 0xAE / 0xFF` 已被上一轮 57 字扩容占满，
   全码位普查（`work/_planc/m25_usage.py`）显示 **111 个单字节码全部至少用过 1 次**，
   唯一空闲的 4 个（`0xB1 0xB5 0xE7 0xF1`）正是用户译文里的**手柄图标码**
   （`{{BTN:E0B1}}`×7 / `E0B5`×21 / `E0E7`×1 / `E0F1`×1，引擎直接拿字节画图标，**动不得**）。
2. **把 `的/你` 搬成 2 字节对偶码是可行的**（语言表压缩余量 15127 B，实测），
   但**不能再往上抬**：一旦 lead 覆盖到 `0xB1`，图标码就会被吞掉。

⇒ 本轮取**恰好停在图标码之前**的上界：

```
gate:  4 处 ELF `sltiu ...,0xAE`  →  `0xB1`
       0x416EE8 (ds16 cave 字节→对偶判定)   0x417160 (StringWidth lead 判定)
       0x41751C (DoWordWrap 逐字)          0x5656A4 (SWKERN 字形计数)
lead:  0xA1..0xB0（+282 码位：lead 0xAE / 0xAF / 0xB0）
```

**副作用（白捡的容量）**：lead `0xAE..0xB0` 里原本有 101 个「死 pair」（偶像/人名等闲置字，
其中含用户译文实际用到的 `志`=`AFA5`、`略`=`AFEC`），它们在新上界下**自动变成合法码位**，
而它们的字形**本来就已经画在图集里**（逐字模板匹配 0 误差）⇒ 上一轮因为「引擎读不到」而
被迫做等价替代的 `志/略` 这两个字，本轮**原样回归**。

**全 ELF 扫描确认**：`sltiu …,0xAE` 只有这 4 处（`work/_planc/m23_scan_gates.py`），
其余 `0xA1`/`0xFF` 立即数是下界与 trail 上界检查，保持不动。

## 三、引擎采样规则（本轮重新实证，两处旧口径被纠正）

### 3.1 对偶（pair）

```
slot = (lead-0xA1)*94 + (trail-0xA1) ; row = slot/62 ; col = slot%62
引擎格 x = 16 * ((col + PHI[row]) % 64)     y = yrow(row) = 2 + 16*(row + 3*[row>=12])
PHI = 行0-3:6  行4-7:12  行8-11:18  行12:24  行13-16:30  行17-18:36  行19-23:2
```

证据：把现役图集按 `方正像素16.ttf` 16px 模板与 1297 个对偶字逐点比对
（`work/_planc/m20_judge.py`）：

| 候选公式 | mismatch=0 的字数 |
|---|---|
| `x = 16*col`（ELF cctc cave 直接读到的 U0） | **0 / 1297** |
| `x = 16*((col+PHI[row]) % 64)` | **785 / 1297**（行 19..23 全部 100%：27/27、31/31、52/52、24/24） |

⇒ 图集行存在**逐行整体相位**（成因是历史各轮对图集做的行移位/重铺），
ELF 侧的 `cctc cave`（`0x417050`）算的是 `U0=16*col`，两者靠图集数据本身对齐。
**旧口径 `tcslib.atlas_cell_xy()`（`x = 4+16c`）与本盘实际不符**，本轮**未改**它
（只改与 lead 上界有关的常量），但落点一律按上式写、并额外在 `4+16c` 处补一份拷贝给预检看。

### 3.2 单字节码（记录 `(u0,v0)`）

```
引擎采样 = ((u0 + 16*PHI[row(v0)]), v0 + 1)
```

- `的 0xAF`：记录 `(16,178)` → `16 + 16*18 = 304` ⇒ 图集里 `的` 的字形正好在 `(304,178)` ✓
- `务 0xC9`：记录 `(704,338)`（row 18，PHI=36）→ `704+576 = 1280 → 256` ⇒ 与历史上
  「实机探针涂 (256,338) 使『务』变实心块」一致 ✓
- **旧文档里的「恒定 +576」只是 row 18/19 的巧合**（row 18 的 16×PHI 恰为 576）。

### 3.3 写入安全判据（本轮新增）

> 写入框（16×16）必须与**全部活字形采样窗**零交叠 —— 不只是「不覆盖活墨」。
> 因为即便别人的采样窗那一小块是空白，**我写进去的墨也会出现在那个字的渲染里**。

活窗集合 = 全部**渲染得到**的对偶格（1300 个字）∪ 三个 face 的**记录采样窗**
（ASCII + 单字节，544 条）。据此普查新 lead 空间（行 19..24，空闲槽 132 个），
**严格干净（零交叠）的槽有 67 个**，从中选 17 个。

## 五、★ 最容易踩的坑：**旧编码的文本必须整体重编码**

`inject_text_csv.py` 有一条设计上的优化（`inject_text_csv.py:998`）：

```
if cell == r['text_zh']:      # 「没人工改过」的行
    stats['skipped_untouched'] += 1
    continue                  # ← 一个字节都不写
```

「dump 后不改动 = 产物与基底 sha256 完全相同」在**只增码位**的轮次里是对的，
但**本轮把 `的/你/荐` 从单字节码改成了对偶码** ⇒ 盘上凡是没被改过的行，
仍然保存着旧的 1 字节 `的(0xAF)` / `你(0xB0)`；而在新 gate 下这两个字节**是 lead**，
引擎会把 `0xAF xx` 当成一个对偶码读 ⇒ **整段乱码 + 吞掉后一个字**。

实测证据（`work/_planc/v3_diag.py`，同一行 `LANG G007.I006`）：

| 盘 | 字节片段 | 用新 charset 解码 |
|---|---|---|
| 只跑了一般的注入 | `… a8 ae **af c5** a1 bd …` | 「…最长**虽方**获胜。」❌ |
| 强制重编码后 | `… a8 ae **a8 ba** c5 a1 bd …` | 「…最长**的一方**获胜。」✅ |

**解决**：`work/_planc/make_reencode_tables.py` 生成一份表副本，
**只把 `text_zh` 列清空**（译文 `text_edited` 一个字都不动）⇒ 注入器认为每行都「被改过」
⇒ 2250 行全部按新 charset 重编码写盘。实测：候选 2261 行、实际改动 435 行、
与源盘等价跳过 1826 行，容器展开长度不变（多出的字节从容器原有零填充里吃，余量充足）。

> ⚠ **给后续轮次的硬提醒**：只要动了「字节 ↔ 字符」的映射（不只是新增码位），
> 就必须走这一步，否则盘上旧编码的段落会在新口径下乱码。

## 九、已知限制（**必读**）

1. **lead 上界只到 `0xB0`**：这是被「图标码 `0xB1` 不能当 lead」和「没有空闲单字节码可搬」
   两条约束卡住的**本盘上限**。再往上扩（历史版的 `0xB1..0xB3`）需要先腾出至少 1 个
   位于 `0xB1..0xFE` 的空闲单字节码。
2. **`的`/`你` 变成 2 字节码**：盘上这两个字每次出现多占 1 字节，语言表展开长度不变，
   但**压缩后体积上升**（本次从容器零填充里吃掉了约 2.7 KB）。若将来要再改文本很多，
   请先复核语言表余量（现约 15 KB 压缩余量 / 128545 B 展开）。
3. **旧盘文本必须用旧 charset 读**：本轮改了 `0xAE..0xB0` 的语义，
   `work/_planc/charset_before_planc.json` 是改动前的字符表（读 `GR_ZH92`/`GR_ZH91` 等旧盘用它）。
   用新 charset 去 dump 旧盘，`的/你` 会解错。
4. **17 个新字形占了行 21 的格子**：那里原本是**旧世代 EN 小写带的残墨**（不被任何 FT 记录采样，
   实测无活窗交叠）。若将来重铺 EN 带，需要避开这 17 格（坐标见 §四）。
5. **tcs 预检口径未改**：`tcslib.atlas_cell_xy()` 仍是 `x = 4+16c`（与本盘实际相位不符，属历史遗留）。
   本轮的落点因此**双写**（引擎格 + tcs 格），除了 `钢/题` 两格（tcs 格有活字，只写引擎格）。
   `dump_font.py` 报的 `has_glyph` 是按 tcs 格判的，对这些字属于「有墨即通过」的弱判据。
6. **`dump_text_csv.py` 有个既有 bug**（非本轮引入，但挡住了 `make_build` 的「版本文本副本」步骤）：
   `tools/text_csv/dump_text_csv.py:575` 把变量 `marks` 覆写成 `wrap_hint_cell()` 返回的
   **位置列表（int）**，到 `:607` 的 `' '.join(marks)` 抛 `TypeError`。
   触发条件：某条 SFXML 文本**既是长段（wrapW>0）又含图标标记**。
   本轮因此用 `--no-text-snapshot` 构筑（**ISO 不受影响**）；一行改名即可修好。
