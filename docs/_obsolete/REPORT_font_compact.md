## 1. 为什么要重写（不是"想换个写法"）

旧工具 `repack_font.py` 的**搬字逻辑是对的**（封包感知读写、确定性顺序、幂等、写盘前自检），
但它的**重编码只覆盖"可注入文本表"** ⇒ round51 由 `repack_leak_scan.py` 查实：

| | 内容 |
|---|---|
| 重排会改的 | ① charset JSON 的 `pair_of`（逐字换码位）② 图集像素 ③ 把可注入文本表拷成"强制重编码"副本 |
| **会被重编码的文本** | `EN_STRINGS.RES`（2 份副本：MENU.IMG#25 / GR.IMG#902）+ `EN_SPECIAL_FEATURE.XML`（MENU.IMG#283，且**只重写 `<text>` 元素**） |
| **漏掉的** | ★ **SFXML 的 `<item name="…">` / `<group name="…">` 属性** —— 「特别收录」的中文标题就在这儿（145 个 `name` 属性 / 123 个含中文）；`dump_text_csv` 只抓 `<text>` 元素，属性从来没进过表 |

后果（round50 实机可见）：标题条被画成「何为**强知营**」。机理：**字节没变、charset 变了** ⇒ 旧码位指到别人的字形上。
round51 用「重排前 charset + 搬运表」把 123 个中文属性里 **113 个**复现成别的字（`何为幽灵？`→`何为幽灵；`）。

⇒ 本轮重写 = **把重编码覆盖面补全**，并加一道「漏一个容器就出事」的硬门禁。

## 2. 搬字规则（确定性、幂等）

1. **口径全部复用 `repack_font`**（round46 起已在实机跑通，不重写、不复制，直接 `import`）：
   * 引擎采样格 `slot=(lead-0xA1)*94+(trail-0xA1); row=slot//62; col=slot%62; x=16*col; y=2+16*(row+3*[row≥12])`
     （`tcslib.atlas_cell_xy_engine_view`，无相位）；
   * 像素容器是 **GIF 封包流**，读写一律按 `tcslib.atlas_container_segments()` 的**数据区**偏移，**绝不碰 48B 包头**；
   * **可用格** = 1504 − 被单字节/图标记录码占死的格 − 被 FT 记录矩形（别人的采样窗）压着的格；
     `GR_ZH105` 实测 = 1504 − 51 = **1453**（`ft_rect` = 0，因为 round54 已把 84 条记录搬出网格）。
2. **顺序** = 按**当前槽位升序**（= 图集行主序），同槽按码点 ⇒ 第 *i* 个字 → 第 *i* 个可用格
   ⇒ 因为槽位号本身就是行主序，重排后顺序不变 ⇒ **再跑一次是 0 改动**。
3. **清零**：全部可用格先清零，再逐字写入新格，最后 `protect`（FT 记录矩形）说了算 ⇒
   未使用区域的残留墨一并清掉。
4. **只改像素容器数据区**：48B 包头逐字节不动、容器外（COMMON.PAK 其它记录 / FONT.RES）**零改动**。
5. **布局断言（本轮新增，写盘前 + 门禁各一次）**：
   * 硬：`max(在用 slot) < min(空闲 slot)`（否则**拒绝写盘**：几何上做不到"可用格全在最末端"）；
   * 报告 + 门禁：`在用 == slot 0..N-1`（`used_prefix_ok`）且 `空闲 == slot N..1503`（`free_tail_ok`）。

`GR_ZH105` 实测：**搬 1039 字、原地不动 136 字、改码位 1039 个、清空可用格 278 个、像素改动 95 472 nibble**；
图集总墨点 89 518 → 89 518（**一个墨点都没丢**）。

## 4. 全盘扫描兜底 + 「真文本 vs 二进制巧合」判据（★ 本轮最关键的口径）

### 4.1 口径（三档）

1. **候选段**：按"肯定不是文本"的字节（控制字符 / C1 区 `0x7F..0x9F`）切段，
   段内再用**引擎同款 greedy 解析**（`<0x80`=ASCII、对偶优先、单字节码、其余回落 PUA 即断）
   ⇒ 取"干净（无回落字节）且**连续 ≥4 个汉字**"的段 —— 就是用户口径的"用旧 charset 能解出连续中文的字节串"。
   预处理用 numpy 先筛"含 ≥4 个连续高位字节"的区间（真中文的必要条件），1.6 GB 从小时级降到分钟级。
2. **"真文本"判据**（标定过的，见 4.2）：
   `最长汉字串 ≥6` 且 `汉字数 ≥16` 且 `不同汉字 ≥10` 且 **`对偶码汉字占比 ≥0.50`**。
3. **改写范围**：落在**已知文本容器**（SFXML + LANG×2）里的段随容器整块重映射；
   落在**别的"真文本"容器**里的段 ⇒ 走**通用容器重写**（展开→逐字重映射→重压≤槽）；
   落在 **IMG 之外非压缩区**的"真文本"段 ⇒ **原位重映射**（同长度覆盖）；
   其余判为**巧合** ⇒ 不改、逐项计数进报告。
   **任何一段"真文本"没能被改写 ⇒ 立即中止、不写盘**（`plan_reencode()` 里就拦，写盘之前）。

## 8. 已知限制（如实说明）

1. **门禁的域不是"ISO 的每一个字节"**，而是"**判为真文本的段** + **全部被重写容器的整块**"。
   原因：二进制资产里有 **1110 万段**"干净 ≥4 连续汉字"的巧合（压缩数据/纹理/视频/音频），
   逐段重编码会把游戏数据改坏，且与验收条件"差异只落在文本容器、#551..#565 差异 0"直接冲突。
   判据经过标定（§4.2），在现役盘上**只**选出 3 个已知文本容器、零误报；判为巧合的段**逐项计数进报告**，不隐藏。
2. **短文本盲区**：若某个**未知**容器里只有很短的陈旧中文（单个 2~5 字标签、周围全是二进制），
   本判据可能判为巧合而跳过（阈值：最长汉字串 ≥6 且汉字数 ≥16 且不同汉字 ≥10 且对偶码占比 ≥0.5）。
   缓解：① **文本类扩展名**（`.XML/.TXT/.MIS/.ATR/.RES`）的容器**全部**被展开扫描，且"真文本必须已重写"一条不放；
   ② `plan_reencode()` 对**任何**未覆盖的真文本段**立即中止**；③ 报告里有逐容器 top-40 与前 5 个例子。
3. **51 个记录码格**：`repack_font` 的 `ATLAS_ENGINE_SINGLE_CELLS`（行 19 col 0..33 / 行 24 col 0..5,12 /
   行 21,22 col 5..8 / 行 23 col 8,9）是**硬编码**保护表，本工具保守地把它们算作"不可用" ⇒
   本工具口径 **可用格 278**，而 `font_cell_map` 的口径给出 **可用 329**
   （round54 已把 84 条记录搬出网格，这些格现在是空白且无记录矩形压着）。
   两者**不矛盾**：用户看到的"可用 329"是 `font_cell_map` 的口径，且这 329 格**全在 slot 1175..1503** ✓；
   本工具口径留了 51 格余量（将来加字只会用 278 个里的空位，顺序仍是从 slot 1175 起往尾部排）。
4. **不改文本内容，只换码**：`text_edited` 一字不动；若某份 `--inject-csv` 表与盘上现值逐行相同，
   注入器会跳过（0 改动）—— 这是设计行为（**本轮 GR_ZH106 正是如此**），
   盘上文本靠 §3 的**容器级重映射**保持一致，不依赖注入器是否回写。
5. **耗时**：真实跑一轮约 **6~7 分钟**（全盘原始扫描 ~100 s + 4690 个容器展开扫描 ~210 s + 写盘/门禁 ~60 s）；
   `--dry-run` 只算搬字（~2 s，不做扫描）。
6. charset JSON 里**旧字段 `_font_repack` 保留**（里面是上一轮的旧戳），本轮的新戳写进 `_font_compact`；
   人工单跑看到"charset 记录的盘不是本盘"的提示时，**以 `_font_compact.iso_sha256` 为准**。
7. **单字节「死 pair」顺带收敛（本轮实测到的一个重要副作用）**：
   `GR_ZH105` 的 charset 里有 **37 个**对偶字的 lead ≥ 0xAE（`志略齐坐款""扳倍宾偏挂栓泛箱聚链震延普虽螺衍衣裂誉贡轮迟造钢题额鼓（）荐`），
   旧 slot 1222..1402 —— 而 tcslib 记的引擎 DBCS 判据是 `sltiu lead,0xAE`（lead ≥ 0xAE 会被读成两个单字节，
   即所谓"死 pair"）。这 37 个字里 **36 个在正文里用到，合计 67 字次**。
   本轮的布局把所有在用字压到 **slot 0..1174（lead = 0xA1..0xAD）** ⇒ 这 37 个字现在落在 **slot 1138..1174**，
   实测 `pair_of` 里 **lead ≥ 0xAE 的条目：37 → 0 个**（旧 `charset_before_r56.json` 37 / 新 `charset_compiled_zh16.json` 0）
   ⇒ 若那条引擎判据成立，这 67 处文字在 GR_ZH106 上会**从"两个怪字"变成正确汉字**（改善，但与 GR_ZH105 有肉眼可见差异）；
   若判据不成立（引擎其实接受 lead≥0xAE），则两边一样。**这一条机器判不了，必须实机 A/B**（见 §9）。
8. **一个工具口径的小差别（不影响验收）**：本工具的"可用格"= 1453（排除 51 个硬编码记录码格），
   `font_cell_map` 的"可用" = 329（按实测：空白 + 无记录矩形压着）。两者的**在用/空闲槽位结论完全一致**（§6.1）。
