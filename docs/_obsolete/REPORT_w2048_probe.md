## 0. 一句话结论

**❌ 判据全不过 ⇒「图集变大被引擎挡住」被确证**：以 `GR_ZH123.iso`（实机已证 ✓）为基底，
**只把图集 w 1024→2048（h 一字不动）**，裸跑 6000 帧 **0 张截图 / needle `newfontrevisedrs` 0 命中 /
`TLB Miss` 0** —— 与基线（**191 张 / 2873 命中**）对比是**黑屏**。引擎**没有崩**（6000 帧跑满、
无 TLB、EE 仍在跑），**卡在读字库容器这一段**：全盘最后一次读盘停在 **LBA 776,669**
（新容器区 776,463..776,718 的中段），此后 ~5000 帧**零读盘**、GS 只剩启动期那点工作量。

**同时排除了"是我构筑方式的问题"**：一个**只长大、图集一个字节不动**的对照盘
（同样 +262,144、同样 682 条 off 平移、同样 ISO 加长 84 扇区）**跑出 191 张截图 / 2872 命中 ✓**。
⇒ 起作用的唯一变量就是**图集/容器的变大**本身。

## 1. 唯一变量与配方

```
基底 = work\builds\GR_ZH123\GR_ZH123.iso        (1,648,164,864 B = 804,768 扇区)
加上 = w 1024 → 2048（h 512 不变）所必然连带的机械项（px_size / 容器重切）
```

| # | 位置（记录内） | 位置（PAK / IMG） | 位置（ISO 绝对） | 前 → 后 |
|---|---|---|---|---|
| ① | `+0x01C` **w** | `PAK+0x104D` | `0x5EC8744D` | `1024 (0x400)` → **`2048 (0x800)`** |
| ② | `+0x438` **px_size** | `PAK+0x1469` | `0x5EC87869` | `0x40010 (262,160)` → **`0x80010 (524,304)`** |
| ③ | `+0x43C` **容器** | `PAK+0x146D` | `0x5EC8786D` | 8 段 262,160 B → **16 段 524,304 B** |
| ④ | `+0x020` **h** | `PAK+0x1051` | `0x5EC87451` | **`0x00000200` → `0x00000200`（一字节不动 ✓ 回读断言 `[A4]`）** |
| ⑤ | `+0x000/+0x008..0x017` 记录头与名字 | — | — | 未动（`[A4]` 逐字节回读） |
| ⑥ | `+0x024` clut_size + `+0x028..0x437` 调色板 1040 B | — | — | 未动（`[A4]` 逐字节回读） |

**连带的机械项（不是第二个变量）**

| # | 位置 | 前 → 后 |
|---|---|---|
| ⑦ | COMMON.PAK `stored`（条目 #3 的 `+24` 字段 @`IMG+0x8D8`） | `400,659` → **`662,803`**（+262,144） |
| ⑧ | 682 条 `off` 字段（`off ≥ 0xB9120` 的条目，@`IMG+0x830+48i+32`） | 各 **+262,144**（例：FONT.RES `0xB9120` → `0xF9120`） |
| ⑨ | MENU.IMG 头 `size`（@IMG+0）＋ ISO9660 目录记录 data length（@`0x828D8` 小端 / `0x828DC` 大端） | `58,300,882` → **`58,503,168`**（28,566 扇区，**扇区对齐**） |
| ⑩ | PVD `volume space size`（@`0x8050` 小端 / `0x8054` 大端） | `804,768` → **`804,852`** 扇区 |
| ⑪ | ISO 文件本身 | `1,648,164,864` → **`1,648,336,896` B（+172,032 = +84 扇区）** |

> **⑪ 为什么必须加长 ISO（算术，不是选择）**：现盘可用连续空位只有
> **61,236 B（IMG 声明尾料，实测 100% 为 0）+ 30,254 B（IMG 声明尾 → 卷尾）= 89,908 B**，
> 而本次 Δ = 262,144 B ⇒ 差 **170,654 B**；把 MENU.IMG 声明长度做成扇区对齐后
> 需要 28,566 扇区、卷只到 28,482 ⇒ **必须追加 84 扇区**。
> **GA 对照盘（§3）用同一套 ⑦..⑪ 机制跑通 ⇒ 这条机制已被证明无罪。**

**新容器口径（严格沿用现役"alloc = 图像 + 16"铁律，与配方给的 `0x80010` 一致）**

```
16 段 × 48 B 头 + 像素区 523,520 B + 16 B 尾 no-op = 524,304 B = 0x80010   ✓
  · 段 k 的 A+D 行号 = 32k（0,32,64,…,480；0x8000 B = 32 行 × 1024 B/行）
  · 段 k 的 IMAGE NLOOP = 0x800（32,768 B）；末段 = 0x7D0（32,000 B = 31.25 行）
  · 行 0..510 的 x<1024 部分**逐字节复制现役**；x≥1024 全填 `0x11`（现役空区口径，已核对）
  · 覆盖率 = 511.25 行，与现役 8 段的 511.25 行**完全相同**（段头同样从像素区里挤出来）
  · 配方里的 "16*(48+32768)+16 = 524,304" 算术上等于 525,072；我按配方同时给出的
    `px_size = 0x80010 = 图像 + 16` 落盘（与现役 8 段容器同构），回读 `[A2]` 16 段/524,304 ✓
```

## 5. 结论

1. **W=2048 不可行（本口径下）**：只改图集宽度（h 不动）就已经把引擎挡在 UI 之前，
   连字库容器的读取都没走完。**"图集可以变大"这条路在 W 方向同样不通** ——
   与 h 方向（h=640/1024）看到的是**同一堵墙**：**容器 / `px_size` 变大本身**。
2. **不是 W 特有的算术问题**：`0x80010` 与加载器的分块账**不冲突**
   （W=2048 ⇒ B′=0x40000/2048=128、单元 144、`c·u − P = 0` 恰好整除，落在报告 §4.1 的"安全"集合里），
   所以失败**不能用分块账解释**，只能是引擎侧的尺寸/容器处理。
3. **h 一个字节都没动**（`[A4]` 回读 `00 02 00 00`）、调色板/名字/记录条数/FONT.RES/ELF/charset/文本
   全未触碰；名字区与 4096 槽哈希表逐字节不变（`[A7]`）。
4. ⇒ **本轮的答案交给下一轮**：364 个缺字**不能**靠"把图集加宽到 2048"解决；
   若仍要在 h=512 内解决容量，只能走**码位/格位空间**那条线（cave gap 3→0 ⇒ 31 行，
   或压缩 ASCII 带宽），**不是**图集尺寸那条线。
