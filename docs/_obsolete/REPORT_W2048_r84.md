### 2.1 没动的东西（逐字节验证）

```
✓ h  = 512                       （任务书禁令；本次一个字节都没动）
✓ FONT.RES 槽 4421 B             （逐字节不变，已 assert）
✓ ELF                            （一个字节都没动）
✓ charset / 文本                 （一个字节都没动）
✓ 名字区 11,542 B                （逐字节不变，已 assert）
✓ 4096 槽哈希表 16,384 B          （逐字节不变，已 assert）
✓ 容器段数 8                     （★ 没改成 16 —— 见 §2.2）
```

### 2.2 ★ 与 Lead 配方的一处偏离（省了 262,160 B）

Lead 配方写「容器段数 **8 → 16**（每段 48 B 头 + 0x8000 数据）」。
但 2048 宽下**每行是 1024 B**，一段 64 行 = 65,536 B，**8 段就够覆盖 512 行**：

```
2048 × 512 @4bpp = 524,288 B = 8 段 × 65,536 B      ← 8 段刚好
```
⇒ 保持 8 段、只把**每段数据翻倍**，容器 = 524,688 B。
若按 16 段（每段 0x8000）则 = 525,072 B（多 384 B 头），**且行映射会错位**。
两种都试算过，**8 段是对的**（`zx_r84_layout` 不涉及；见 `zx_r84_w2048.py` 内注释）。

### 2.3 ★ 容器逐 texel 正确性（写盘前已验证）

```
[A8] 新容器左半 (x=0..1023) 逐 texel == 旧容器 : True ✓
     右半 (x=1024..2047) 全空                  : True ✓
     seg0..7 首行 = 0/64/128/192/256/320/384/448 ; SSAY 与旧盘一致 ✓
     IMG nloop = 4096 (= 65536/16) 与解析器口径一致 ✓
```
⇒ **纹理内容本身没有问题**：像素口径、段表、GIFTAG 全部自洽。
⇒ 黑屏**不是**容器构造错误，而是**引擎不接受这个尺寸**。

## 5. ⇒ 对「完全扩容不缺字」的最终裁定

```
假说「黑屏主因是容器/px_size 变大」      → ★ 本实验正面确证 ✓
   · GR_ZH123（容器不动）        → 通 ✓
   · GR_TEST_W2048b（只动容器宽） → 黑 ✗  ← 本次

   · H640 / H640B / H1024 / GR_ZH121（h+容器同时变） → 黑
   · **W2048（只容器变，h 不动）                     → 黑**  ← 关键单变量
```
