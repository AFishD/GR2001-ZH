分支 `round61/hook-nav` · 执行者 = 模拟器钩子/闭环导航子代理 · 2026-10-13

> **一句话**: 给自定义 gsrunner 加了**两个运行时开关** —— `-grmemwatch`(按帧输出指定 EE RAM
> 区间, 外部进程可实时 tail) 与 `-grinputlive`(每帧轮询命令文件, **不重启**注入按键/截图/

### 踩过的三个坑 (都已在源码里修掉, 记下来免得复现)

1. **`OpenCFile` 默认拒绝读共享** —— Python 端 tail `memwatch.bin` 直接 `PermissionError [Errno 13]` (Windows 的 `ERROR_SHARING_VIOLATION`)。改用项目自带的 `OpenSharedCFile(..., DenyNone)`。**这是"内存钩子能不能实时读"的成败点。**
2. **记录头是 12 字节不是 8** —— `[frame][addr][size]` 三个 u32。第一版 Python 按 8 字节步长解析, 读出来的"帧号"其实是地址。
3. **live 读偏移不能用 `ftell`** —— 在"fread 读到 EOF"和"ftell"之间如果驱动脚本追加了字节, 这段新字节会被**永久跳过**(丢命令)。改成按实际读入字节数推进, 未成行的尾巴下次重读。

## 3. 新开关用法

```bash
pcsx2-gsrunner.exe -grdumpdir <dir> \
    -grmemwatch 0x013379D0 4 1  -grmemwatch 0x0091C000 0x6000 1 \
    -grinputlive <命令文件> \
    -grdrawwin 1 1 -grscanframes 1000000 -grsnap 500 -grmaxframes 40000 \
    -grmemcards <dir> -renderer dx11 -- <iso>
```

| 开关 | 语义 |
| --- | --- |
| `-grmemwatch <addr> <size> <interval>` | 每 `interval` 帧把 EE 物理地址 `addr` 起 `size` 字节追加进 `<dumpdir>/memwatch.bin`, 记录 = `[u32 frame][u32 addr][u32 size]` + 数据。**可重复**。文件 `DenyNone` 打开 ⇒ 运行中可被 Python 实时 tail。 |
| `-grinputlive <file>` | 每帧轮询该文件, **新追加的行立即生效, 不重启**。命令: |

live 命令一览:

| 命令 | 效果 |
| --- | --- |
| `<按键> tap` | 短按 —— 按下并在 **3 帧后自动释放** (帧率同步的确定性脉冲) |
| `<按键> release` / `<按键> hold` | 立刻释放 / 一直按住 |
| `dump <tag>` | 立刻 dump 全 EE(32 MB)+IOP(2 MB) RAM → `<tag>_f<帧>_eeram.bin` (绕过 40 次上限) |
| `snap <tag>` | 立刻截图 → `<tag>.png` (固定名, 可覆盖) |
| `drawwin <a> <b>` | **运行时**改 drawlog 窗口 (启动时用 `-grdrawwin 1 1` 只开文件不记内容) |

## 5. 第 1 步: 内存钩子 —— "读哪里"

### 5.1 侦察方法

`r61_recon.py` / `r61_recon2.py`: 用 live 命令把游戏开到目标列表, 在**每一个选中行**上各做一次
**全 EE RAM (32 MB) dump + 截图**, 然后差分找"随选中行变化"的地址。
**行号不是猜的** —— 每张截图都用 `r61_check_rows.py` 量"金色高亮条中心 y"反查行号
(round60 口径, 独立于内存)。

### 5.2 主菜单: **标量全局量 `0x013379D0`** ✅

- 采样行 (1-based): `[9,1,2,3,5,6,7,8,9]` (第 4 项灰条被跳过), 采样帧
  `[15703,16701,17701,18702,19704,20701,21701,22702,23703]`。
- 差分 (32 MB × 9, u8 与 u32 两个尺度):
  **`0x013379D0` 是唯一精确命中** `[9,1,2,3,5,6,7,8,9]` 的地址 (u8 扫描 92 个候选里 1 个精确命中;
  u32 扫描 5 个候选里 1 个精确命中, 且是同一个地址)。
- 值语义: **1-based 列表项号**, 值域 `{1,2,3,5,6,7,8,9}` (第 4 项不可选)。
- 这是一个**稳定全局量** (ELF 数据段), 换盘/换内容不变 ⇒ 适合做钩子。

### 5.3 特别收录列表: **不是标量, 是"每项一个选中标志位"** ⚠️ (本轮最重要的负面结论)

采样行 (1-based, 由金带 y 反查): `[1,2,3,4,5,6,8,9,10]` —— 第 7 行「专家」是灰条, 光标跳过。
金带 y 实测 = `83,111,138,165,193,220,275,302,329` (灰条位 y=248 光标永不去)。
采样帧 `[13134,14135,15135,16134,17135,18134,19134,20135,21134]`。

**穷举结果 (全部 0 命中)**:

| 数据源 | 解释 | 假设 |
| --- | --- | --- |
| EE 主存 32 MB | u32 整数 / **float32** / u8 低字节 | 1-based `[1..10]` / 0-based `[0,1,2,3,4,5,7,8,9]` / 可选行序号 `[0..8]` / 反向 / 前一行 / 后一行 —— **全 0** |
| IOP RAM 2 MB | 同上三种解释 | 同上 —— **全 0** |

⇒ **特别收录列表的"当前行"在 EE/IOP RAM 里没有任何按行号变化的标量。**
(对照: 主菜单有。两者是不同的 UI 实现。)

**它实际怎么表示** —— 用"9 个采样点里 8 个相同、1 个是异类, 且异类落在哪个采样点覆盖全部 9 个"
这个特征扫出来的:

| 行 (1-based) | 标志位地址 | 9 个采样点上的值 |
| --- | --- | --- |
| 1 影片 | `0x0091E7F8` | `[1,0,0,0,0,0,0,0,0]` |
| 2 设定图 | `0x0091EC88` | `[0,1,0,0,0,0,0,0,0]` |
| 3 音乐 | `0x0091F0F8` | `[0,0,1,0,0,0,0,0,0]` |
| 4 武器 | `0x0091F508` | `[0,0,0,1,0,0,0,0,0]` |
| 5 奖章 | `0x0091F918` | `[0,0,0,0,1,0,0,0,0]` |
| 6 背景 | `0x0091FD28` | `[0,0,0,0,0,1,0,0,0]` |
| 7 专家 (灰条) | — (光标不去) | — |
| 8 屏幕截图 | `0x00920588` | `[0,0,0,0,0,0,1,0,0]` |
| 9 访谈 | `0x00920988` | `[0,0,0,0,0,0,0,1,0]` |
| 10 预告片 | `0x0091CE68` | `[0,0,0,0,0,0,0,0,1]` |

**旁证**: 相邻项对象地址相差 ~`0x410` B, 而"第 6 行 → 第 8 行"这一步跨了 **`0x860` = 正好 2 项**
—— 与"跳过第 7 行灰条"逐项吻合。这不是巧合, 是同一套数据结构。

> 因为这是**堆上的对象字段**(地址随堆布局变), 闭环导航里不把它当作跨版本稳定的主观测,
> 而是当作**每次按键的即时校验**(见 §6)。

## 6. 第 3 步: 闭环状态机导航 `tools/capture/nav_hook.py`

### 6.1 结构

```
阶段1 开环引导   start×10 → up×3 → cross        (这段没有可用的状态钩子, 只能按时间线)
阶段2 握手       按 up 看主菜单钩子是否跟着变 ⇒ 判定"菜单已可交互", 最多重试 8 次
阶段3 闭环A      主菜单: 钉顶(up 到钩子=1) → 逐级校验走到「特别收录」(钩子=7) → cross
阶段4 闭环B      特别收录列表: 像素握手确认激活 → 已验证地回到第 1 行 → 7 次已验证的 down → 第 9 行「访谈」
阶段5 取证       cross 打开 → 运行时开 drawlog 窗口 + 截图 + dump 全 RAM
阶段6 页内取证   依次试 down/down/right/l1/r1/left, 每键一张图 (给空白页留证据)
```

### 6.2 三个"防漂移"设计 (逐条对应任务书)

| 要求 | 实现 |
| --- | --- |
| **帧率同步**: `tap` + 紧跟 `release`, 间隔 2~3 帧 | 模拟器侧 `tap` 就是"按下 + **3 帧后自动释放**", 不依赖驱动脚本的时序精度 |
| **每次按键后等钩子状态稳定再判下一步** | `press_verified()`: 按键 → 轮询钩子直到等于期望值 → **再要求该值连续稳定 14 帧** → 才判成功; 260 帧内没到就判失败 |
| **每步校验, 不符就重钉顶 / 报错退出** | 阶段3 每按一次 up/down 都校验钩子值 (值不在标定表里 ⇒ 判"漂移" ⇒ 重新钉顶, 最多 3 轮); 阶段4 每按一次 down 都用**两种观测**验证"正好下移一行", 丢键就重按、连续两次无效就报错退出 |
| **预算** | `-grmaxframes` ≤ 40000; `wait_frame` 单步 300 s 超时; 失败时自动补拍一张 `<tag>_last.png` 并落盘完整钩子序列 `hook_sequence.txt` |

### 6.3 阶段4 的"两种观测" (因为特别收录没有标量钩子)

1. **内存标志位差分 (主)**: 每次按键前后各取一次被监视区间 (`-grmemwatch 0x0091C000 0x6000 1`)
   的快照, 在区间里找"`0→1`"(新选中) 与 "`1→0`"(取消选中) 的字节 —— **要求恰好一对**。
   这正是上一轮"丢键/重键"的失效模式: 少按一次 ⇒ 一个都没有; 多按一次 ⇒ 会有两对。
2. **渲染高亮条 y (锚)**: 从抓到的帧上量金色高亮带中心 y, 用实测表
   `{1:83, 2:111, 3:138, 4:165, 5:193, 6:220, 8:275, 9:302, 10:329}` 直接给出**第几行**。
   它与内存无关, 换盘也成立。

> 之所以要两套: 内存那套是**堆地址**(换版本可能变), 像素那套是**渲染结果**(永远成立)。
> 两者都过才判"这一步可信"; 内存区间因堆布局变化而失效时会退化为只用像素, 并在日志里如实写明。

## 7. 字库测试页"整页空白"的取证

### 7.1 已有基线: 原版那一页是**正常绘制**的

`GR_ZH109` 的「开发访谈 1」页 (F24134, drawlog 窗口 F22933..F25933):

| 站点 | 调用次数 | 含义 |
| --- | --- | --- |
| `219A70` / `219EB0` | 9598 / 9599 | DrawString v2/v3 |
| `21AC00` | 13197 | RSFont::StringWidth |
| `21AD10` | 81592 | RSFont::CharWidth (逐字宽度) |
| `21C4C0` | 1199 | RSTextComponent::DrawTheString |
| `5172E0` | 4198 | MeshSubmit (字形网格提交) |
| `21A190` / `21A290` | 1198 / 599 | 字体 flush |

文本内容 (drawlog 里解出来的): 标题 `开发访谈 1`, 正文 `开发手记：第一辑` / `达伦丘基图斯` /
`制作人` / `与他共事，深知他是团队和公司难…` ⇒ **引擎解析 + 折行 + 提交绘制全都发生了**。

### 7.2 离线字节分析 (测试页 vs 原版)

`r61_page_bytes.py` (独立解容器, 直接看盘上 `<text>` 原始字节):

| 项 | GR_ZH109 (正常) | GR_TEST_FONT2 (空白) |
| --- | --- | --- |
| `<text>` 偏移 / 长度 | 58985 / **2799 B** | 58985 / **2799 B** (一致) |
| 段数 (`{br}`/`{p}` 切段) | 24 | 66 |
| 标记计数 | `{br}`=7 `{p}`=16 | `{br}`=52 `{p}`=13 |
| 用到的字节数 | 132 | 139 |
| **0x7F..0xA0 的字节** | **0 个** | **33 个** (`80..A0` 全用上) |
| `0xFF` | 无 | 有 |

**但这条线索不能定罪** (重要, 免得误导): 这些"新字节"是码表的**单字节码**
(编码是混合 1/2 字节: 例如原文第一行的「一」就是单字节码 `0xC5`), 而
`r61_single_byte_audit.py` 证明 `0x80..0xA0` 与 `0xFF` **在已交付文本里确实被用过**
(17 个 SFXML 条目, 共 34 个字: 凝/若/壳/巨/膛/套/拆/牺/牲/《/》/著/牛/旋/稳/猪/脆/促/终/享/伞/吸/尖/玻/璃/纤/燃/双/池/磅/捕/热/磁/履)。
⇒ **"用了没先例的码位"不成立**, 不是根因。

### 7.3 已排除的另一个假设: "行数超上限"

`r61_line_budget.py`: 用引擎折行模型 (`wrap_w=270`) 算视觉行数, 已交付页面里
**开发访谈 2 = 215 行、开发访谈 3 = 430 行**都是正常显示的; 测试页只有 88 行 (CSV `lines` 字段 131)。
⇒ **"行数太多撑爆缓冲"不成立**。

### 7.4 决定性证据: **正文文本根本没进引擎** (不是"渲染不出来")

`hook3` 在页面上抓的 drawlog (窗口 F15658..F18658, 118707 行, 其中可解码文本 53960 行):

| 站点 | GR_ZH109 原版页 | GR_TEST_FONT2 测试页 |
| --- | --- | --- |
| `219A70` / `219EB0` (DrawString) | 9598 / 9599 | 14389 / 14389 |
| `21AC00` (StringWidth) | 13197 | 25182 |
| `21AD10` (CharWidth) | 81592 | 43168 |
| `21C4C0` (DrawTheString) | 1199 | 3597 |
| `5172E0` (MeshSubmit) | 4198 | 12588 |

⇒ 绘制**管线本身是活的** (调用量甚至更多), 页面也确实画了一堆东西 (标题、海报、箭头、按钮)。

**但把"这一页的正文"当成字符串去找, 两个盘的结果完全相反**:

| 探针 (在页面 EE RAM dump 里搜编码字节) | GR_ZH109 原版页 | GR_TEST_FONT2 测试页 |
| --- | --- | --- |
| item 名 `开发访谈 1` | **4** | **4** (两边都在 ⇒ SFXML 已加载) |
| 原版正文头 `开发手记：第一辑` | **3** | **0** |
| 测试页正文头 `字库测试页 全` | 0 | **0** ← ★ |
| 测试页正文末行头 `障需充口` | 0 | **0** ← ★ |

同一份 dump 的 drawlog 里搜原始字节: 测试页正文头 `a3 b2 a8 c5 a5 cd a2 fd` 出现 **0 次**,
解码文本里含 `字库`/`每行`/`促凝` 的行数 **0**。而原版页的正文头在 RAM 里出现 3 次、并确实被
DrawString 画出来 (drawlog 里解出 `开发手记：第一辑` / `达伦丘基图斯` / `制作人` / `与他共事…`)。

> ★ **结论: 测试页的 `<text>` 正文从来没有变成可用字符串** —— 它既不在 EE RAM 里, 也从未被交给
> 任何 DrawString/StringWidth。**这是"引擎解析/取文本阶段失败", 不是"渲染不出"。**
> 标题能显示, 是因为它来自 `<item name="开发访谈 1">` **属性**, 与 `<text>` 载荷是两条不同的路径。

### 7.5 根因候选: **正文里 20 个连续的 `0x80..0x9F` 字节** (语料里前所未有的形态)

`r61_control_pos.py` / `r61_ctl_audit.py` 把 94 个非空 SFXML `<text>` 载荷逐个扫:

| 项 | GR_ZH109 (原版) | GR_TEST_FONT2 (测试页) |
| --- | --- | --- |
| `开发访谈 1` 载荷长度 | 2806 B | 2806 B |
| 含 `0x80..0x9F` 字节 | **0 个** | **32 个** |
| 其中**最长连续游程** | 0 | **20** (偏移 38 起) + 12 (偏移 62 起) |
| 含 `0xFF` | 0 个 | 1 个 (偏移 2741) |
| **全语料**含 `0x80..0x9F` 的条目 | 14 个 (每条 1~4 个字节, **最长连续游程 = 3**) | 15 个 (最长连续游程 **20**, 就是测试页) |
| **全语料**含 `0xFF` 的条目 | 1 个 (`AN-94 突击步枪`) | 2 个 (`AN-94` + 测试页) |

**位置极关键**: 测试页第一个 `{p}` 在偏移 **35**, 紧接着偏移 **38** 就是那串 20 个连续字节:

```
偏移 32..70:  a3 b2 7b 70 7d 80 81 82 83 84 85 86 87 88 89 8a 8b 8c 8d 8e 8f 90 91 92 93 7b 62 72 7d ...
              「字」  {  p  }  └────────── 20 个连续 0x80..0x93 ──────────┘  {  b  r  }
```

- 测试页是按**编码字节升序**铺全部 1285 个字 ⇒ 第一段之后的第二段正好从码表最小的
  `《》享伞促凝双吸…`(单字节码 `0x80 0x81 0x82 …`)开始, 于是**一上来就是 20 连**。
- 已交付语料里 `0x80..0x9F` 只以 1~4 个、最长连 3 的形式零星出现 ⇒ 引擎从没被这种"连续控制码段"考过。
- 与实测现象完全吻合: 文本在**取字符串**这一步就失败了 ⇒ 整页正文空白, 且**翻页/滚动也没有内容可翻**
  (测试页正文框右侧确实有 ▲▼ 滚动箭头, 但没有文本)。

**建议的下一步 (本轮未做, 交 Lead 定)**:
把测试页正文按 `{p}` 段**二分截断**做几张探针盘 (每次只保留前 N 段), 找出"从第几段开始整页变空",
即可把根因从"20 连 `0x80..0x9F`"收敛到**具体哪一个码位**; 或者直接把 `--order` 改成让
单字节码**不要连续排在一起**(例如按 unicode 排, 或每 2 个单字节码之间夹一个对偶码),
验证"连续游程"是不是触发条件。二者都不需要改引擎。

## 8. 已知限制 / 未做

1. **引导段仍是开环**: `start×10 → up×3 → cross` 按固定帧号走 —— 这一段游戏还没有可读的
   UI 状态钩子 (主菜单项号变量虽然 F1800 就有值, 但那时菜单还没激活)。从主菜单开始才是闭环。
2. **特别收录列表没有标量钩子** (§5.3)。跨版本稳定性靠"像素锚 + 内存即时校验"两者互补,
   而不是靠一个地址。
3. **`nav_sf_interview.txt` 的固定时序在 `-grinputlive`(3 帧短按) 下会走到主菜单而不是特别收录**
   —— 同一份时间线在 `-grinput`(12 帧长按) 下能进特别收录 (round60 的截图金带 y=83/302 与
   特别收录 10 行表吻合, 与我这次的主菜单网格 126..346 不同)。**这说明固定帧时序对按键长度敏感**,
   也正是本轮要消掉的东西。
4. 页内"翻页/滚动"键的语义未定论 (见 §7.4)。
5. 未改任何历史 ISO、未改 `GR_ZH109/text/`、未改 `tcslib.py` / `repack_font.py` /
   `font_compact.py` / `make_build.py`; 未 commit、未切分支。
