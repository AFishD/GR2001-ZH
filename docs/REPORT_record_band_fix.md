# 报告：记录带「上一代字形溢出墨」——「中/斗」左下方横条 的定位与修复（round47）

> 结论一句话（给用户）：**那条横条是"中"下面那个字（聚）的上一代字形，早先被写高了一行，
> 顶端那一行剩在了"中"的格子里；round45 把它搬正了却没把这一行残墨擦掉。本轮的 GR_ZH96_fix
> 把这一行恢复成字体原样，横条已经没有了，游戏里不会再看到它。**

---

## 0. 用户报障（原话）

> 「中」「抖」字的左下方出现一条横条，疑似是被下方的文字进行了污染。这一行最右侧的一部分块
> 下方都有几个脏像素，并且实际游戏可见。检查原因。

## 1. 现象与结论

| 项 | 查实结果 |
|---|---|
| 「中」的码位 | **单字节码 `0xD6`**（`charset_compiled_zh16.json` 的 `codes`），不是对偶码 |
| 它的 FT 记录矩形 | `(u0,v0,u1,v1) = (912,338,928,354)`（`FONT.RES` face=default，3 个 face 同值） |
| 引擎采样窗 | **就是这一格**：`x = 912..927`，`y = 338..353`（16×16；见 §2.1 证据） |
| 脏像素在哪 | **在矩形内部**：该格最后一行 `y=353` |
| 长什么样 | 本盘 `.#######........`（x=913..918 多 6 个墨点）；字体模板应为 `.......#........` |
| 「抖」 | charset 里**没有**「抖」这个字。用户看到的其实是同一行的 **`0xD8`「斗」**（多 10 个墨点，像多了个提手旁）⇒ 与「中」同因 |
| 受影响范围 | 该条带上一共 **20 个记录格**（全是行 18 的单字节码 `0xC2..0xDA`），差异**只在 y=353 一行、共 76 个 texel** |
| 成因 | round45 **之前**，行 19..24 的对偶字形写在 `yrow-1`（比引擎格高 1 行）⇒ 每格第 0 行**溢出到上一行的记录格里**。「中」正下方那格是槽位 (19,27)「聚」；round45 把「聚」搬到 (19,57) = `(912..927, 354..369)`，**但上一代留在 y=353 的那一行没人清**（round45 清带范围 = `[yrow, yrow+16)`，恰好少一行 `yrow-1`；而"记录矩形原样贴回"又把这一行连同污染一起贴了回来） |
| 是不是 round45 造成的 | **不是**。y=353 这一行在 GR_ZH93/GR_ZH94 里**逐像素相同**（都带这条残墨）。round45 做的是把字形搬到引擎格（正确），只是**没顺手把残墨清掉** |

### 1.1 与 Lead 判断的差异（据实订正）

Lead 的定位大方向对（**就是"差一行"**：清带少清了 `yrow-1` 这一行），但两处需要订正：

1. **不是"记录带被下移一行"**：`v=354` 起内容整体下移 1 行，恰恰是 round45 的**正确修复**
   （字形从 `yrow-1` 搬到引擎真正采样的 `yrow`）。用户看到的横条在**矩形内的最后一行 y=353**，
   不在矩形下方；`v=354/355` 那两行**不在**「中」的采样窗里。
2. **"544 条记录矩形与 GR_ZH93 逐像素相同"这个硬指标与用户报障互相矛盾**：ZH93 的这 20 个格子
   **本身就带这条残墨**（这正是用户报障的东西）。要修用户的问题，就必须让这 20 格偏离 ZH93。
   本轮采取的口径是：**504/544 与 ZH93 逐像素相同；另外 40 条（= 20 个真实格子 × 2 个 face）
   只在那 76 个污染像素上不同，且改完之后与字体源模板逐像素相同（err=0）**（§4 有逐条数据）。

## 2. 定位过程与证据

### 2.1 先确定"引擎到底采样哪一格"

* `docs/REPORT_glyph_align.md` §2.1 的反汇编：单字节码走 FT 记录表，**用记录矩形当采样窗**；
  本轮又用两条独立证据复核：
  1. 盘上 108 个 16×16 记录格，用 `方正像素16.ttf`（与 `tools/font_pipeline/gen_font16.py` 同法
     渲染：`truetype(16)` + `draw((8,8))` + 取 `[8:24,8:24]`）**逐像素 0 误差命中在 `(u0,v0)`**；
     把模板放到 `((u0+576) mod 1024, v0+1)`（`REPORT_font_ext_zh93.md` §2.2(b) 那条口径）误差
     54..130 ⇒ 那条口径是 **flat 容器坐标 → 引擎坐标的换算**（`tcslib.atlas_flat_pos`：
     `x+96×(段号+1)`，进位时 `y+1`）被当成了引擎坐标，**不是**采样点。
  2. 手柄图标码的记录矩形是 `(89,395,135,408)`（46×13）与 `(136,420,146,436)`（10×16）——
     尺寸都不是 16 的倍数、墨迹恰好填满矩形，只有"采样窗 = 记录矩形"能解释。
* ⇒ 「中」的可见区域 = `(912..927, 338..353)`，**y=353 就是它的最后一行**。

### 2.3 残墨的来源（可复现）

* 槽位 (19,27) 的字形（那时是「聚」）在旧相位下写在引擎图 `(912..927, 353..368)`
  ——正是「中」这一格的正下方、**上沿高出 1 行**；
* round45 的搬运式：`fx = 16*((col+OLD_PHI[row]) % 64)`、`fy = yrow(row) + 回绕`，
  经 `flat_to_engine()` 换算后读到的是 `(912, 353)`（= 旧字形的第 0 行）⇒ 搬到新格
  `(912..927, 354..369)`；**y=353 那一行不在清带范围内，于是原地留了下来**；
* 因此 ZH94 的 y=353 与 y=354 逐像素相同（都是那一行），而 y=355 起 = ZH93 的 y=354 起。
* 全部 3 个 face 的记录矩形指向同一批格 ⇒ 一次修复对 3 个 face 同时生效。


## 3. 修法

新补丁 **`tools/iso_build/patch_zh96_record_band.py`**（幂等、可重放、只做一件事）：

1. 读盘上 `COMMON.PAK` 的 `new_font_revised` 像素容器（引擎口径解码，复用
   `patch_zh94_glyph_align.Atlas` 的同一套封包口径）+ `FONT.RES` 的 3 个 face 记录表 + charset 单字节表；
2. 取全部 544 条记录矩形，只看**溢出带行** `S = {yrow(r)-1 : r ∈ 19..24} = {353,369,385,401,417,433}`；
3. 用 `方正像素16.ttf` 渲染该格字符的 16×16 模板；
4. **只有**当"格内差异全部落在 S 行里"（= 这一格的字形就是模板、只是被溢出墨盖住）才动手，
   把这些像素改成模板值（墨→索引 0 / 空→调色板空值 1）；否则**跳过不动**（打印原因）。

安全边界（全部有自检，不通过就 `assert` 终止）：

| 约束 | 实现/自检 |
|---|---|
| 不碰 48B 包头 | 逐像素 `Atlas.set_px`（只写段数据区）；回读后核对"像素容器以外的 PAK 字节逐字节不变" |
| 不碰行 19..24 的字形 | 变更像素**必须**全部落在 S 行（S 行都不在 6 条引擎行带里）；`[self1]` 带外必须 0 |
| 记录矩形其它行不动 | `[self2]`/`[self3]`：修好的格在非 S 行 0 改动；544 条记录矩形（非 S 行）与源盘 0 差异 |
| 修完就是字体原样 | `[self4]`：修好的格与模板逐像素相同 |
| 幂等 | 对已修好的盘再跑 = **0 像素改动**（文本/图集都不动，产物 sha256 不变） |
| 图标小矩形 | 矩形不是 16×16 ⇒ 自动跳过（`0x7B/0x7D/0xE7/0xF1` 的 46×13、`0xB1/0xB5/0x20` 的 10×16），**一个像素不碰** |
| 不改 charset / 不改 FT 记录 / 不改文本 | 补丁只写像素容器那一段；逐字节比较见 §4.2 |

#### 4.5.4 「斗」还是「抖」——逐字结论

* 第二个字是 **「斗」**（单字节码 **0xD8**），**不是「抖」**。
* 它为什么看起来像「抖」：修前那一格**最底一行多了 11 个墨点**，位置恰好在「斗」左下方（正是「扌」该在的地方）⇒ 视觉上像多了一只手（`ab/cell_zhong_dou_ab.png` 是这一格的放大对照）。
* 修后这 11 个墨点被清掉（`ab/ab0b_cells.log` 逐格 ASCII：0xD8 差异行 = 格内第 15 行 = `y=353`）。
* 另一条独立证据：**全游戏文本表里根本没有「抖」这个字**（`ab/_find_page.log`：grep 命中 0；只有 T0019/T0048 两条含「斗」）⇒ 用户看到的第二个字只能是「斗」。

  f9800 起）—— 修前「是」底部多一横、看起来像被重复画了一次，修后干净。

  "更高水平的战斗技能"），该页需要三级菜单导航；而本环境的菜内导航有三重抖动
  （按键登记 ±1、引导时间线漂移、"选择文件"屏输入解锁窗口，见 §4.5.7），多轮尝试都停在
  「输入名字」键盘屏/提示框，未能稳定进入该页 ⇒ 如实记为未拍到。

#### 4.5.7 本轮踩到并记录的工具链教训（后续实机一律照做）

1. **`gsrunner` 只能单实例**：两个实例同时跑必有一个 `exit=-1` 被杀（实测 3 次：cap_94 f23000、
   本工程师 f2300、11:41 那次）⇒ 起跑前 + 轮间都要检查进程，必要时要看门狗。
2. **自定义 mc 目录会破坏时间线**：`run_opt.py` 每轮会复位 `third_party/emu/run/memcards` 的模板卡；
   绕过它自带 mc 目录 ⇒ 卡里没存档 ⇒ 游戏走"新建档案" ⇒ 停在「输入名字」键盘屏，**永远到不了目标页**。
   正确做法见本节的抓帧命令（模板复位 + 独占目录）。
3. ★ **按键语义 + 导航必须用 drawlog 复核**：`-grinput` 的 `tap` 默认**按住 12 帧**，而本作菜单按住
   ~7 帧就开始连发 ⇒ 单个 `tap` 会移动 **2~3 项**且随帧相位漂移（这就是历次"导航漂移"的根因）；
   正解是 `tap` + 紧跟一行 `release`(fr+2) 的 2~3 帧短按。**并且**：输入序列启动即固定、运行时无法改写
   ⇒ 一定要开 `-grdrawwin` 把"每帧绘制文本"写进 `drawlog.txt`，跑完立刻核对"实际到了哪一页"
   （注意：该文件在运行中被模拟器独占锁定，只能等进程结束后读）。
4. （附带坑）**「选择文件」屏的初始高亮就是档 1**：照抄 `nav_sf6/nav_r47` 的 `up×3` 会把高亮从档 1
   **上绕到最底的「新建」**，于是 cross 变成"新建档案"⇒ 进「输入名字」键盘屏。逐帧对照见
   `ab/m_filesel.png`（失败轮：金色在「新建」）vs `ab/m_filesel_before.png`（成功轮：金色在档 1）。

## 5. 已知限制

### 5.1 与 GR_ZH93 的关系
那 40 条记录与 ZH93 不同是**故意的**：ZH93 在这 20 个格子上带着残墨。逐像素"回到 ZH93"
与"修掉用户看到的横条"不可兼得；本轮选择修掉横条，并保证改完之后等于字体源模板。

### 5.2 图标矩形与行 24 / EN 带的记录码
* 手柄图标矩形不是 16×16，没有可比对的模板 ⇒ **本轮不动**（保持与 ZH93 一致）。
  它们是否也被上一代字形压过，需要一份"干净图标"参照才能判定，本环境里没有。
* 行 24（`0x9D/0x9E/0x9F/0xA0/0x92/0xAE/0xFF`）与 EN 带那批单字节字的字形**不是**本轮 TTF 渲染
  出来的（与模板差 60..120 像素，整格平移也解释不了）⇒ 补丁按"差异不止在溢出带"**主动跳过**。

### 5.3 ⚠ round46 字库重排带来的口径冲突（影响后续构筑）
* `tools/font_pipeline/data/charset_compiled_zh16.json` 已在 **2026-10-12 10:23:51** 被 round46
  写入（`_font_repack.last_applied`，`moved/codes_changed = 636`），并有 `work/builds/GR_ZH95/`。
  ⇒ **现役 charset 与 GR_ZH94 的图集已经对不上**（636 个对偶字槽位不同）。
* ⇒ 以 GR_ZH94 为基底的构筑**现在不能带 `--inject-csv`**：注入器会用新 charset 重编文本，而图集还是旧的
  ⇒ 636 个字会写乱。本轮因此不加注入；文本与 ZH94 逐字节相同（§4.2 已证）⇒ 满足
  "2261 条逐字符相同、修改 0 条"。
* 单字节码表（110 条）**未被重排改动**（逐条比对 0 差异），所以本补丁的"码 → 字"映射不受影响。
* 若要"重排 + 记录带修复"合盘：在**重排后的盘**上再跑一次本补丁即可（幂等、任何盘都能跑）。
* `dump_font.py` 只读共享 charset，所以"旧图集 + 新 charset"的盘上它的缺字/对齐数字会失真；
  本报告的做法是**两盘用同一个 charset 各 dump 一次再对照**（§4.4）。

### 5.4 文本表既有的往返问题（与本轮无关，但会挡住 diff_text_versions）
`diff_text_versions.py GR_ZH96_fix GR_ZH94` 会因文本表里既有的 `{{BTN:E0A8}}`（`0xA8` 落在
对偶 lead 区间 `0xA1..0xB0`）触发"往返自检不通过 (429 行)"而拒绝 dump（exit=1）。
`diff_text_versions.py GR_ZH94 GR_ZH93` 因为走的是已有快照所以正常（exit=0）⇒ 是**表/工具**侧
既有问题，不是本轮的盘。

### 5.5 采样窗的 1 行余量
`REPORT_font_ext_zh93.md` 记的口径是"采样窗 = `[v0+1, v1+1)`"（= 比记录矩形低 1 行）。本轮用
模板扫描否证了它的 `u0+576` 部分（那是 flat↔引擎换算），但"是否也低 1 行"这条**没有**被
模板法否证（模板只说明字形**画在** `(u0,v0)`）。两种口径下 y=353 都在可见区内，所以本轮修法
对两种口径**都**减少污染：

* 口径 A（采样窗 = 记录矩形那 16 行）：y=353 是显示的最后一行 ⇒ 横条**彻底消失**；
* 口径 B（采样窗 = 下移 1 行）：y=353 是显示的倒数第二行 ⇒ 残留横条消失，最底下一行仍会显示
  「下方那个字」的第 0 行（这是"记录格与下面汉字格在几何上就重叠 1 行"的固有代价，
  要连它也去掉就得动「聚」等已搬好的字形，得不偿失）。

实机目视确认已由 §4.5 补完（主菜单对照：修前「训/习/务」左下方残墨可见、修后消失）。
