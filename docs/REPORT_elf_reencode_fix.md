| 盘 | 载入提示条 | 证据 |
|---|---|---|
| `GR_ZH105`（紧凑**前**） | 「**请等待！**」✓ | `work/builds/GR_ZH105/temp/dump_r56docA/snap_f00001500.png` |

（`0x50B840 / 0x50B860 / 0x50B890 / 0x50B8C0 / 0x50B8E8`，全在 ELF 里）。

## 2. 根因（三条，缺一不可）

| # | 洞 | 事实 |
|---|---|---|
| ① | **扫描阈值太宽**：`SCAN_MIN_CJK = 4` | 「请等待」只有 **3** 个字 ⇒ 连候选都不是。标定依据（`docs/REPORT_font_compact.md` §4.2）认的是"最长汉字串 ≥6"的**长文本**，短串从来没进过视野 |
| ② | **候选区间下限也太大**：粗扫 `SCAN_RAW_MIN_BYTES = 12` | 即使把①降到 2，「请等待!」这条串只有 **7 B**（`请等待` + `!`），整条区间会被丢掉 ⇒ 必须另起一套**细扫** |
| ③ | **ELF（非 IMG 区）不在覆盖范围** | round56 的兜底只处理"落在**真文本容器**里"的段；ELF 的 `texty` 判据要求"汉字数 ≥16"，5 条载入串一条也进不去。历史规则把 ELF 当"受保护区"，本轮证明：**受保护 ≠ 不用换码**，而是**必须换码且只准换这几个字节** |

### ★ 为什么 round56 的验收没抓到（假绿，必须记下来）

`work/builds/GR_ZH98/temp/r56/diff_attr.py` 里 ELF 区间写的是

```python
ELF = (295 * SEC, 295 * SEC + 0x180000)      # 1.57 MB
```

而真正的 ELF（`SLUS_206.13`，PVD 里 size = 37 453 732）是 **37.5 MB**（按 ELF 头 `e_shoff + e_shentsize*e_shnum` 算
= `0x93800..0x244B7A4`）。载入串在 `0x50B840`（≈ 5.3 MB）—— **根本没进窗口**，
所以当时报的"ELF 差异 0 ✓"是**窗口没盖住**，不是"没差异"。

本轮用扩到 37.5 MB 的窗口重算：`GR_ZH106` vs `GR_ZH105` 的 **ELF 差异仍然是 0 B** ——
这反过来证明了根因（round56 一个字节都没改 ELF）。修正后的脚本：
`work/builds/GR_ZH98/temp/r57/diff_attr_r57.py`（建议后续沿用）。

## 3. 修法（`font_compact.py`，r57）

### 3.1 阈值与预筛

| 项 | r56 | **r57** | 为什么 |
|---|---|---|---|
| `SCAN_MIN_CJK` | 4 | **2** | 「请等待」3 个字要能进候选 |
| 粗扫区间下限 `SCAN_RAW_MIN_BYTES` | 12 | 12（不变） | 长文本快扫，命中 430 万段的量级不能再放宽 |
| **细扫区间下限** `SCAN_SHORT_MIN_BYTES` | — | **4** | 2 个汉字 = 4 B ⇒ 「请等待!」(7 B) 能整条进视野 |
| **细扫预筛** | "区间内 ≥4 个连续高位字节" | **"区间内含 ≥1 个旧码表的合法对偶码位置"**（65536 项 LUT，numpy 向量化） | 随机字节命中率 ≈ 1175/65536 ≈ **1.8%/位置**，比"≥4 连续高位字节"精确约 20 倍 ⇒ 下限降到 4 B 也不爆炸 |

### 3.2 判据：真文本 vs 二进制巧合（**C 字符串口径**，在 GR_ZH105 上标定，IMG 之外零假阳）

一段"≥2 连续汉字"被判为**真文本**，当且仅当：

| # | 判据 | 作用 |
|---|---|---|
| ① | 段所在的"无控制字节极大区间"**两侧都是 `0x00`** | 是一条完整的 C 字符串（引擎 `DrawString` 读的就是这种串） |
| ② | 整串能被旧码表 greedy 解析**完整消费**（无解不出的字节） | 排除混着二进制噪声的串 |
| ③ | 串内**对偶码字符占比 ≥ 0.50** | ★ 决定性指标：真文本 **0.50~0.75**；二进制巧合 **0.00~0.33**（巧合串里混着大量单字节码噪声字：著/手/命/前…） |
| ④ | 串内**至少 1 个对偶码的码位本轮变过** | 码位没变 ⇒ 换码后字节一模一样，**根本不用动**（「载入中」就是这一类） |

判据③的标定（`GR_ZH105`，IMG 之外 12 146 段 ≥2 汉字段）：

| 判据 | 选中段数 | 真文本 | 假阳 |
|---|---|---|---|
| ①②（NUL 串 + 干净解码） | 221 | 10 | **211** ✗ |
| ①②③（+ 对偶码占比 ≥0.5） | **6** | **6** | **0** ✓ |
| ①③④ 但不要② | 56 | 5 | 51 ✗ |

⇒ 只有"**C 字符串 + 对偶码占比**"这一组能做到零假阳；单看"段内全是对偶码"（`pair_ratio==1.0`）会放进 56 段。

### 3.3 已知文本区登记表（`KNOWN_TEXT_REGIONS`）

```python
dict(name='ELF 载入提示条 5 语言槽表 (Loading... / Please wait!)',
     elf_rel=(0x478020, 0x4780F4),           # ELF 相对偏移; 绝对 = ELF 基址 + 该值
     ratio_min=0.0, min_cjk=2,
     provenance='docs/han_v2/BOOT_SCREENS.md §7.2 — GR_ZH15 起 tmp/bootscreen/elf_patch.py 写入的 '
                '5 语言槽: FR/DE/IT/ES/EN × {载入中…, 请等待!}')
```

* ELF 基址由 **LBA 扫描 `\x7fELF\x01\x01\x01`** 定位（优先 LBA 295），不写死绝对偏移；
* 区内的 C 字符串**免除判据③** —— 那儿的字节是**我们自己写进去的**，未来再重排时连「载入中」的码位也会变，
  而它只有 0.33 的对偶码占比，靠判据③ 兜不住；
* 登记表是**可解释的出处**，不是"跳过表"：每一条都带 `provenance`，写进报告与 charset 元信息。

### 3.4 门禁加强（用户要求的"逐段逐字比对，做不到就中止"）

| 检查 | 内容 |
|---|---|
| **A（原有，扩到短串）** | 每条短串：盘上字节 == 计划值；**改动的字节必须全部落在"旧码表解析出的 2 字节对偶码"区间内**（ASCII / 单字节码一个都不许动）；`新 charset 解盘上 == 旧 charset 解基底`（逐字）；字符数不变 |
| **A0（原有）** | 3 容器 + 5 原始区 + 像素容器的盘上字节 == 计划值 |
| **A2（本轮新增）** | **写盘区间两两不重叠**（8 个区间）—— 重叠 = 同一段被改两次，必有一次是错的 |
| **B0（本轮新增）** | **短串逐条闭环**：5 条串逐条 `旧解 == 新解` 且**长度不变**；"判为真文本却没写盘"的候选 **0** |
| **B（原有）** | 全盘复核：旧码表 **4 303 945** 段命中 = IMG 条目内 4 287 595（容器扫描负责） + 原位重映射 2 + IMG 之外巧合 16 348 + **范围外真文本 0** |
| C1–C4 / D / E（原有） | 图集回读 == 目标图；逐字像素落在新格 1175/1175；FT 采样窗 0 改动；48B 包头不变；**在用 = slot 0..1174 / 空闲 = 1175..1503**；对产物再 plan 一次 **0 改动** |

## 6. 已知限制（如实说明）

1. **判据③ 的边界**：对偶码占比 <0.5 的串不会被判为真文本。本轮靠**已知文本区登记表**兜住了「载入中」
   （占比 0.33，只是恰好码位没变才不用改）。⇒ **以后每加一处"非容器的文本区"，必须往
   `KNOWN_TEXT_REGIONS` 登记**（带出处），否则将来重排时它会像 GR_ZH106 那样静默变味。
2. **细扫不解析 IMG 条目内部**：条目内的段交给容器扫描，而容器级判据 `texty` 要求"最长汉字串 ≥6" ⇒
   **装在容器里的短串文本仍可能漏**（本轮实测确实有一处，见 §6.1，本轮按用户口径**没动**）。
3. **二进制巧合段"换码后意义会变"是必然的**（charset 换了）：本工具**不改它们**，只逐条留证计数
   （IMG 之外 16 348 段，其中"换码后意义变了"的 956 段；改了就会把 `.PSS/.TM/.SS` 这类媒体数据改坏）。
4. **判据只认"NUL 结尾的 C 字符串"**：定长表、按行分隔的文本文件（无 NUL）不在覆盖内 —— 见 §6.1。
5. **耗时**：细扫 ≈ 200 s + 粗扫 ≈ 125 s + 容器扫描 ≈ 300 s ⇒ 字库步骤总时长约 **11 分钟**
   （每轮构筑都跑；要提速可以给细扫加"跳过 IMG 条目内部区间"的快路径，本轮没做，优先保证不漏）。
