## 3. 为什么「命令」是错译

1. **词义选错**：英文 `Order` 是**多义词**。在「小队设置 / 名册」语境里它是名词「**顺序、次序**」；
   旧译取的是「命令、下令」义项（`give an order` 的 order），与界面元素的功能无关。
2. **与同屏帮助条自相矛盾**：同一屏上，本按钮的帮助条英文是
   `Left and right to change soldiers order.`，
   而这份汉化的帮助条**已经**把它译成「左右键更换队员顺序。」（G58.I092）。
   也就是说：汉化自己把 `order` 译作「顺序」，却把同一个词的按钮名译作「命令」——
   屏幕上一句话同时出现「命令」和「顺序」两个词指同一件事。
3. **与控件形态矛盾**：按钮两侧是 `◀ ▶`（左右键循环），下面没有命令目标、没有确认动作。
   它是个「顺序选择器」，不是一个「下命令」的动作。
4. **用户实测**：用户自己在该页看到帮助条「左右键更换队员顺序。」，并指出实际作用是切换队员顺序。

## 4. 新译法与理由

**定为「顺序」。**

- 与英文原盘 `Order` 的名词义项一一对应；
- 与同屏帮助条「左右键更换**顺序**队员顺序」/「左右键更换队员**顺序**」用词完全一致（这份汉化自己已有的口径），改后同屏自洽；
- **2 个汉字**，与旧译「命令」同为 2 字 ⇒ 按钮框宽度不变、不会溢出（实机已核对，见 §7）；
- 语言表中已有该字：`顺 = 对偶码 (A6,B8)`，`序 = 对偶码 (A5,BD)`，无需扩字表、无需改字库。

被否掉的候选：

| 候选 | 否决理由 |
|---|---|
| `排序` | 按某规则**排序**，暗示有排序依据（姓名/军衔）；原盘只是 `Order`，且与帮助条「顺序」不一致 |
| `调序` | 中文 UI 罕见词，且同样与帮助条用词不一致 |
| `编组` | 词义跑偏（编队/分组），不是顺序 |
| `次序` | 可以，但不如「顺序」与帮助条口径一致 |

## 5. 数据位置与字节改动

语言表结构：`{u32 ngroups}` + 每组 `[{u32 id(第2组起)}{u32 count}]` + 条目 `{u32 len}{data}{u16 attr}`，
容器为 8 条 LZO 子流（`16384×7 + 尾流`，每条前置 `{u32 clen}{u32 olen}`）。
G58 = 第 58 组（0-based 57），I195 = 组内第 196 条（0-based 195）。

| | MENU.IMG #25 `EN_STRINGS.RES` | GR.IMG #902 `EN_STRINGS.RES` |
|---|---|---|
| LBA | 776286 | 19175（索引按名字表解析后与常量 902 核对一致） |
| 槽长 `stored` | 47570 | 47619 |
| 明文长 `real` | 128545（实际内容仅用 68615 B，其后 59930 B 全 0） | 128668（内容 68615 B） |
| 条目表行 | `0x830 + 48×25` | `0x830 + 48×902` |
| `stored`/`real`/`off` | **补丁前后完全一致** | **补丁前后完全一致** |

目标条目 `G58.I195`（两份表里的偏移相同）：

```
明文偏移   0xBE5E .. 0xBE61   长度字段  u32 = 3   →  u32 = 4
明文偏移   0xBE62 .. 0xBE64   数据     e0 a1 ba    →  a6 b8 a5 bd   (+1 B)
                                        （命令）        （顺序）
```

- 旧字节 `e0 a1 ba` = `命`(单字节码 0xE0) + `令`(对偶码 `A1 BA`)，3 B；
- 新字节 `a6 b8 a5 bd` = `顺`(对偶码 `A6 B8`) + `序`(对偶码 `A5 BD`)，4 B；
- 明文里目标条目**之后**的所有条目整体后移 1 B；
- 为**保持 8 条子流的 olen 与整体布局完全不变**，从明文**末尾**扣掉 1 B 零填充
  （明文末 59930 B 全为 0x00，脚本内已断言），故 `real`、`stored`、各子流 olen 全部不变；
- 压缩时**明文未变的子流原样复用原压缩字节**（5 条复用、3 条重压），把改动面压到最小。

逐字节证据（含前后对照 dump、条目表 12 字段对照、8 条子流框架对照）：
`work/archive/cmp/r29_label/r29_byte_evidence.md`。

**未触碰**：ISO 尺寸、`MENU`/`GR` 两处头部（前 `0x830` B）、两处条目表（前 700 行）、
`GR.IMG` 条目的 `off`/`stored`、制作组名单条目、`MENU.IMG` 内部偏移、ELF。
全部差异字节（MENU 槽 17431 B + GR 槽 17432 B）均落在两个资源槽内——脚本逐字节断言过。

## 6. 补丁脚本与可重放性

```
python tools/iso_build/patch_zh_fix_order_label.py <src_iso> <dst_iso>
```

脚本内含：

- **基底断言**：`src` 的 sha256 必须等于现役盘 `GR_ZH89`（可用环境变量 `R29_ALLOW_ANY_BASE=1` 放行）；
- **定位断言**：条目 `G58.I195` 的明文偏移必须 = `0xBE62`、旧长度必须 = 3、旧字节必须 = `e0 a1 ba`；
- **结构完整性断言**：`ngroups` 仍为 66、条目数不变、条目总数 2232 → 其余 **2231 条逐一字节相同**；
- **回环断言**：每条重压子流解压回原明文；写盘后**回读**槽、重解 8 子流、逐字节比对；
- **范围断言**：差异字节必须全部落在两个槽内，且两处头部/条目表逐字节未动；
- **可重放**：连跑两次产物 sha256 一致。

实跑输出：

**为什么两份表都改**：`MENU.IMG#25` 与 `GR.IMG#902` 是同一逻辑表的副本（组数、条目数、每个条目明文，
以及 `G58.I195` 的旧字节全部一致）。两份都改可保证无论界面读哪一份，显示一致；
且两份都有 5 万字节以上的零填充余量，改法零结构风险。

## 10. 一条重要工具情报：既有中文 dump 口径有 bug（未改既有脚本）

`tools/diag/res_text_dump.py`（以及沿用同一 `dec()` 写法的脚本）在解码 zh16 时**优先匹配对偶码**，
而实测引擎/本项目编码器的口径是**单字节码优先**。两者只在 `0xAF`、`0xB0` 上分歧
（它们既是单字节码 `的`/`你`，又是对偶首字节），但足以让整份 dump 出现系统性错字：

```
G12.I003 正确: …使用指挥界面向小队中的队员下达命令。        （"队中的队员"）
          旧口径: …使用指挥界面向小队弗中他队员下达命令。    （(AF,A1)=弗 抢先匹配）
G58.I001 正确: 全部取消分配     旧口径: 全部取消分配（这里恰好不歧义）
```

本次排查用的是修正口径的新脚本 `work/_dis/r29_res_scan.py`（单字节优先，注释里写了证据）。
**建议 Lead 后续统一口径**，否则所有基于 `res_text_dump.py` 的译文体检都会带错字。
本任务按纪律**没有修改** `tools/diag/res_text_dump.py`。
