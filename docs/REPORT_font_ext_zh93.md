## 二、缺字分类与码位分配策略

### 2.1 为什么不能"直接用那 78 个空位"

任务书给的算式是「合法对偶空间 1222 − 已用 1144 = 78 空位 ≥ 76」。实测发现这个算式**漏了一项**：

* 现役图集里，**76 个单字节汉字的字形本身就占用了 76 个"合法对偶槽"的格位**
  （例：`的 0xAF` 的字形落在 slot 683 的格上，`你`→684 …）。
* 因此 78 个空位里，**只有 21 个的格位是真空的**，其余 57 个的格位已被
  单字节字形或**旧世代残墨**占住。

⇒ 若照原算式直接写，新字会覆盖现役字形（乱码/掉字），**必须先把"哪个格是活的"搞清楚**。

### 2.2 引擎真实取样规则（本次实测标定，全部可复现）

**(a) 对偶码（DBCS）** —— 引擎按 cave 公式算 UV，实测"相位"（逐行不同）：

```
字形在存储帧的位置： x = 16 * ((slot%62 + phi(row)) % 62)
                     y = 2 + 16*(row + 3*[row>=12])      slot=(b0-0xA1)*94+(b1-0xA1)
实测相位 phi:  row 0..3→6  4..7→12  8..11→18  13..15→30  17..18→36  19..23→2
```

依据：用 `方正像素16.ttf` 16px 模板对整张图集做**逐像素 d=0** 搜索，
767 个字的字形位置与上表**逐行完全一致**（脚本 `work/builds/GR_ZH93/temp/a21_phase2.py`）。

**(b) 单字节码** —— 实机探针标定（诊断盘涂实心块 → 取帧比对）：

```
引擎采样窗 = ( (u0 + 576) mod 1024 , v0 + 1 )
```

* 证据 1：`务 0xC9` 记录 (704,338) → 涂 (256,338) 后实机「快速任务」的**务变实心块**，
  而 (704,338) 本身不生效 ⇒ 采样点 = 704+576 = 1280 → 256 ✓
* 证据 2：`选 0xEC` 记录 (256,354) → 涂 (832,354) 后「选项」「选择文件」的**选变实心块** ⇒ 256+576 = 832 ✓
* 记录 rect 本身**不被采样**（是旧世代残墨）。

### 2.3 最终分配

| 来源 | 数量 | 说明 |
|---|---|---|
| 空闲对偶槽（引擎格为空格/死副本） | **41** | 683..699（行11，17 个）+ 1176,1177（行18，2 个）+ 1182..1209 中的空闲者（行19，22 个） |
| 空闲单字节码 | **35** | `0x7F..0xA0`（除 `0x92`）33 个 + `0x92` + `0xAE` |
| 合计 | **76** | 与缺字数**恰好相等** |

⚠ **`0xB1 / 0xB5 / 0xE7 / 0xF1` 一律未动** —— 实测用户译文里有
`{{BTN:E0B1}} ×35 / {{BTN:E0B5}} ×105 / {{BTN:E0E7}} ×3 / {{BTN:E0F1}} ×3`
按键图标占位，改动它们会让这些标记失效（首版曾误用 0xE7，预检立刻报错，已回退）。

### 2.4 为什么**不采用** lead 扩容（历史上的"方案 C"）

* `tools/text_csv/tcslib.py`（本轮冻结）的 `PAIR_LEAD_HI = 0xAE` ⇒ 任何 lead ≥ 0xAE 的
  对偶码会被预检判为 `dead_pair` 并**阻断写盘**，交付要求的"预检 exit 0"无法达成；
* 历史实测（`patch_zh88_lead.py`）：lead 抬到 0xB0 会吞掉单字节 `0xAF`(的)/`0xB0`(你)，
  8425 处调用归零 ⇒ **灾难性错位**；抬到 0xAE 虽零回归，但解决不了本轮的预检阻断。
* ⇒ 本轮走"**零 ELF 改动 + 数据面扩字**"，最稳。

## 三、渲染与写盘方法

1. **字形**：`third_party/fonts/方正像素16.ttf` @16px，PIL 阈值 128 ⇒ **二值、无抗锯齿**；
   每个字形都断言"有墨"且"墨不越 16×16 窗"（越窗即报错退出）。
2. **对偶新字**：字形写在 §2.2(a) 的引擎格；**同时**保证预检格（`4+16*(slot%62)`, `yrow`）
   有墨（该格是别的活字形，本补丁**不碰**）⇒ 预检 pass。
3. **单字节新字**：字形写**两份**：
   * 引擎格 `((u0+576)%1024, v0+1)` —— 引擎真正采样处；
   * 记录 rect `(u0,v0)` —— 给 `tools/text_csv` 的字形预检看（引擎不采样，两份互不干扰）。
   落点全部在 **行 24 / 行 27 的空区**（动态搜索空格，两份拷贝互不重叠）。
4. **FONT.RES**：large + default 两面各改写 35 条记录（各 10 B，结构/长度不变），
   重新 LZO 压缩后**等长覆写回原槽 4421 B**（`assert len ≤ 4421`）。
5. **图集**：`COMMON.PAK` 记录内 `px` 段**等长覆写**；`MENU.IMG` 内部偏移、
   IMG 条目 `off/stored` **一律未动**；只改图集字节与 FONT.RES 槽字节。
6. **自检**：补丁内置断言 —— 所有图集改动必须落在"授权格"内（越界即 assert 失败）。

## 五、已知限制（**请务必读**）

1. **⚠ 实机验证未完成 —— 这是本轮最大的缺口。**
   诊断盘 `DIAG2/DIAG3` 证明了两条采样通道真实有效（务/选 的字形在 `(u0+576)%1024` 处
   被引擎采样，涂块后实机对应字变实心块 ✓✓）；**但扩容后的整盘在 `run_opt.py` 里
   跑不进主菜单**：引导前 1200 帧与现役盘逐帧一致，之后停在过场动画并循环
   （`GR_ZH93` 与"只打补丁未注文本"的 `GR_ZH92_font` 都如此），
   说明**问题出在字库补丁本身**，而不是文本注入。
   最可疑的两点（按可能性排序）：
   * **FONT.RES 槽重压**：虽然 `dump_font` 能正常解出 5942 B / 3 face / 544 条记录，
     但引擎侧可能有本工具链没覆盖的校验；
   * **图集写入的某些格**：`DIAG4` 诊断盘（只涂 7 格）也复现了"主菜单文字全消失"，
     而 `DIAG3`（涂 10 格）只坏 1 个字 ⇒ 存在**少数"碰不得"的格**尚未定位。
   **⇒ 下一步（给 Lead 的建议）**：
   a. 先用 `--patch` 分两步隔离：只改图集 / 只改 FONT.RES，各出一张盘跑 `run_opt.py`；
   b. 对图集写入做"逐格二分"（类似 DIAG3/4），定位到具体哪一格触发；
   c. 定位后把该格从落点候选里排除，重跑本补丁（补丁是**幂等**的，可直接重跑）。
2. **实机取帧的绝对帧号会漂移**：同一 nav 下现役盘 F3300 出主菜单，扩容盘更晚，
   所以对照必须按**画面内容**对齐，不能按帧号。
3. **码位空间已用尽**：合法对偶槽 + 可用单字节码合计只剩 76 个位置，本轮**刚好用满**
   （41 对偶 + 35 单字节）。下一次再要加字，必须先做 lead 扩容（同时改 `tcslib`）
   或重建更大的图集。
4. **2 个旧字仍缺字形**（`娆`/`琚`，与本轮 76 字无关，属历史遗留）。
5. `0x92` / `0xAE` / `0xFF` 三个 EN 符号位被本盘改作汉字码位（实测用户文本未使用）；
   若将来要恢复 EN 撇号/®，需重新分配这 3 个字。
6. 首版曾误用 `0x7F`（< 0x80 会被 `tcslib` 当 ASCII 解码 ⇒ encode/decode 不对称），
   被注入器当场拦下（`SFXML:T0039 编码失败`），已改为只用 ≥ 0x80 的码位。
