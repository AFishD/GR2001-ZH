## 三、格位公式：错在哪、怎么定的

### 3.1 最终公式（已固化进 `tcslib.atlas_cell_xy_engine`）

```
slot     = (lead-0xA1)*94 + (trail-0xA1)
row, col = slot // 62, slot % 62
p        = col + PHI[row]
x        = 16 * (p % 64)                      ← 图集一行 64 格, 引擎一行只有 62 ⇒ 回绕
y        = yrow(row) + (1 if p >= 64 else 0)   ← ★ 回绕列的字形低 1 行
yrow(r)  = 2 + 16*(r + 3*[r >= 12])
PHI      = 行0-3:6 行4-7:12 行8-11:18 行12:24 行13-16:30 行17-18:36 行19-23:2 行24:0
```

### 3.2 证据链（每一环都能重跑）

|---|---|---|---|
| E1 | 1297 个对偶字逐字模板比对（Lead 已做）| 本式 **785/1297** 0 误差；无相位 `16*col` **0/1297** | `docs/REPORT_plan_c_zh93.md` §3.1 |
| E2 | **独立复核**：跨行抽样 67 字做模板比对 | 本式 **38** 个 0 误差；无相位 **0**；legacy `4+16c` **1** | `temp/r41/p06_pair_formula.py` |

| E4 | **★ x 回绕列**（`col+PHI ≥ 64`，现役 297 个已用 pair）| 模板 0 误差位置 = `(16*((col+PHI)%64), yrow+1)`，**8/8**；用 `yrow` 则 mismatch 30–131 | `p07_wrap_truth.py` |

即：**位置公式在抽样里 100% 命中**，逐像素满分率约 80%。

### 3.3 旧口径为什么"一直没炸"

`patch_zh93_planc.py` L268-275 写得很清楚：它**先写 `4+16*col`（"tcs 预检副本"）、再写引擎格**。
于是旧预检按 legacy 格查也查得到墨 —— 但那是**为了迁就错误口径而多写的副本**。
改用引擎口径后，**这些副本不再承重**（§五 建议里有一条）。

### 3.4 副产物之一：修掉 2 个字形误报

| 盘 | 旧口径说"缺字形" | 引擎口径 | 说明 |
|---|---|---|---|
| `GR_ZH93` | `欣`(slot 1364) `袁`(slot 1426) | **都有字形** | 它们的 legacy 格 (4,402)/(4,418) 是空的，引擎格 (32,402)/(32,418) 有墨 |

⇒ `GR_ZH93` 缺字形 **21 → 19**，剩下的 19 个**全是 ASCII**（`^ _ \` a | ~` + 小写），
属「字形在别的 face、实机可读」的已知告警。**现役盘上没有任何新增误报**（见 §四 R3/R4）。

### 3.5 ★ 副产物之二（更要紧）：`延` 与"1 行渗漏"，以及旧盘上真缺的 **22 个字**

**现象**：Lead 留的 `work/builds/GR_ZH93/temp/LEAD_还差延字字形.md` 说写盘前预检
`exit=3`，报 `延 U+5EF6` 盘上没有字形。查下来这不是"图集缺延"，而是**两类**问题叠在一起：

**(a) `延` 在现役盘上好好的，是旧格位公式读错了格。**

| 盘 | `延`=`ADF1` 的**引擎格** (512,354) | 旧口径格 (484,354) |
|---|---|---|
| `GR_ZH93` | 墨 67 px，`方正像素16` 模板 **mismatch = 0** | 墨 76 px（但那坐标不是 16px 对齐格、不是延）|
| `GR_ZH91`/`92` | 墨 10 px，**且全在格子第 0 行** ⇒ 剔掉后 = 0（它的真字形在 (240,386)，即**另一个 slot 的格**）| 墨 0 px |

⇒ Lead 那次 `exit=3` 的 `--src` 应是 **`GR_ZH92`（或 91）**：旧口径在现役盘 `GR_ZH93` 上
对 `延` 是**能查到**的（76 px），在 `GR_ZH92` 上是 0 ⇒ 报缺。**在 `GR_ZH93` 上 `延` 无需任何处理。**

**(b) 但同一个格子判据有个坑："整格有墨"会被相邻行的 1 行渗漏骗到。**

回绕列（`col+PHI ≥ 64`）的字形比 `yrow` **低 1 行**，它最后一行正好落进
**下一行 cell 的第 0 行** ⇒ 只看"整格有没有墨"会把这点渗漏当成"这个字有字形"。
`GR_ZH92` 上正好有 **22 个字**中招（格子里的墨**只有**这一行）。实测（`p18_bleed_guard.py`）：

| 判据 | `GR_ZH93` | `GR_ZH92` |
|---|---|---|
| 「整格（含第 0 行）有墨」 | 1319/1319 有字形 | **1319/1319 有字形 ⇒ 22 个是假的** |
| 「**第 1..15 行**有墨」（本轮采用）| **1319/1319**（0 个被误杀）| **1297**/1319（如实报出 22 个）|

⇒ 因此 `_check_grid` 采用「剔掉第 0 行」的判据（`tcslib.GRID_BLEED_ROWS = 1`）。
它**不会误杀**任何真字形（现役盘 1319/1319 全过），却能把渗漏-only 的格子如实报成缺字形。

**(c) 由此得到一条对下一轮很关键的结论：拿旧盘当基盘会缺 22 个字，不是一个。**

用同一份用户原表（`work/builds/GR_ZH92/text`）跑预检：

| `--src` | 结果 |
|---|---|
| `GR_ZH93.iso` | **exit 0**，输出与改前**逐行完全相同** |
| `GR_ZH92.iso` | **exit 3**：**22 个字 / 68 处文本** —— `匣 斤 款 毫 米 采 坐 “ ” 扳 倍 宾 偏 挂 栓 … 延`（**全在 atlas row 19, y=354**）|

逐字复核（`p19_missing22.py`，全图集模板穷举）：这 22 个字在 **`GR_ZH93` 上全部 mismatch = 0 存在**；
在 `GR_ZH92` 上，`米`/`延` 的字形躺在**别的 slot 的格**里（`(528,402)` / `(240,386)`），
`斤`/`倍`/`栓`/`偏` 全图集都找不到匹配 ⇒ **那一行（row 19）是 57 字扩容 / 方案 C 那一轮才铺进图集的**。

⇒ **结论**：`延` 这条待办可以**关掉**（现役盘不缺）；真正要做的是**确保构筑基盘是
`GR_ZH93` / `GR_ZH93planc` 这一支**。若确实要用 `GR_ZH92` 当基盘，那是 **22 个字**要铺。

## 五、已知限制（诚实清单）

1. **PHI 是实证拟合，不是从反汇编完整推出来的。**
   * 反汇编（ELF cctc cave `0x417050`）能证明的只有 `U0 = 16*col`、`V0 = yrow(row)`（**无相位**）；
     相位来自**图集数据侧**的历史行移位/重铺，只能用模板比对拟合。
   * 置信度：**位置**层面很高（E7 无偏抽样 **40/40** 全局最佳命中预测格；E3 全量 1319/1319 有墨）；
     **逐像素**层面中等（E1 785/1297 = 60% 满分，其余多为**别的字体风格**的字形，E8 已排除"位置错"）。
   * 残余不确定性：`坠` `撑` `的` 等少数字**全图集都找不到 0 误差模板**（`p07` 实测），
     只能用"那一格确实有墨"作证；`%64` 回绕本身也只有 8/8 抽样 + 全量"有墨"两类证据（**不是**逐字满分）。
2. **PHI 只对"当前这张图集"成立。** 一旦图集被重铺/换盘（`gen_font16` 重放、行移位类补丁），
   必须**重新拟合**，否则 `cell_x/cell_y` 会整体偏移。已在 `BUILD_TOOLCHAIN.md` §8.7 已知限制里写明。
3. **"有字形"判据是「引擎格第 1..15 行有墨」，不是「有完整字形」。** 它能挡住 1 行渗漏，
   但挡不住"字形残缺/被别的字覆盖"这类问题（要靠模板比对，本轮为 `坠`/`撑`/`的` 等少数字
   就出现过"格里有墨但模板对不上"）。**要发布前把关，仍建议用模板比对而不是这个判据。**
4. **同一份 charset 配不同基盘，结论完全不同**（§三.5(c)）：`GR_ZH93` 上 1319/1319 全有字形，
   `GR_ZH92` 上真缺 22 个。数据本身没变，变的是"盘上有没有铺过那一行"。
5. **`row 24` 的 16 个 slot 是"引擎能寻址、但从未被任何一轮铺过"的新行**（`y=434`）。
   PHI[24]=0 是实测的（E5），但那 16 格里已有 7 个被 **FT 记录的单字节字形**（`若/纤/终/脆/膛/著` 等，
   `v0=434`）占着 ⇒ 只有 9 格真空。**"45"这个数字里含这 9 格**；若将来发现 row 24 的实际相位不是 0，
   受影响的也只是这 9 格（其余 36 格在 row 23，相位 2，证据充分）。
6. **`strict_window_free = 41` 是信息项、不是承诺。** 它的判据是「引擎格空 + 与全部活字形采样窗零交叠」，
   与 `patch_zh93_planc.py` 的 LIVE 同口径，但**没有**把历史写在 legacy 位置的"预检副本"算进冲突
   （改口径后副本已不承重，覆盖它无害）。真要写新字形，仍建议走 planc 那套「写前逐格验证零交叠」的流程。
7. **单字节码的 `v0+1` 是文档口径**（`REPORT_plan_c_zh93.md` §3.2）实测量级为 1px；
   CSV 里单字节/ASCII 的 `cell_x/cell_y` 按它输出，`cell_legacy_*` 保留记录矩形原值，
   两者相差 1 行时**不要当成两套公式**。
8. **`GR_EN_ORIG`（英文对照盘）是唯一"新口径更严"的盘**：1319 个对偶字里引擎格空 **785**、
   legacy 空 **727**（`p11`）。但那张盘**本来就没有中文**，两边都在报"全缺"，
   且它是分析师用的对照盘、不是构筑 `--src`，属预期行为。
   （中文盘里：`GR_ZH93` **0** 缺；`GR_ZH91/92` **22** 缺，且那 22 个是真缺 —— §三.5(c)。）
9. **`font_usage.py` 仍是 legacy 口径**（`slot_cell()` = `4+16*col`）。本轮按铁律未改它；
   它报的"格位号"用于**回收规划**，与"引擎落点"是两件事。要让它也走引擎格，需改它 1 行 + 它自己的自检文案。
10. 本轮**没有**跑完整构筑（`make_build.py` 全流程会重拷 1.65 GB ISO），只做了
    `make_font_dump()` 的契约冒烟测试；字库 dump 是构筑的最后一步、只读、且契约逐字段核对过。
11. **容量口径 = 「现役 charset」×「这一张盘」**，两者可以来自不同轮次。实测拿 `GR_ZH92.iso`
    跑（`--no-png`，exit 0）：引擎格位自查仍 `1504/1504 OK`，容量 1504/1319/185 不变，
    但 **有字形 1473 / 缺字形 53**（= ASCII 19 + 单字节 12 + 对偶 **22**），
    对偶有字形 **1297/1319**；直接可用 **52** 格 / 需回收 **133** 格（旧盘图集更空 ⇒ 可用的更多）。
    **这不是 bug**，是"用新字表看旧盘"的正常结果，也正是 §三.5(c) 那条结论。
