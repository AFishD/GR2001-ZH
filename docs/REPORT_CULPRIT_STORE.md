## 0. 一句话结论

**肇事 store 找到了，而且不是「指针算错」，是 NULL 没检查。**

第 44 帧，游戏自己的 **LZ77 解压函数 `0x00539110`** 为一块 **65,552 字节（0x10010）的解压资源** 调用堆分配器 `0x00102D40` 申请 `0x10011` 字节，分配器**返回 0（NULL）**；紧接着

```
0x00539174  sw $v0, 4($s3)     ; s3[4] = 输出缓冲基址 = 0
0x00539178  sw $v0, 8($s3)     ; s3[8] = 输出游标     = 0   ← 无 NULL 检查
```

随后解压循环就把输出**逐字节写到地址 0、1、2 …**：

```
0x005391CC  sb $a0, 0($v1)     ; v1 = *(s3+8) = 0 + 已输出字节数   ← 第一条写坏 0x1300 的 store
0x004039C8  sb $v0, 0($v1)     ; 同一个 *(s3+8)，memcpy 的尾巴循环
```

所以 **`0x1300` 既不是「应该写的地方」也不是「被算错的指针」，它就是 `NULL + 4864`**（解压输出的第 4864 个字节），`0x0..0x300` 的异常向量区是输出的第 0..768 字节。第 45 帧 EE 一进异常向量就执行垃圾指令 → `EE: Unrecognized op` → `Trap exception` 死循环。

写坏的对象、写坏的地址、写坏的量级全部与「汉化文本/字库」无关：**失败的那块资源在英文原盘与汉化盘里逐字节相同**，肇事指令序列在两个盘里也**逐字节相同**（见 §5）。汉化能影响的只是「这次 malloc 会不会失败」（堆余量），本轮**未能证明**这一点。

### 2.3 指针来源链（从 malloc 结果到 store 的目的地址）

```
0x0053916C  jal 0x00102D40        ; v0 = malloc(s0+1)，s0 = *(blob) = 资源解压后大小
0x00539170  addiu $a0, $s0, 1     ; （延迟槽）请求 = 0x10011
0x00539174  sw $v0, 4($s3)        ; s3[4] = 输出缓冲基址  ← 0（NULL）未做检查
0x00539178  sw $v0, 8($s3)        ; s3[8] = 输出游标      ← 0
...
0x00539230  jal 0x00403930        ; memcpy(dst = *(s3+8), src = *(s3+0x24)+desc[4], n = desc[8])
0x00539234  addu $a1, $v1, $v0    ; （延迟槽）src = 窗口基址 + 回引用偏移
```

- **源指针**：`sink[0x10]..[0x18]` = `blob+4` / `blob+len` / 位流游标；回引用 copy 的源 = `sink[0x24]（滑动窗口基址，初始 = sink[4]）+ 描述符偏移`。

> **关键**：调用者**确实**检查了返回值，但 `0x00539110` 的返回值是「资源头里的解压后大小」（恒 ≠ 0），**不是**「分配是否成功」。于是 malloc 返回 NULL 时调用者的失败分支永远不会走，解压照跑。

**候选修复站点必须落在 0x00539110 内部**（不是调用者），因为：
- 两个调用点共用同一段逻辑，改一处漏一处；
- 调用者的失败分支是现成可用的（`free(s1[0x14])` + 置失败标志 + 跳过后续），只要让 `v0 == 0` 就能复用。

## 3. B. 分配器字段的写者（含对上一轮结论的更正）

### 3.1 更正 1：`-grwatch` 的 64 命中上限是**每个监视区各自**的

`GRResearch.cpp:175` `MAX_WATCH_HITS = 64` 是 `Watch` 结构体自己的计数（`w.hits`），不是全局共享。上一轮报告 §5.3「0x0055B7B0 的 64 条在第 8 帧就用完，没能抓到第 44 帧改写它的 block；抓到的是低端 0x1300 的 64 条（命中上限被低端地址用完了）」这个解释不成立——两个区各自都有 64 条预算。

### 3.2 更正 2：收窄到 4 字节**不能**把预算留到第 44 帧

本轮 `c03` 用 `-grwatch 5617584 4`（正好 `0x0055B7B0` 起 4 B，`c03_allocres_freelist/watch.txt`）：结果与 8 B 完全相同 —— 64 条命中分布在 **frame 0:1 / 1:16 / 3:16 / 5:16 / 8:15**，第 8 帧就耗尽。原因是这 8 个字节里 `+0x10/+0x14`（即 `0x55B7B0/+B4`）是一对**同值的头/尾指针**，永远同时被改，收窄宽度不减少写次数。

**因此「第 44 帧改写它的 block」不能用 `-grwatch` 抓到**；本轮改用 `-grhook` + 反汇编 + 帧快照把它钉住（下节）。

### 3.3 这个字段到底是什么

`0x0055B7A0` 起的结构是**堆管理器的空链表/桶哨兵**：`+0x10/+0x14`（= `0x0055B7B0/+B4`）是 next/prev 头尾指针，**空表时两个都等于 `0x0055B7A0` 自己**。

### 3.4 第 44 帧实际发生了什么（hook + 帧快照，两条独立证据）

- `c03` 的 hook 直接把**失败的那次分配**钉在 block `0x001024E8`：cycle `65029607307`，`a1 = 0x00010020`（对齐后的请求尺寸）、`s0 = 0x00010011`、**`v0 = 0`**。同一帧更早（cycle `65029581676`）同一 block 用 `a1 = 0x420` 成功返回 `v0 = 0x00B71EB0`。
- 帧快照（`c05`，自己复跑的那份）：

| 地址 | f43 | f44 | f45 |
|---|---|---|---|
| `0x0055B7A0` | F229F9FE | F229F9FE | **F229FDFE** |
| `0x0055B7B0 / B4` | 0055B7A0 / 0055B7A0（空表） | 0055B7A0 / 0055B7A0（空表） | **00010020 / 00010020** |

### 5.5 结论与未达成（如实）

**结论（区分三层，避免误读）**

1. **直接原因（已证实，与汉化无关）**：`0x00539110` 在 `malloc(0x10011)` 返回 NULL 后不做检查，把 NULL 当输出缓冲基址，解压输出写到 `0x0…` → 覆盖异常向量 → 第 45 帧进异常向量执行垃圾 → Trap 死循环。这套代码在英文原盘与汉化盘**逐字节相同**。
2. **触发条件（已证实）**：只有按下 L1（第 30 帧）才走到这条「申请 65,553 B」的路径；不按键 260 帧干净（上一轮对照）。
3. **「汉化是否导致这次分配失败」（未达成）**：失败的直接原因是分配器返回 0；我能证明的只有「英文盘那次会话里同类请求连续成功、汉化盘存档崩前该空闲桶为空表」，**没有**做过「同一进度点、未修盘 vs 汉化盘」的堆余量对照，因此**不能**断言 OOM 由汉化造成。

**未达成 / 需要什么**

- **未做到「从未修盘/英文盘冷启动走到同一场景」**：本机无头 gsrunner 只能靠 `-grinput` 盲按键，无法从冷启动导航到「任务中 + 按 L1」的场景（需要菜单/读盘/载入进度等一长串不确定输入）。**需要的输入**（任一即可把第 3 点变成可判定）：
  1. **英文原盘、同一场景的即时存档**（在「任务中、能按 L1 触发武器资源加载」处存档，CRC 应为 `3E571E95`）—— 有了它就能做「同场景、两版」的堆余量/分配成败对照；
  2. 或者汉化盘同一场景的存档 + 英文盘同一场景的存档（两张盘各一份，进度点对齐）；
  3. 或者接受「本机导航做不到」而由用户按路径亲自复现一次英文盘（看是否也崩）。
- **未抓到「第 44 帧改写 `0x0055B7B0` 的那条 store 指令本体」**：`-grwatch` 的每区 64 命中上限在 frame 8 就被这对指针用完（见 §3）；本轮给出的是「block + 值 + 时间」级证据（block `0x001024E8`、`a1=v=0x00010020`、`v0=0`、1 帧后槽位值 = 0x00010020）。要拿到指令本体，需要把 `MAX_WATCH_HITS` 调大（改源码重编 gsrunner）或给 watch 加「按帧窗口」——两者都要动 `third_party\emu\pcsx2_src`（本轮纪律不允许）。
- **未复现用户机上的 `TLB Miss` 形态**（上一轮已记录，本轮同样未出现；本机把低端页当可写，于是走「写坏异常向量 → 自陷」这条路）。
- 第二条复现路径（cross→R1）在本存档下**未复现**（§4）。

## 6. E. 候选修复站点表（**只给站点，不写 ISO**）

映射关系（本轮用 `tools\verify_sites.py` 双向核对过，并与 `LAY_fix1_bytecount.meta.json` 的 `0x0021AC40 → iso_off 0x001AE4C0` 一致）：

```
iso_off(va) = va − 0x00100000 + 0x80 + 295*2048 = va − 0x0006C780
```

| # | 站点 VA | ISO 偏移 | 原字 | 建议新字 | 理由 / 风险 |
|---|---|---|---|---|---|
| **F1** | `0x00539174` | `0x004CC9F4` | `AE620004` `sw $v0,4($s3)` | `j  <cave>`（`0x0C000000\|(cave>>2)`） | 在 malloc 之后插入 NULL 检查的唯一入口（4 B 够放一条 `j`）。**必须配 cave**，不能原地塞两条指令 |
| **F2** | `<cave>`（空闲 cave，见 `docs\REPORT_cave_count_vs_bytes.md`） | — | 空 | 见下方 cave 代码 | 失败时 `s0 = 0` 并跳到既有尾声 `0x005392A0`，让返回值变成 0 |
| **F3** | 不改 `0x005392A0` | — | — | — | **不要**把 `0x005392A0`(`72001628`) 直接改成 `lw $v0,8($s3)`：调用者把该返回值也当**尺寸/指针**参与后续算术（`0x0051BF54..0x0051BF94`：`s1[0x30] + 对齐量` 的 divu/sll/subu）。改语义会引入新问题 |
| **F4** | 不改 `0x004039C8` | — | — | — | memcpy 是库函数，全 .text 169 处调用；在它内部拦截 NULL 会误伤正常 `memcpy(dst=0)` 的语义（不该动） |

**F2 的 cave 代码（建议，待下一轮验证后统一出盘）**

```
cave:
    beq  $v0, $zero, .fail      ; malloc 返回 0 ?
    nop
    sw   $v0, 4($s3)            ; 成功：原逻辑
    sw   $v0, 8($s3)
    j    0x0053917C             ; 回到原流程（继续建源/尾指针）
    nop
.fail:
    sw   $zero, 4($s3)          ; 基址 = 0（保持结构自洽）
    sw   $zero, 8($s3)
    move $s0, $zero             ; ★ 让既有尾声 0x005392A0 的 pcpyld v0,s0 返回 0
    j    0x005392A0             ; 走既有尾声
    nop
```

**为什么这样修是「最小且能用既有错误处理」**：
- `0x00539110` 的返回值唯一的消费者是调用者 `0x0051BE10` 的 `sw v0,52(s1)` / `sw v0,48(s1)` + `bne v0,zero`；返回 0 ⇒ 调用者走**它自己的**失败分支：`free(s1[0x14])`（或 `free(s1[0x1c])`）、清零、置失败标志、跳过后续解压（`0x0051BEB4..0x0051BEE4` / `0x0051BF1C..0x0051BF38`、`0x0051BEF0`、`0x0051BFA4`）。
- 不改分配器、不改 memcpy、不改调用者，只给「解压器的分配点」加 4 条指令 + 一次跳转。
- 副作用面：`sink[4]/[8]` 保持 0（与当前失败时的值一致），不会有新的写行为。

**其它可选（非首选）**
- 若允许改调用者：在 `0x0051BEAC`/`0x0051BF14` 之后追加「若 `sink[4]==0` 则跳失败分支」——同样需要 cave，且要改两处（不推荐）。
- 若想根治「第 44 帧分配失败」本身：那是**堆余量**问题（可能来自 MENU.IMG 重建后的驻留尺寸变化，见 §5.4），属数据/容量侧，需要先做 §5.5 的对照实验才能定向（本轮不可判定）。

## 9. 对上一轮报告（`REPORT_SAVESTATE_REPRO.md`）的更正

1. **§3.2「0x0055B7B0/B4 第 44 帧与对照分叉 ⇒ 分叉点被钉在第 44 帧」**：该字段每帧被反复改写（同一帧内成对命中即为证据），帧边界采样值不同只是采样瞬间不同；**不是**语义分叉。真正的第 44 帧异常是「申请 0x10011 返回 0」（§3.4）。
2. **§5.3「`-grwatch` 64 命中上限被低端地址用完」**：不成立。`MAX_WATCH_HITS` 是**每个监视区各自**的预算（`GRResearch.cpp:175` + `w.hits`）；`0x0055B7B0` 那一区是自己在前 8 帧被写满 64 次的（本轮 `-grwatch 5617584 4` 复现同样结果）。
3. **§4 根因假设「`0x00101xxx` 字符串/列表管理代码拿着错误指针去写」**：方向不对。写低端内存的不是 `0x00101xxx`，而是 `0x00539110` 这个 LZ77 解压器；`0x00101xxx` 是**堆管理器**（`0x00102D40` = malloc），它是「返回 0 的那一方」，不是「拿错指针的那一方」。用户机上的 `TLB Miss, pc=0x101d10…0x102584`（+ store 到 0x14/0x10）与本次的 `sink[4]/sink[8]` 被写 0 属**同一条因果链的两端**（分配失败 → NULL 入结构 → 后续写 NULL+偏移），可作为下一轮的验证方向。
4. **§6.4「走 X 切火箭弹 → R1 发射那条路径」**：本轮按任务书表跑了，未复现（§4）。
