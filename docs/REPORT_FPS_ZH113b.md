## 0. 结论

> ### ★ (iii) **本地未复现 2fps。** 7 条 32000 帧的手臂（3 张盘、4 份输入表、两个相反顺序）+ 1 条 probe，
> 全部 `TLB Miss = 0`、`Trap = 0`、`unmapped = 0`、`Pausing = 0`；
> **全部 7 条里最坏的单帧是 33.395 ms（29.9 fps），最干净那对里最坏只有 15.080 ms（66.3 fps）** ——
> 与用户报的 2 fps 相差 15~33 倍。**两盘都没有出现帧率塌陷，也没有任何"冻结/空转"段。**

> ### ★★★ 但抓到一个**比 2fps 更值钱、且可复现三次**的硬事实：
> **在同一批内（同输入表、同帧数、同设置、串行不并发），汉化盘比英文原盘慢 25%~40%。**
> 最干净的一批（第四批，两臂**都没有任何外来实例**、渲染计数差 0.04%、读盘逐段相同、
> 同画面段序列逐段相同）：
> **`GR_ZH113b_v4` = 91.04 fps vs `GR_EN_ORIG_v4` = 127.74 fps（EN/ZH = 1.403）**，
> 而 `@HWSTAT@ Average CPU Thread Time` = **10.818 ms vs 7.701 ms（+40.5%）**，CPU Thread Usage 两臂都 96.7%。
> ⇒ **多出来的时间全在 EE 侧 CPU，不在渲染、不在读盘、不在模拟器配置。**
> ⇒ 而且**连"屏幕上只是一张静态预渲染贴图"的 f300–540 段也慢 11~12%**
> （ZH `192.97`/`193.54` fps vs EN `214.41`/`219.17` fps，两批独立复现）
> ⇒ **病根在"引擎起来之后每帧都在跑的补丁代码"，不是"汉化文本画得多"。**

三种候选的判定：

| 候选 | 判定 | 依据 |
|---|---|---|
| (i) 本地复现 2fps 且只在汉化盘 | **否** | 7 臂全部 `TLB=0 / Trap=0 / unmapped=0`；`@HWSTAT@ Max Frame Time` 汉化盘最好的一批 15.080 ms（66.3 fps）、最差的一批 33.395 ms（29.9 fps）；**慢窗口 0 个**；最长连续同画面 300 帧且是那张静态记忆卡贴图 |
| (ii) 两盘都出现（与汉化无关） | **否** | 两盘都没出现 |
| **(iii) 本地未复现** | **★ 是** | 见 §4/§5；环境差异逐条列在 §7 |

> ⚠ (iii) **不等于**"汉化无罪"——本轮同时量到汉化盘有 **25~40% 的 EE 侧 CPU 回归**（§6），
> 这是**独立于 2fps 的一条新事实**，需要 Lead 决策是否追。

### 3.1 如实记录：A/B 手臂**没能进关卡**（这是本轮最大的未达成项）

**probe（臂 0）进过关卡** —— `out\zh113b_probe\snap_f00012900.png` 是 in-level 3D 场景 + HUD 正常
（罗盘 / 武器 030 / x4 倍镜），f12600 是「载入中…」。**所以这张输入表在原理上能到 in-level。**

但 **5 条 32000 帧的手臂全都没进**：

| 批 | 实际停在哪 | 截图证据 |
|---|---|---|
| 一（v2） | **小队设置页**，且被 f9000 那一下 cross 把小队清空了（队员全是「－空－」，「开始」变灰） | `out\GR_ZH113b\snap_f00015480.png`、`f00018420.png` |
| 三（v3） | **小队设置页**（焦点在不同队员上，f11500..12700 五下 cross 全没按到「开始」） | `out\GR_ZH113b_v3\snap_f00014040.png`、`f00018000.png`、`f00024240.png` |
| 四（v4） | **多人游戏菜单**（地图/游戏类型/难度/时间限制/重生 + 地图预览） | `out\GR_ZH113b_v4\snap_f00014040.png`、`f00024240.png` |

**根因（两条，都是有证据的）**：

1. **`cross@5400` 的有无会改变整条轨迹**：probe 的 D 段是 4 次 cross（4200/4700/**5400**/6500），
   v2/v3 是 3 次。少一次 ⇒ 后面每一步都晚一点 ⇒ 到「小队设置」页的时刻不同。
2. **小队设置页的焦点位置对"页面出现的那一帧"极敏感**：`up hold 7700..12900` 这段窗口
   落在不同的焦点起点上，就会停在不同条目（probe 停在「开始」，v2/v3 停在队员/顺序箭头）。
   `cross` 打在「全部取消分配」上会清空小队、打在「开始」上才会载入关卡。
   而**引导阶段的帧号本身会漂移几十~几百帧**（读盘/记忆卡时序），所以开环固定帧号无法可靠穿过这条链。
   ⇒ 这正是项目里 `tools\capture\nav_state.py` 存在的理由（它是**闭环**：跑一轮 → 判界面 → 调计数 → 再跑）。

**因此**：臂 1–7 的数字是**「引导 → 主菜单 → 战役 → 简报页 → 小队设置页 / 多人游戏菜单」负载**下的对比，
外加被送到那些界面上的 R1 / cross / 方向键 / start / select 等输入。
**这不影响 §6 的结论**（f300–540 那段跟这些界面完全无关，也慢 11%），
也不影响 §4 的"没复现 2fps"结论（负结论不依赖走到了哪一屏）。
**但"in-level 里射击 / 暂停菜单存读档 / 切换小队页面"这三件事，本轮没有在正确的界面上做到 —— 如实列为未达成（§8）。**

## 6. ★ 主发现：汉化盘有 25~40% 的 EE 侧 CPU 回归

### 6.1 三个对照把原因夹死了

**(a) 渲染负载相同** —— 见 §5.2：Draw Calls / Render Passes / Copies 差 **0.04%~0.11%**，
GS Thread 8~11%、GPU <1%（都不是瓶颈）。
第一/三批也一样（第一批：481673 vs 481657 = 0.003%）。

**(b) 读盘行为相同** —— `cdvd.log` 每行 = `<frame> <lba>`，`cdvd_bands.py` →
`work\builds\GR_FPS\CDVD_BANDS.json`：

* **第四批：总读 62451 / 62459，8 个阶段逐段相同，寻道跳距逐段相同。**
* 第一批：总读 64915 / 64923，逐段相同（只差 8 个扇区，来自 `MENU.IMG` 尾部搬迁）。

⇒ **不是"汉化盘让游戏多读/读得远"。**

**(c) 多出来的时间在 EE CPU** —— `Average CPU Thread Time`：第四批 **10.818 vs 7.701 ms（+40.5%）**；
第一批 **13.868 vs 11.160 ms（+24.3%）**；第三批 **13.829 vs 10.880 ms（+27.1%）**。
CPU Thread Usage 两臂都 ~97%（EE 单线程受限）。

**(d) 两臂确实跑在同一条轨迹上** —— `cross_arm.py`（逐帧比快照 sha1），四批结果一致：

```
共同帧号 529 · 逐字节相同 = 12 (2.3%) · 不同 = 517 (97.7%)   （文本被汉化 ⇒ 大部分帧本来就该不同）
第一次分歧 @f300 —— 就是那张被重绘成中文的记忆卡贴图
"两臂逐字节同画面"的连续区间:  f840..f1200 (420 帧) · f1980..f2160 (240 帧)
```

⇒ 两臂**有 660 帧是逐字节完全相同的画面**（那两段屏幕上没有本地化内容）⇒ 帧号对齐、轨迹一致。

### 6.2 ★★ 最干净的对照：**连"只显示一张静态贴图"的那 240 帧也慢 11~12%**

先把 f300 那屏认对（截图 `snap_f00000300.png`）：它**不是 PS2/厂商 logo**，
而是**游戏自己的记忆卡提示贴图** —— `docs/han_v2/BOOT_SCREENS.md` §4.1 已定案：
`Accessing memory card (8MB) (for PlayStation®2) in MEMORY CARD slot 1…` =
**`MENU.IMG` 条目 5 `EN_MESSAGE_MC_4.RSB`（384×178 预渲染贴图，ISO LBA 776658）**，显示窗口 **f262–584**。
本项目已把它**重绘成中文**（同文档 line 175「记忆卡检查画面 f262-584 中文上屏」、
line 238「MC4『正在读取插槽 1 中的记忆卡 (8MB)…』Zpix 统一」）。
⇒ 汉化臂显示中文、英文臂显示英文（两臂该帧 sha1 不同），
但**它是贴图、不走字体渲染管线**，而且该区间两臂读盘次数完全相同 ⇒ 这一屏的**绘制成本两臂相同**。

| 子区间（`subband.py`） | 内容 | `GR_ZH113b` fps | `GR_EN_ORIG` fps | 比 | ZH_v4 | EN_v4 | 比 |
|---|---|---|---|---|---|---|---|
| **f300–540** | **只有那张预渲染记忆卡贴图**（无字体文本、该区间不读盘、引擎几乎静止） | **192.97** | **214.41** | **0.90** | **193.54** | **219.17** | **0.883** |
| f660–2460 | 标题屏 / "Press START"（开始有字体文本） | 146.76 | 192.94 | 0.76 | 141.86 | 190.64 | 0.744 |

★ **两批独立复现**：ZH 的 f300–540 段 `192.97 / 193.54` fps，EN `214.41 / 219.17` fps
⇒ **同一屏、同一成本、同一帧区间，汉化盘稳定慢 11~12%。**
（这一段的跨批复现性比整段平均值更好：它是固定内容、固定时长、只受 CPU 影响。）

⇒ 结论：**慢的不是"汉化文本渲染工作量"**，而是**引擎起来之后每帧都在跑的补丁代码**；
相对损失随"该帧引擎干了多少活"而增大（0.90 → 0.66），即**每帧一个固定增量 + 一个随工作量增长的增量**。

### 6.3 为什么不太可能是伪影

- **顺序无关**：第一批 ZH 先跑、第三批 EN 先跑、第四批 ZH 先跑 —— 三次都是 EN 快 25%~40%。
- **竞争条件不利的一方反而更快**：第一批 EN 臂带着 12 个采样点的外来实例竞争仍快 25%；
  第三批 EN 臂带 47 个采样点竞争，却是三轮里 EN 最快的一次。
- **缓存对汉化盘有利**：第一批 ZH 臂跑之前，别人的会话刚在同一台机器上反复跑过 `GR_ZH113b.iso`
  （`GR_MEMDRIFT\zh113b_long`），ISO 页缓存是热的；EN 臂是第二次跑、缓存更冷 —— 即便如此 EN 仍快 25%。
- **EN 臂多做了活**：第一批 EN 臂的 `PressSTARTbutton` / `Chooseyourprofil` 两个 needle 各命中
  **15805 / 15804 次**（汉化臂 0 次，字符串被汉化了）⇒ EN 臂的 `grlog.txt` 是 4,915,951 B，
  汉化臂只有 2,457,539 B，**多写 2.4 MB 日志还是快 25%**。
  （这同时是"两臂各自加载了自己那张盘"的硬证据。）
- **第四批零竞争**且**读盘/渲染/画面段逐项相同**，仍然差 40%。

5. **★ 顺带提醒**：本轮量到**汉化盘比英文原盘慢 25~40%（EE 侧 CPU）**。
   这**不影响可玩性**（我们的机器上汉化盘仍有 91 fps 的余量），但如果用户的机器本来就吃力，
   汉化盘会把"刚好够用"变成"不够用" —— **用户感觉"变卡"有一部分可能来自这里，而不是那个 2fps 事件。**

### 给 Lead（技术）

1. **`TLB Miss` 行数 = 唯一可零成本跨环境使用的降级判据**（Release 构建每进程最多 50 行）。
   本轮再次确认：**用户两份会话都打满 50，我们 7 条手臂都 0**。
   **"本机跑不出缺页"这条已经第四次成立，不要再当反证用。**
   同时注意：那 50 行的 pc 全是分配器 `chunk_free` 的 unlink 路径，**是"堆被踩坏"的指纹，不是帧率指纹**，
   而且每簇只持续 0.1~2.4 ms（一次性突发）。
2. **★★ 本轮最大的交付：一个本机有区分度的定量信号 `eff fps`**
   （= `grlog.txt` 的 `run end, frames=` ÷ `RUN.txt` 的 `elapsed_s`）。
   汉化盘 74.04 / 74.56 / 91.04，英文盘 92.59 / 97.86 / 127.74。
   r76 报告 §7 卡住的**盘链二分现在可以做了**，每张盘 ~4~7 分钟、只数一个数：
   ```powershell
   foreach ($v in 'GR_EN_ORIG','GR_ZH98','GR_ZH109','GR_ZH111','GR_ZH113','GR_ZH113b') {
     python work\builds\GR_FPS\tools\run_arm.py --arm $v `
       --iso "C:\...\work\builds\$v\$v.iso" `
       --frames 32000 --snap 0 --perf 1 --nav nav_play_v4.txt --tag fpsbisect
   }
   ```
   第一次掉到 ~91 fps 以下的那一版 = 引入这 25~40% 回归的版本。
   （**注意**：必须同一批内 ZH/EN 成对跑，因为不同轨迹的绝对 fps 不同 —— 见 §5.1 的 74 vs 91。）
3. **优先验的两条假说**：
   - **H-A（最高优先）**：这 25~40% 回归来自 **ELF 补丁本身**（不是数据搬迁）。判据三条：
     ① §6.2 里"只显示一张预渲染贴图"的 f300–540 段就慢 11~12%（那一屏不走字体渲染管线）；
     ② 相对损失随每帧工作量单调增大（0.90 → 0.66），像**每帧都会跑的补丁代码**；
     ③ 渲染计数与读盘计数两臂逐阶段相同（第四批 0.04% / 逐段相同）。
     最小实验：**"只把 ELF 补丁打回英文原版、数据保持汉化"的盘** vs `GR_ZH113b`，
     或反向（英文 ELF + 汉化数据），各跑一次 v4 导航比 eff fps。
   - **H-B**：这 25~40% 与用户的 2fps 是同一件事的两端（补丁代码在某个状态下代价爆炸）。
     判据 = 本轮汉化盘最坏单帧 15.08 ms（66.3 fps），离 2fps 差 33 倍
     ⇒ H-B 需要额外的触发条件（配置 / BIOS / 存档状态），不能只靠代码回归解释。
4. **下一轮第一件事仍然是"对齐用户配置"**：把 `EmuFolders::DataRoot` 指到 `%LOCALAPPDATA%\PCSX2`
   （一行 override，属已授权文件），再重跑一次短测。**这比再多跑几对 A/B 更值钱。**
5. **要真正覆盖"in-level 射击 / 存读档 / 小队页面"，开环固定帧号脚本不够**（§3.1 的根因）。
   建议用现成的闭环 `tools\capture\nav_state.py`（跑一轮 → 从 `drawlog` 判界面 → 调计数 → 再跑），
   或给 gsrunner 的 `-grinputlive` 写一个"看截图再决定下一个键"的驱动器。
   **本轮的输入表（`nav_play_v4.txt`）已经把"到小队设置页为止"这一段稳定跑通了**，可以直接复用做前缀。
