## 二、根因

### 2.1 文本对、字形对 —— 是引擎取不到

| 盘 | 0xEE「个」的 FT 记录（large / default 两个 face 相同） | 框内墨 |
|---|---|---|
| GR_ZH98（搬字前） | `pad=0 advance=16 rect=(288,354,304,370)` | 26 px |
| GR_ZH108（现役） | `pad=0 advance=16 rect=(1008,195,1024,211)` | **26 px** |

- 两处的 16×16 点阵**逐像素相等**（差异 0 px，形状就是正确的「个」）；
- 旧位置 `(288,354,304,370)` 在现役盘上**已清空**（墨 0）；
- `pad`(rec[0]) / `advance`(rec[1]) = `0`/`16`，**一个字节没动**。

⇒ 文本对、字形对、记录指向也对 —— 唯一的问题是这个矩形**落在了哪里**：
`(1008,195,1024,211)` 的右缘 `u1 = 1024` **正好等于贴图宽度**。

### 2.2 这个矩形是怎么跑到贴图右缘的：round54 的「64 列」布局

`tools/iso_build/patch_zh104_relocate.py`（round54，见 `docs/REPORT_relocate_zh104.md`）把 84 条
「占着对偶格」的单字节字形搬到对偶网格之外的两条 16 行带里，落点公式是

```
bands = (195, 211);  x_step = 16;  n_cells = 128
cells = [(y0, 16*k) for y0 in bands for k in range(W // CW)]      # W//CW = 1024/16 = 64 列!
⇒ x = 0, 16, 32, …, 976, 992, 1008        ← 最后两格已经越过安全上界
```

`work/builds/GR_ZH98/temp/r54/layout.json` 里逐条可查：`0xED「这」 → (992,195,1008,211)`、
`0xEE「个」 → (1008,195,1024,211)`（「个」是那批里码位最大的 16×16 字形，正好排到第 64 格）。
84 条里**只有这 2 条**越过 `x=976`。

另外 round55（`tools/iso_build/patch_zh105_ft_rects.py`）为了腾出 7 个被压住的可用格，把 17 条
**空矩形**（`0x20` 空格 / `0x7F` / `0xA1..0xAD` 对偶 lead / 图标码 `0xB1`/`0xB5`）指到了
`(1014,0,1024,16)`、把 3 条**空** 16×16（`0xAE`/`0xAF`/`0xB0`）指到了 `(1008,0,1024,16)` ——
它自己的注释把那一片（`x=992..1007`）当成「对偶格公式永不采样的空白垃圾场」。
它们全是 **0 墨**，所以今天没有可见症状（见 §2.4）。

### 2.3 安全上界 = `x ≤ 976`（`u1 ≤ 992`）—— 三条证据 + ★ 用户实机订正

> ★ **round59 事后订正（用户实机截图，务必先读）**：用户提供的 `GR_ZH108`「制作人手记 1」页截图显示
> **`0xED`「这」`(992,195,1008,211)`（`u1=1008`）渲染完全正常** ✓，而它旁边「这**个**月」的
> 「个」（`0xEE`，`u1=1024`）是斜纹方块 ✗。
> ⇒ **真正被证伪的是「`u1 > 992` 就会坏」这个说法** ✗：`u1 = 1008` 是**安全**的。
> **实测边界**：只有 **`u1 = 1024`（矩形右缘正好等于贴图宽度）** 才坏。
> 本报告的 §2.3 标题与下面第 2 条因此**过窄**（它只证明了 `u1 ≤ 992` 可用，没证明 993..1008 不可用）。
> **修复采用的 `x ≤ 976` 是"保守但无害"的选择**：它等于**对偶网格自己寻址到的最右一列**，
> 是最容易守住、最有解释力的硬不变量；越界记录里**只有 `0xEE` 有可见症状**，其余搬走只是消除地雷。

1. **引擎自己的寻址上界**：对偶网格公式 `tcslib.atlas_cell_xy_engine_view`：
   `col = slot % 62 ≤ 61 ⇒ x = 16*col ≤ 976`。这不是"惯例"，是**引擎代码里的除法/取模**：
   引擎能自己算出来的最右一列就是 `x=976`（`u1=992`）。
   实测那一列在图集上有 **18 个活字形、共 1197 px 墨** —— 引擎确实在采样 `x=976`。
   （★ 订正：这只说明 `x=976` **可用**，**不能**推出 `x>976` 不可用。）
2. **实机证据（同一页）**：**`0xEC`「选」在 `(976,195,992,211)`（`u1=992`）显示正常**；
   用户后续截图又给出 **`0xED`「这」`(992,195,1008,211)`（`u1=1008`）也正常**；
   而 **`0xEE`「个」`(1008,195,1024,211)`（`u1=1024`）是斜纹方块**。
   ⇒ **可用区间至少到 `u1=1008`；坏的是 `u1=1024`（右缘 = 贴图宽度）。**
3. **历史包线**：搬字前的 `GR_ZH98` 上，3 个 face 全部 **544 条**非退化记录 `max(u1) = 992`；
   `GR_EN_ORIG`（512 宽 PSMT8 贴图）是 513。**"记录矩形右缘压到贴图宽度"是 round54 才第一次出现的事情。**
   （★ 订正：这是"历史上没人越过 992"的**巧合包线**，不是"越界必坏"的证明。）

> 机制旁证（**没有**重新逆向，只引仓库既有结论）：`docs/han_v2/PS2_FONT_MECHANISM.md` §2.2 记
> `ComputeCharTextureCoords` 把记录坐标 `>>1` 成"半 texel / 512 空间"的纹理坐标、再按纹理尺寸归一化
> ⇒ 坐标上界正好是 `512 = 1024/2`，而「个」的 `u1 = 1024`（`/2` 后 = 512）**落在上界外侧**。
> 本轮只把这条当旁证；硬证据是上面 1/2/3 三条。

### 2.4 复核结论（与 Lead 初步定位的两点出入，已按实测定稿）

现役盘 `u1 > 992` 的记录实测 **22 个码位 / 3 个 face 共 46 条记录**（不是 4 条）：

| 码位 | 记录矩形 | 有墨? | 说明 |
|---|---|---|---|
| `0xED`「这」 | `(992,195,1008,211)` | **54 px** | 活的单字节汉字（正文 247 处）—— 越界，但**没有实机证据说它坏**（坏字那页没有「这」）⇒ 本轮一并搬走 |
| `0xEE`「个」 | `(1008,195,1024,211)` | **26 px** | 活的单字节汉字（正文 222 处）—— **用户看到的唯一坏字**；也是全盘**唯一**"有墨 + 右缘 = 贴图宽度"的记录 |
| `0xAE` `0xAF` `0xB0` | `(1008,0,1024,16)` | 0 px | round55 只改了记录表、把它们指到了空区（**没有墨**）⇒ 今天无症状；但它们是 dump 里"真正还能用的单字节码"，留在贴图右缘是地雷 |
| `0x20` `0x7F` `0xA1..0xAD` `0xB1` `0xB5` | `(1014,0,1024,16)` | 0 px | 空格 / 未用码 / 对偶 lead / 引擎硬编码 UV 的图标码 ⇒ 引擎要么不画、要么画空白、要么从别处取 UV ⇒ 今天无症状 |

⚠ 两点与 Lead 初步定位不同，请注意：
1. **`0xAE`/`0xAF`/`0xB0` 在现役盘上是 0 墨**（它们的字形像素早被 round55 留在了别处）——
   "唯一活着的字是 `0xEE`"这句话成立，但理由不是"另外 3 条也画得出来只是没用"，而是"另外 3 条本来就是空的"；
2. 越界记录共 **22 条**（`0xED` 也在内，`x=992`），不是 4 条。

## 三、为什么前两轮 A/B 没抓到（以及静态工具为什么也看不见）

1. **搬字发生在 round54（GR_ZH103 → GR_ZH104），而用户参与过的 A/B 都在它之后**：
   r57 是 `GR_ZH105 vs GR_ZH107`、r58 是 `GR_ZH107 vs GR_ZH108` —— 三张盘**都已经是搬字后**的盘，
   差异里当然看不到"搬字前 vs 搬字后"。**round54 从未做过这个 A/B**（它的验收只有静态断言 + 回读自检）。
2. **静态工具结构上看不见**：`single_cell_font.py` 是按**记录矩形**去图集取格的 —— 它在 GR_ZH108 上
   就已经报「个 = `match`, diff 0」（本次复核也一样：`0xEC`/`0xED`/`0xEE` 三条都 `match`、错误 0）；
   `dump_font.py` 的 `has_ink` 同样只看"矩形 ±(4,2) 邻域有没有墨"。
   它们证明的是**"字形画在记录指的地方"**，证明不了**"引擎能不能取到那个地方"**。
   ⇒ 这一类 bug **只有实机 A/B（或"上界不变量"这种结构性判据）能抓**。
3. 本次复核顺带证实 **round54 的搬字本身是逐像素忠实的**：84 条记录现役矩形 == 计划矩形，
   且 84/84 的现役新矩形像素 == `GR_ZH98` 旧矩形像素（逐像素相等）。问题只在**落点越界**这一点上。

## 四、修法（`tools/iso_build/patch_zh109_edge_fix.py`）

### 4.1 规则

> **把每一条 `u0 ≥ 992` 的非退化 FT 记录，连同它的字形像素，搬到 `x ≤ 976`（`u1 ≤ 992`）的安全空位；保尺寸。**

- 落点 = 搬字带空区里 **无墨 / 不被任何对偶槽位（全部 1504 个）覆盖 / 不被任何记录矩形覆盖** 的连续空格
  （确定性扫描：y 升序、x 升序、16 像素对齐；不足时退 2 像素步长）；
- **有墨的 2 条**（`0xED`/`0xEE`）：各自独立落点，**像素逐像素搬过去**，旧位置清空；
- **空的 16×16 三条**（`0xAE`/`0xAF`/`0xB0`）：各自独立落点（它们是"还能用的单字节码"，
  留成互相独立的矩形，免得以后给其中一个写真字形时连累另外两个）；
- **17 条空 10×16**（`0x20`/`0x7F`/`0xA1..0xAD`/`0xB1`/`0xB5`）：今天**共用同一个矩形**，整组**共用一个**新空矩形
  （空白 → 空白，画面必然不变；搬它们只为把"任何记录矩形都不得越过 `x=976`"做成**硬不变量**，不留地雷）。

| `0xEE` | **个** | 16×16 | `(1008,195,1024,211)` | **`(352,213,368,229)`** u1=368 | 26 px | 222 | large, default |
| `0xAE` | – | 16×16 | `(1008,0,1024,16)` | `(384,213,400,229)` u1=400 | 0 | – | large, default |
| `0xAF` | – | 16×16 | `(1008,0,1024,16)` | `(416,213,432,229)` u1=432 | 0 | – | large, default |
| `0xB0` | – | 16×16 | `(1008,0,1024,16)` | `(448,213,464,229)` u1=464 | 0 | – | large, default |
| `0x20` `0x7F` `0xA1..0xAD` `0xB1` `0xB5`（17 条） | – | 10×16 | `(1014,0,1024,16)` | `(480,213,490,229)` u1=490（**共用一个**） | 0 | – | large, default（`0x20`/`0x7F` 另含 huge） |

Lead 点名的「那 4 条」（`0xAE`/`0xAF`/`0xB0`/`0xEE`）新矩形全部 `x ≤ 976` ✓（上表加粗两条是**有墨**的）。

### 4.3 落点为什么取 `y=213` 而不是带内的 `y=211`

`dump_font` / 单格字库判"这条记录画得出来吗"时看的是 **矩形 + (4,2) 偏置 + ±(4,2) 邻域**。
落点若贴着带 1 的字形墨（带 1 的格是 `y=195..210`），那些**本来就该是空**的记录会被邻域里的墨"染"成"有墨"，
让字库 dump 的「有墨 502 / 无墨 42」这个对照数字变掉。取 `y=213`（离带 1 的墨 ≥2 px）并让落点之间留出
`±(4,2)` 间隔 ⇒ 这些空矩形的新邻域仍然干净，**有墨/无墨逐条不变**（见 §六 ⑦）。

### 4.4 硬断言（写盘前，全部通过）

| ② | 待清像素只落在旧矩形内；旧矩形 ∩ 对偶格 = 0、∩ **别的**记录矩形 = 0（有墨的记录先搬后清） | ✓（4 个旧矩形 / 22 条记录） |

| ⑥ | 搬完后 3 个 face 全部非退化记录 `max(u1) ≤ 992` | ✓（1024 → 992） |

### 4.5 幂等
