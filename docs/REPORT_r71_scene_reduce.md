## 4. ④ 可回收字形诊断 —— **只能救回 2 个字，剩下 45 个必须改文**

### 4.1 诊断方法与结论

口径（与 round49 `_font_recycle_zh98` 同源，按**本轮产物**重算）：

```
LIVE = 本轮改后三张注入表的正文
     ∪ GR_ZH113 的 9 张 view 表里所有 ≥0x80 的字符（xml/txt/mis/atr/其它RES/ELF/ISO文件/二进制容器可读串）
DEAD = charset pair_of 的 1504 个字 − LIVE
```
★ 关键：**不算 GR_ZH113 现役 long 表**——它 58 条全部会被本轮替换，只被它引用的字本轮后就成死字形。

**结果**：

| 项 | 数量 |
|---|---|
| 1504 个对偶槽里"任何文本都不用"的字 | **2 个：`凌` `牌`** |
| 110 个单字节码里"任何文本都不用"的 | 0 个 |
| 其中"只靠旧缩减版 long 表活着"的 | **0 个**（旧文本用到的字，别处也都在用） |
| 高精准度条目还缺的字 | **47 种** |
| 够不够换 | **不够，差 45 个** |

补充证据（盘上自算，`GR_ZH113b/font/GR_ZH113_B_font_summary.json`）：

* 汉字（对偶码）总容量 = 16 lead(0xA1..B0) × 94 trail = **1504**，**已用 1504 ⇒ 空 0 个**；
* "现在就能直接放新字"的干净格 = **0 个**；"格子上压着旧字形、得先回收"的 = **0 个**；
* 单字节码已用 110，`0x80..0xFF` 只剩 2 个没主的字节 **`B1 B5`**，而它们是**引擎硬编码的手柄图标码**
  （`{{BTN:E0B1}}` △ / `{{BTN:E0B5}}` ✕）⇒ 动不得，**真正能用的单字节码 = 0 个**。

**建议清单（给"另一条线"的扩字/回收工作）**

### 4.2 为什么不能"扩到 1504 以上"

引擎对偶码寻址上限就是 16 lead × 94 trail = 1504（`_expand_zh113` 记录：round67 已把 1175 扩到 1504，
"用满引擎 lead 上限"）。`font_compact` 本轮也确认：`对偶槽位 1504 = 在用 1504 + 空闲 0`。
⇒ **不回收就没得加**。

## 7. 需用户拍板 / 已知限制 / 与指令的偏差（如实）

### 7.1 ★ 目录名：`GR_ZH113_B` → `GR_ZH113b`（构筑器不接受小写后缀）

`tools/iso_build/make_build.py:891` 有硬断言：
`re.fullmatch(r'(GR_ZH\d+(_[A-Za-z0-9]+)*|GR_TEST_[A-Za-z0-9_]+)', ver)`
⇒ `GR_ZH113b` **不合法**，`GR_ZH113_B` 才合法。做法：**用 `GR_ZH113_B` 构筑（exit 0）→ 成功后把目录与 ISO 改名成 `GR_ZH113b`**；
`build_info.json`、`text/`、`font/`、`temp/` 里的文件名/路径仍是 `GR_ZH113_B`（改名会让 `text.meta.json` 的表格名对不上）。
细节见 `work/builds/GR_ZH113b/README_rename.md`。**如果 Lead 更希望保持构筑器原名，把目录改回 `GR_ZH113_B` 即可，ISO 内容不受影响。**

### 7.2 ★ 注入表必须"挂在 GR_ZH113 的骨架上"（第一次构筑失败的原因）

丰富版底本来自 **GR_ZH109 时代的 dump**，它的 `offset`/`len_bytes` 是 GR_ZH109 盘的口径，
直接拿去注入 GR_ZH113 会被结构核对照拦下：
`!! SFXML:T0028: CSV 的 offset/len (23177/145) 与源盘 (23177/143) 不符 —— CSV 已过期/来自别的盘`（exit 1）。
⇒ 正确做法：**取 `GR_ZH113/text/GR_ZH113_text_long.csv` 当骨架（列都对），只替换 `text_edited` 列**（脚本 `r71r_rebase.py`）。
⚠ 另外：`--check-only` **不查** offset/len（所以第一次 `--check-only` 是 exit 0 的假绿），
**只有真正写盘（`--dst`）才会跑结构核对照**——后续轮次请务必以"能写盘"为准。

### 7.3 ★ 共享文件 `charset_compiled_zh16.json` 被构筑器自动"盖章"

本轮构筑跑了默认的 `font_compact` 步骤（**没有**加 `--no-font-compact`，按指令要求）：
它报告 `对偶槽位 1504 = 在用 1504 + 空闲 0`、`字库已经是紧凑的 ⇒ 无需重排+无需重编码（0 改动）`，
产物与基底同 sha256、字体容器 0 改动（Lead 修的"网格占满"崩溃确实没再复现）。
但它按既有流程调用了 `stamp_charset(ver, iso_sha)`，于是 **charset JSON 的 3 个字段变了**：
`_font_compact.iso_version` → `GR_ZH113_B`、`iso_sha256` → `ff3abd3c…`、`stamped` → `2026-10-14 18:46:56`。

* **字→码位映射一字未变**：用**两份盘各自的** `font_charset.csv`（dump_font 从盘上算出的独立记录）
  逐字对表，`GR_ZH113` 与 `GR_ZH113b` 各 1612 条 **0 不一致**（`r71y_charsetdelta.py`）；
  `pair_of` 仍 1504 / `codes` 仍 110 / `moved_last=0` / `codes_changed_last=0`。
* 我**没有**手工编辑过该 JSON；但这条"共享文件被动过"必须让"另一条线"知道——
  如果那边的流程依赖 stamp 指向 GR_ZH113，请以本条为准或回盖。

### 7.4 `short` 表 11 行 `max_bytes` 变化（不是文本变化）

`max_bytes` = `len_bytes` + **同容器余量**，是**只读参考列**。SFXML 正文变长后该容器余量变化
（23808 → 21387），于是 11 行 SFXML 短条目的 `max_bytes` 跟着变；**`text_zh`/`text_edited` 一字未变**
（`r71ad_shortdiff.py` 的逐列比对：变化列只有 `max_bytes`）。容器余量仍剩 36790 B（`tail_free_bytes`），**未超槽**。
